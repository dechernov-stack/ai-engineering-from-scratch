## Проблема

Каждые полгода выходит новый мультиагентный фреймворк. AutoGen в 2023. CrewAI в 2024. LangGraph и OpenAI Swarm в 2024. Google ADK в апреле 2025. Microsoft Agent Framework RC в феврале 2026. Каждый пресс-релиз заявляет, что это «правильная абстракция».

Если пытаться изучать их по одному, вы быстро выгорите. API выглядят по-разному. В документации по-разному трактуется, что такое «агент». Один фреймворк называет своё общее хранилище памяти «доской объявлений» (blackboard), другой — «пулом сообщений», третий — «StateGraph». Начинает казаться, что вся область просто бесконечно переизобретает одно и то же.

Это не так. Под маркетингом скрываются четыре стабильных примитива. Выучите их один раз — и сможете прочитать любой новый фреймворк за один абзац.

## Концепция

### Четыре примитива

1. **Агент (Agent)** — системный промпт плюс список инструментов. Без состояния; каждый запуск начинается заново с его системного промпта и текущей истории сообщений.
2. **Передача управления (Handoff)** — структурированная передача управления от одного агента другому. Механически — это либо вызов инструмента, возвращающий нового агента, либо ребро графа, следующее условию.
3. **Общее состояние (Shared state)** — любая структура данных, которую могут читать (иногда и писать) несколько агентов. Пул сообщений, доска объявлений, хранилище ключ-значение, векторная память.
4. **Оркестратор (Orchestrator)** — тот, кто решает, кто говорит следующим. Варианты: явный граф (детерминированный), LLM-селектор говорящего (мягкий), вызов передачи управления от последнего говорившего (OpenAI Swarm), или планировщик над очередью (роевая архитектура).

Это всё пространство проектирования целиком. Каждый фреймворк выбирает значения по умолчанию для каждой оси; всё остальное — это поверхностный синтаксис.

### Как каждый фреймворк 2026 года отображается на эту модель

| Фреймворк | Агент | Передача управления | Общее состояние | Оркестратор |
|-----------|-------|---------|--------------|--------------|
| OpenAI Swarm / Agents SDK | `Agent(instructions, tools)` | вызов инструмента возвращает Agent | забота вызывающей стороны | следующий вызов handoff от LLM |
| AutoGen v0.4 / AG2 | `ConversableAgent` | speaker-selector на GroupChat | пул сообщений | функция-селектор (LLM или round-robin) |
| CrewAI | `Agent(role, goal, backstory)` | `Process.Sequential / Hierarchical` | выходы Task, связанные в цепочку | управляющий LLM или статический порядок |
| LangGraph | функция-узел | ребро графа + условие | `StateGraph` редьюсер | граф, детерминированный |
| Microsoft Agent Framework | агент + паттерны оркестрации | специфично для паттерна | thread / context | специфично для паттерна |
| Google ADK | агент + карточка A2A | задача A2A | артефакты A2A | решает хост |

Поверхностные различия выглядят огромными. Под ними — те же четыре рычага.

### Почему это важно

Как только вы увидите примитивы, сравнение фреймворков превращается в короткий чек-лист:

- Доверяет ли оркестратор маршрутизацию LLM (Swarm) или фиксирует маршрутизацию в коде (LangGraph)?
- Общее состояние — это полная история (GroupChat) или проекция (редьюсер StateGraph)?
- Могут ли агенты изменять промпты друг друга (менеджер CrewAI) или только передавать управление (Swarm)?

Эти три вопроса отвечают на 80% вопроса о том, какой фреймворк подходит под конкретную задачу. Вы перестаёте искать «лучший мультиагентный фреймворк» и начинаете проектировать под ту ось, которая действительно важна.

### Инсайт про отсутствие состояния

Все примитивы, кроме общего состояния, не имеют состояния. Агент — это функция от (промпт, инструменты). Передача управления — это вызов функции. Оркестратор — это планировщик. **Единственная сущность в системе, обладающая состоянием, — это общее состояние.** Именно там живут все интересные баги: отравление памяти (Урок 15), порядок сообщений, версионирование, конкуренция за запись.

Фреймворки, скрывающие общее состояние (Swarm), перекладывают проблему на вызывающую сторону. Фреймворки, централизующие его (чекпоинт LangGraph, пул AutoGen), делают его инспектируемым, но перекладывают стоимость координации на реализацию общего состояния.

### Анатомия отдельного примитива

#### Агент

```
Agent = (system_prompt, tools, model, optional_name)
```

Никакой памяти. Никакого состояния. Два агента с одинаковым системным промптом и инструментами взаимозаменяемы. Всё, что выглядит как состояние, привязанное к конкретному агенту, на самом деле находится в общем состоянии или в протоколе передачи управления.

#### Передача управления

```
Handoff = (from_agent, to_agent, reason, payload)
```

Доминируют три реализации:

- **Возврат функции** — инструмент возвращает следующего агента. Это паттерн OpenAI Swarm. Агенты несут маршрутизацию в своих схемах инструментов.
- **Ребро графа** — LangGraph. Рёбра декларативны. LLM выдаёт значение; условие выбирает следующий узел.
- **Выбор говорящего** — AutoGen GroupChat. Функция-селектор (иногда сама являющаяся вызовом LLM) читает пул и выбирает, кто говорит следующим.

#### Общее состояние

```
SharedState = { messages: [], artifacts: {}, context: {} }
```

Как минимум — список сообщений. Часто больше: структурированные артефакты (выходы Task в CrewAI), типизированный контекст (редьюсеры LangGraph), внешняя память (MCP, векторная БД).

Две топологии: **полный пул** (каждый агент видит каждое сообщение) и **проекция** (агенты видят представление, ограниченное их ролью). Полные пулы просты, но плохо масштабируются. Проекции масштабируются, но требуют заранее продуманной схемы.

#### Оркестратор

```
Orchestrator = ({state, last_speaker}) -> next_agent
```

Четыре разновидности:

- **Статический** — граф фиксируется на этапе сборки (детерминированный LangGraph, CrewAI Sequential).
- **Выбор LLM** — LLM читает пул и выбирает следующего говорящего (AutoGen, CrewAI Hierarchical).
- **На основе передачи управления** — текущий агент решает, вызывая инструмент handoff (Swarm).
- **На основе очереди** — воркеры забирают задачи из общей очереди; явного «следующего говорящего» нет (роевые архитектуры, Matrix).

### Что меняется между фреймворками

После того как примитивы зафиксированы, остальные проектные решения сводятся к следующему:

- **Стратегия памяти** — эфемерная или устойчивая контрольная точка (checkpointer LangGraph).
- **Граница безопасности** — кто может одобрить передачу управления (human-in-the-loop).
- **Учёт затрат** — бюджеты токенов на каждого агента.
- **Наблюдаемость** — трассировка передач управления, сохранение состояния для воспроизведения.

Всё это реализуемо поверх примитивов. Ни одно из этих решений не является новым примитивом.

## Построй это

`code/main.py` реализует четыре примитива в ~150 строках Python на основе stdlib. Никакого настоящего LLM — каждый агент представляет собой скриптовую политику, чтобы фокус оставался на структуре координации.

Файл экспортирует:

- `Agent` — dataclass с именем, системным промптом, инструментами, функцией-политикой.
- `Handoff` — функция, возвращающая нового агента.
- `SharedState` — потокобезопасный пул сообщений.
- `Orchestrator` — три варианта: `StaticOrchestrator`, `HandoffOrchestrator`, `LLMSelectorOrchestrator` (симулированный).

Демо запускает один и тот же трёхагентный конвейер (исследование → написание → проверка) через все три типа оркестраторов и в конце выводит пул сообщений. Видно, что результаты отличаются только тем, *кто выбирается следующим*; агенты и общее состояние идентичны во всех прогонах.

Запустите это:

```
python3 code/main.py
```

Ожидаемый результат: три прогона оркестратора, по одному на каждый паттерн. Каждый выводит итоговый пул сообщений. Прогон на основе передачи управления достигает меньшего числа агентов, если исследователь решает закончить раньше — это в миниатюре иллюстрирует компромисс LLM-маршрутизации.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле значит |
|------|----------------|------------------------|
| Agent | «LLM с инструментами» | Тройка `(system_prompt, tools, model)`. Без состояния. |
| Handoff | «Передача управления» | Структурированный вызов, называющий следующего агента и опциональную полезную нагрузку. Три реализации: возврат функции, ребро графа, выбор говорящего. |
| Shared state | «Память» / «контекст» | Единственная часть мультиагентной системы, обладающая состоянием. Пул сообщений или доска объявлений. |
| Orchestrator | «Координатор» | Тот, кто решает, кто запускается следующим. Статический граф, LLM-селектор, на основе передачи управления или на основе очереди. |
| Primitive | «Абстракция» | Одна из четырёх осей, которую параметризует каждый фреймворк. Не является функцией фреймворка. |
| Message pool | «Общая история чата» | Общее состояние с полной историей. Легко понять, плохо масштабируется. |
| Projected state | «Ограниченное представление» | Специфичное для роли представление в общем состоянии. Масштабируется, требует проектирования схемы. |
| Speaker selection | «Кто говорит следующим» | Паттерн оркестратора, при котором функция (часто LLM) выбирает следующего агента из группы. |
