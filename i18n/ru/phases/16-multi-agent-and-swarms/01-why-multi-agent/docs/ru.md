# Зачем мультиагентность?

> Один агент упирается в стену. Разумное решение — не агент покрупнее, а больше агентов.

**Type:** Learn
**Languages:** TypeScript
**Prerequisites:** Phase 14 (Agent Engineering)
**Time:** ~60 минут

## Цели обучения

- Определить потолок одного агента (переполнение контекста, смешанная экспертиза, последовательное узкое место) и объяснить, когда разделение на несколько агентов — правильный шаг
- Сравнить паттерны оркестрации (конвейер, параллельное разветвление, супервизор, иерархия) и выбрать подходящий для заданной структуры задачи
- Спроектировать мультиагентную систему с чёткими границами ролей, общим состоянием и контрактом коммуникации
- Проанализировать компромиссы мультиагентной сложности (задержка, стоимость, сложность отладки) по сравнению с простотой одного агента

## Проблема

Вы построили одного агента в Phase 14. Он работает. Он может читать файлы, запускать команды, вызывать API и рассуждать о результатах. Затем вы направляете его на реальную кодовую базу: 200 файлов, три языка, тесты, зависящие от инфраструктуры, и требование исследовать внешние API перед написанием кода.

Агент захлёбывается. Не потому, что LLM глупа, а потому, что задача превышает возможности одного цикла агента. Окно контекста заполняется содержимым файлов. Агент забывает, что он прочитал 40 вызовов инструментов назад. Он пытается быть одновременно исследователем, программистом и ревьюером — и делает все три роли плохо.

Это и есть потолок одного агента. Вы упираетесь в него каждый раз, когда задача требует:

- **Больше контекста, чем помещается в одно окно** — чтение 50 файлов выходит за пределы 200 тыс. токенов
- **Разной экспертизы на разных этапах** — исследование требует иного промптинга, чем генерация кода
- **Работы, которую можно распараллелить** — зачем читать три файла последовательно, если их можно читать одновременно?

## Концепция

### Потолок одного агента

Один агент — это один цикл, одно окно контекста, один системный промпт. Представьте это так:

```
┌─────────────────────────────────────────┐
│            SINGLE AGENT                 │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │         Context Window            │  │
│  │                                   │  │
│  │  research notes                   │  │
│  │  + code files                     │  │
│  │  + test output                    │  │
│  │  + review feedback                │  │
│  │  + API docs                       │  │
│  │  + ...                            │  │
│  │                                   │  │
│  │  ██████████████████████ FULL ███  │  │
│  └───────────────────────────────────┘  │
│                                         │
│  One system prompt tries to cover       │
│  research + coding + review + testing   │
│                                         │
│  Result: mediocre at everything         │
└─────────────────────────────────────────┘
```

Ломаются три вещи:

1. **Насыщение контекста** — результаты вызовов инструментов накапливаются. К 30-му ходу агент уже потребил 150 тыс. токенов содержимого файлов, вывода команд и предыдущих рассуждений. Критические детали из 5-го хода теряются.

2. **Путаница в ролях** — системный промпт, который гласит «ты исследователь, программист, ревьюер и тестировщик», порождает агента, который наполовину исследует, наполовину пишет код и никогда не заканчивает проверку.

3. **Последовательное узкое место** — агент читает файл A, затем файл B, затем файл C. Три последовательных вызова LLM. Три последовательных выполнения инструментов. Никакого параллелизма.

### Мультиагентное решение

Разделите работу. Дайте каждому агенту одну задачу, одно окно контекста и один системный промпт, настроенный под эту задачу:

```
┌──────────────────────────────────────────────────────────┐
│                    ORCHESTRATOR                          │
│                                                          │
│  "Build a REST API for user management"                  │
│                                                          │
│         ┌──────────┬──────────┬──────────┐               │
│         │          │          │          │               │
│         ▼          ▼          ▼          ▼               │
│   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│   │RESEARCHER│ │  CODER   │ │ REVIEWER │ │  TESTER  │  │
│   │          │ │          │ │          │ │          │  │
│   │ Reads    │ │ Writes   │ │ Checks   │ │ Runs     │  │
│   │ docs,    │ │ code     │ │ code     │ │ tests,   │  │
│   │ finds    │ │ based on │ │ quality, │ │ reports  │  │
│   │ patterns │ │ research │ │ finds    │ │ results  │  │
│   │          │ │ + spec   │ │ bugs     │ │          │  │
│   └─────┬────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘  │
│         │           │            │             │         │
│         └───────────┴────────────┴─────────────┘         │
│                          │                               │
│                     Merge results                        │
└──────────────────────────────────────────────────────────┘
```

У каждого агента есть:
- Сфокусированный системный промпт («Ты ревьюер кода. Твоя единственная задача — находить баги.»)
- Собственное окно контекста (не загрязнённое работой других агентов)
- Чёткий контракт ввода/вывода (получает заметки исследования, выдаёт код)

### Реальные системы, делающие это

**Субагенты Claude Code** — когда Claude Code порождает субагента с `Task`, он создаёт дочернего агента с ограниченной задачей. Родитель сохраняет свой контекст чистым. Дочерний агент выполняет сфокусированную работу и возвращает сводку.

**Devin** — запускает агента-планировщика, агента-программиста и агента-браузер. Планировщик разбивает работу на шаги. Программист пишет код. Браузер исследует документацию. У каждого отдельный контекст.

**Мультиагентные команды разработки (SWE-bench)** — лучшие системы на SWE-bench используют исследователя, читающего кодовую базу, планировщика, разрабатывающего исправление, и программиста, реализующего его. Одноагентные системы показывают более низкие результаты.

**ChatGPT Deep Research** — порождает несколько поисковых агентов параллельно, каждый исследует свой угол, затем синтезирует результаты.

### Спектр

Мультиагентность — это не бинарный выбор. Это спектр:

```
SIMPLE ──────────────────────────────────────────── COMPLEX

 Single        Sub-         Pipeline      Team         Swarm
 Agent         agents

 ┌───┐       ┌───┐        ┌───┐───┐    ┌───┐───┐    ┌─┐┌─┐┌─┐
 │ A │       │ A │        │ A │ B │    │ A │ B │    │ ││ ││ │
 └───┘       └─┬─┘        └───┘─┬─┘    └─┬─┘─┬─┘    └┬┘└┬┘└┬┘
               │                │        │   │       ┌┴──┴──┴┐
             ┌─┴─┐          ┌───┘───┐    │   │       │shared │
             │ a │          │ C │ D │  ┌─┴───┴─┐    │ state │
             └───┘          └───┘───┘  │  msg   │    └───────┘
                                       │  bus   │
 1 loop      Parent +      Stage by    │       │    N peers,
 1 context   child tasks   stage       └───────┘    emergent
                                       Explicit      behavior
                                       roles
```

**Одиночный агент** — один цикл, один промпт. Хорош для простых задач.

**Субагенты** — родитель порождает дочерних агентов для сфокусированных подзадач. Родитель поддерживает план. Дочерние агенты отчитываются. Именно так работает Claude Code.

**Конвейер** — агенты выполняются последовательно. Вывод агента A становится вводом агента B. Хорош для поэтапных рабочих процессов: исследование -> код -> проверка -> тестирование.

**Команда** — агенты работают параллельно с общей шиной сообщений. У каждого своя роль. Оркестратор координирует работу. Хорошо, когда разные навыки нужны одновременно.

**Рой (swarm)** — множество идентичных или почти идентичных агентов с общим состоянием. Нет фиксированного оркестратора. Агенты забирают работу из очереди. Хорошо для высокопроизводительных параллельных задач.

### Четыре мультиагентных паттерна

#### Паттерн 1: Конвейер

```
Input ──▶ Agent A ──▶ Agent B ──▶ Agent C ──▶ Output
          (research)  (code)      (review)
```

Каждый агент преобразует данные и передаёт их дальше. Просто для понимания. Сбой на одном этапе блокирует остальные.

#### Паттерн 2: Разветвление / слияние (Fan-out / Fan-in)

```
                ┌──▶ Agent A ──┐
                │              │
Input ──▶ Split ├──▶ Agent B ──├──▶ Merge ──▶ Output
                │              │
                └──▶ Agent C ──┘
```

Разделение работы между параллельными агентами, затем слияние результатов. Хорошо для задач, разбивающихся на независимые подзадачи.

#### Паттерн 3: Оркестратор-исполнители

```
                    ┌──────────┐
                    │  Orch.   │
                    └──┬───┬───┘
                  task │   │ task
                 ┌─────┘   └─────┐
                 ▼               ▼
           ┌──────────┐   ┌──────────┐
           │ Worker A │   │ Worker B │
           └──────────┘   └──────────┘
```

Умный оркестратор решает, что делать, делегирует исполнителям и синтезирует результаты. Сам оркестратор — это агент с инструментами для порождения исполнителей.

#### Паттерн 4: Равноправный рой (Peer Swarm)

```
         ┌───┐ ◄──── msg ────▶ ┌───┐
         │ A │                  │ B │
         └─┬─┘                  └─┬─┘
           │                      │
      msg  │    ┌───────────┐     │ msg
           └───▶│  Shared   │◄────┘
                │  State    │
           ┌───▶│  / Queue  │◄────┐
           │    └───────────┘     │
      msg  │                      │ msg
         ┌─┴─┐                  ┌─┴─┐
         │ C │ ◄──── msg ────▶ │ D │
         └───┘                  └───┘
```

Нет центрального оркестратора. Агенты общаются напрямую друг с другом. Решения возникают из взаимодействия. Сложнее отлаживать, но масштабируется на много агентов.

### Когда НЕ использовать мультиагентность

Мультиагентность добавляет сложность. Каждое сообщение между агентами — потенциальная точка отказа. Отладка превращается из «прочитать один диалог» в «проследить сообщения через пять агентов».

**Оставайтесь при одном агенте, когда:**
- Задача помещается в одно окно контекста (менее ~100 тыс. токенов рабочих данных)
- Вам не нужны разные системные промпты для разных этапов
- Последовательное выполнение достаточно быстрое
- Задача достаточно проста, чтобы разделение добавило больше накладных расходов, чем пользы

**Цена сложности:**
- Каждая граница агента — это шаг со сжатием с потерями: полный контекст агента A сводится в сообщение для агента B
- Логика координации (кто что делает, когда, в каком порядке) сама становится источником багов
- Задержка растёт: N агентов означает минимум N последовательных вызовов LLM, больше — если им нужно обмениваться сообщениями туда-сюда
- Стоимость умножается: каждый агент тратит токены независимо

Эмпирическое правило: если задача занимает менее 20 вызовов инструментов и помещается в 100 тыс. токенов, оставайтесь с одним агентом.

## Построение

### Шаг 1: Перегруженный одиночный агент

Вот одиночный агент, пытающийся делать всё. У него один огромный системный промпт и одно окно контекста, хранящее исследование, код и рецензии:

```typescript
type AgentResult = {
  content: string;
  tokensUsed: number;
  toolCalls: number;
};

async function singleAgentApproach(task: string): Promise<AgentResult> {
  const systemPrompt = `You are a full-stack developer. You must:
1. Research the requirements
2. Write the code
3. Review the code for bugs
4. Write tests
Do ALL of these in a single conversation.`;

  const contextWindow: string[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const research = await fakeLLMCall(systemPrompt, `Research: ${task}`);
  contextWindow.push(research.output);
  totalTokens += research.tokens;
  totalToolCalls += research.calls;

  const code = await fakeLLMCall(
    systemPrompt,
    `Given this research:\n${contextWindow.join("\n")}\n\nNow write code for: ${task}`
  );
  contextWindow.push(code.output);
  totalTokens += code.tokens;
  totalToolCalls += code.calls;

  const review = await fakeLLMCall(
    systemPrompt,
    `Given all previous context:\n${contextWindow.join("\n")}\n\nReview the code.`
  );
  contextWindow.push(review.output);
  totalTokens += review.tokens;
  totalToolCalls += review.calls;

  return {
    content: contextWindow.join("\n---\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}
```

Проблемы такого подхода:
- Окно контекста растёт на каждом этапе. К моменту проверки оно содержит заметки исследования И код И предыдущие рассуждения.
- Системный промпт общий. Его нельзя настроить под каждый этап.
- Ничего не выполняется параллельно.

### Шаг 2: Специализированные агенты

Теперь разделите его. Каждый агент получает одну задачу:

```typescript
type SpecialistAgent = {
  name: string;
  systemPrompt: string;
  run: (input: string) => Promise<AgentResult>;
};

function createSpecialist(name: string, systemPrompt: string): SpecialistAgent {
  return {
    name,
    systemPrompt,
    run: async (input: string) => {
      const result = await fakeLLMCall(systemPrompt, input);
      return {
        content: result.output,
        tokensUsed: result.tokens,
        toolCalls: result.calls,
      };
    },
  };
}

const researcher = createSpecialist(
  "researcher",
  "You are a technical researcher. Read documentation, find patterns, and summarize findings. Output only the facts needed for implementation."
);

const coder = createSpecialist(
  "coder",
  "You are a senior TypeScript developer. Given requirements and research notes, write clean, tested code. Nothing else."
);

const reviewer = createSpecialist(
  "reviewer",
  "You are a code reviewer. Find bugs, security issues, and logic errors. Be specific. Cite line numbers."
);
```

У каждого специалиста сфокусированный промпт. Каждый получает чистое окно контекста только с нужным ему вводом.

### Шаг 3: Координация через сообщения

Соедините специалистов через явную передачу сообщений:

```typescript
type AgentMessage = {
  from: string;
  to: string;
  content: string;
  timestamp: number;
};

async function multiAgentApproach(task: string): Promise<AgentResult> {
  const messages: AgentMessage[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const researchResult = await researcher.run(task);
  messages.push({
    from: "researcher",
    to: "coder",
    content: researchResult.content,
    timestamp: Date.now(),
  });
  totalTokens += researchResult.tokensUsed;
  totalToolCalls += researchResult.toolCalls;

  const coderInput = messages
    .filter((m) => m.to === "coder")
    .map((m) => `[From ${m.from}]: ${m.content}`)
    .join("\n");

  const codeResult = await coder.run(coderInput);
  messages.push({
    from: "coder",
    to: "reviewer",
    content: codeResult.content,
    timestamp: Date.now(),
  });
  totalTokens += codeResult.tokensUsed;
  totalToolCalls += codeResult.toolCalls;

  const reviewerInput = messages
    .filter((m) => m.to === "reviewer")
    .map((m) => `[From ${m.from}]: ${m.content}`)
    .join("\n");

  const reviewResult = await reviewer.run(reviewerInput);
  messages.push({
    from: "reviewer",
    to: "orchestrator",
    content: reviewResult.content,
    timestamp: Date.now(),
  });
  totalTokens += reviewResult.tokensUsed;
  totalToolCalls += reviewResult.toolCalls;

  return {
    content: messages.map((m) => `[${m.from} -> ${m.to}]: ${m.content}`).join("\n\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}
```

Каждый агент получает только адресованные ему сообщения. Никакого загрязнения контекста. 50 тыс. токенов чтения документации исследователем никогда не попадают в контекст ревьюера.

### Шаг 4: Сравнение

```typescript
async function compare() {
  const task = "Build a rate limiter middleware for an Express.js API";

  console.log("=== Single Agent ===");
  const single = await singleAgentApproach(task);
  console.log(`Tokens: ${single.tokensUsed}`);
  console.log(`Tool calls: ${single.toolCalls}`);

  console.log("\n=== Multi-Agent ===");
  const multi = await multiAgentApproach(task);
  console.log(`Tokens: ${multi.tokensUsed}`);
  console.log(`Tool calls: ${multi.toolCalls}`);
}
```

Мультиагентная версия использует больше токенов в сумме (три агента, три отдельных вызова LLM), но контекст каждого агента остаётся чистым. Качество каждого этапа улучшается, потому что системный промпт специализирован.

Этот урок производит переиспользуемый промпт для принятия решения, когда переходить к мультиагентности. См. `outputs/prompt-multi-agent-decision.md`.

## Упражнения

1. Добавьте четвёртого специалиста: агента-«тестировщика», который получает код от программиста и отзыв от ревьюера, а затем пишет тесты
2. Измените конвейер так, чтобы ревьюер мог отправлять обратную связь программисту для цикла доработки (максимум 2 раунда)
3. Преобразуйте последовательный конвейер в разветвление: запустите исследователя и агента-«анализатора требований» параллельно, затем объедините их результаты перед передачей программисту

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|----------------------|
| Swarm (рой) | «Улей из ИИ-агентов» | Набор равноправных агентов с общим состоянием и без фиксированного лидера. Поведение возникает из локальных взаимодействий. |
| Orchestrator (оркестратор) | «Агент-босс» | Агент, чьи инструменты включают порождение и управление другими агентами. Он планирует и делегирует, но может не выполнять саму работу. |
| Coordinator (координатор) | «Регулировщик движения» | Неагентный компонент (часто просто код, а не LLM), который маршрутизирует сообщения между агентами по правилам. |
| Consensus (консенсус) | «Агенты договариваются» | Протокол, по которому несколько агентов должны достичь согласия перед тем, как продолжить. Используется при необходимости разрешения конфликтующих выводов. |
| Emergent behavior (эмерджентное поведение) | «Агенты сами разобрались» | Системные паттерны, возникающие из взаимодействий агентов, но не заданные явно. Может быть полезным или вредным. |
| Fan-out / fan-in (разветвление / слияние) | «Map-reduce для агентов» | Разделение задачи между параллельными агентами (fan-out), затем объединение их результатов (fan-in). |
| Message passing (передача сообщений) | «Агенты общаются друг с другом» | Механизм коммуникации между агентами: структурированные данные, отправляемые от одного агента к другому, заменяющие общие окна контекста. |
