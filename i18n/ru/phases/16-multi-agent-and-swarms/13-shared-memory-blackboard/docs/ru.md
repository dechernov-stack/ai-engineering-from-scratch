# Общая память и паттерны Blackboard

> В мультиагентных системах 2026 года сосуществуют два подхода: **пул сообщений** (все видят сообщения всех, как в AutoGen GroupChat или MetaGPT) и **blackboard с подпиской** (агенты подписываются на релевантные события, как в Context-Aware MCP или фреймворке Matrix). Обе структуры — единственная состояние-содержащая часть мультиагентной системы, а значит, именно там и обитают самые интересные баги. Эталонный сценарий сбоя — **отравление памяти** (memory poisoning): один агент галлюцинирует «факт», другие агенты принимают его за проверенный, и точность постепенно деградирует — причём отладить это гораздо сложнее, чем мгновенный сбой. В этом уроке обе структуры строятся на stdlib, в них внедряется атака отравления, и показываются три митигации, которые действительно работают в продакшене.

**Type:** Изучение + практика
**Languages:** Python (stdlib, `threading`)
**Prerequisites:** Phase 16 · 04 (Primitive Model), Phase 16 · 09 (Parallel Swarm Networks)
**Time:** ~75 минут

## Проблема

Мультиагентным системам нужно место для хранения общих фактов. Буквальный вариант — «передавать всё в сообщениях», но это заново изобретает общее состояние с лишним копированием. Другой вариант — «дать всем глобальный лог», но глобальные логи растут безгранично и легко отравляются. Третий — «проецировать представление для каждого агента» — масштабируемо, но требует тяжёлой схемы.

Когда один из агентов галлюцинирует и записывает галлюцинацию в общее состояние, каждый нижестоящий агент, читающий это состояние, принимает галлюцинацию за факт. К моменту, когда человек это заметит, цепочка рассуждений уже пять шагов в глубину, а первопричина — третье когда-либо записанное сообщение. Отладка деградации точности мультиагентной системы сложнее отладки сбоя.

Это и есть отравление памяти. Это второе по частоте документирования семейство сбоев в таксономии MAST (Cemri et al., arXiv:2503.13657), и оно структурно: любая конструкция общей памяти без происхождения данных (provenance) и неперезаписываемого верификатора рано или поздно проявит этот сбой.

## Концепция

### Две основные топологии

**Полный пул сообщений.** Каждый агент читает каждое сообщение. Так устроены AutoGen GroupChat и MetaGPT. Просто, прозрачно, легко инспектировать, но плохо масштабируется свыше ~10 агентов, потому что контекст каждого агента заполняется работой остальных.

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**Blackboard с подпиской.** Агенты заявляют интерес к темам (topics); субстрат маршрутизирует только релевантные сообщения. Так устроены CA-MCP (arXiv:2601.11595) и децентрализованный фреймворк Matrix (arXiv:2511.21686). Масштабируется дальше, но требует заранее спроектированной схемы, чтобы подписки имели смысл.

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### Когда что выигрывает

- **Полный пул** выигрывает, когда агентов мало (< 10), они разнородны, а разговор короткий. Рассуждать о том, кто что сказал, тривиально, когда все видят всё.
- **Blackboard** выигрывает, когда агентов много, они однородны по роли, но многочисленны по экземплярам (рои), а разговор длительный. Маршрутизация экономит токены и снижает загрязнение контекста.

Продакшен-системы часто смешивают подходы: небольшой полный пул наверху (слой планирования), blackboard-ы ниже (слой воркеров).

### Отравление памяти в одном сценарии

Три агента работают над исследовательской задачей. Агент A — агент извлечения данных. Агент B — суммаризатор. Агент C — аналитик.

1. A получает страницу и записывает сообщение в общее состояние: «Исследование сообщает об улучшении точности на 42%».
2. На самом деле на странице было написано «улучшение на 4,2%». A галлюцинировал десятичную точку.
3. B, читая общее состояние, пишет: «Сообщается о значительном приросте точности на 42% (источник: A)».
4. C, читая общее состояние, пишет: «Рекомендуем внедрение — прирост на 42% трансформирует результаты».
5. Итоговый отчёт ссылается на цифру 42%, которая никогда не существовала.

Ни один агент не упал. Ни один тест не провалился. Система «сработала». Галлюцинация перешла из контекста одного агента в рассуждения всех нижестоящих агентов через общее состояние.

### Почему это структурная проблема

Без общего состояния галлюцинация агента A остаётся в контексте A. Нижестоящие агенты заново получили бы данные или вывели их сами и могли бы поймать ошибку. При наивном общем состоянии контекст A становится контекстом всех, и галлюцинация легитимизируется как факт.

Проблема не в общем состоянии как таковом — проблема в общем состоянии **без происхождения данных и без независимого верификатора**. Три митигации решают эту проблему:

1. **Атрибутировать происхождение каждой записи.** Каждая запись в общем состоянии фиксирует, кто её написал, когда, по какому промпту и (если применимо) на какой источник сослался агент. Нижестоящие агенты читают со скепсисом, привязанным к происхождению.
2. **Версионировать записи; обращаться с ними как с append-only.** Исправление — это новая запись, которая заменяет старую, а не обновление на месте. Так сохраняется аудиторский след.
3. **Держать хотя бы одного агента, который не может писать в общее состояние.** Агент-верификатор, доступный только для чтения, выборочно проверяет записи, заново получает источники и отмечает несоответствия. Поскольку он не может писать в пул, пул не может его отравить.

### Прецедент blackboard (Hayes-Roth, 1985)

Паттерн blackboard появился на четыре десятилетия раньше LLM-агентов. Hayes-Roth (1985, «A Blackboard Architecture for Control») описал специализированные Knowledge Sources, которые наблюдают за глобальной доской, вносят частичные решения и запускают другие источники. Blackboard 2026 года (CA-MCP, Matrix) — тот же паттерн, только с LLM-агентами в роли Knowledge Sources и JSON-блобами в роли частичных решений. Старая литература задокументировала решения проблем конкуренции записи, оппортунистического управления и согласованности, которые современные системы заново открывают.

### Проекция против полного представления

Чистый blackboard даёт каждому подписчику одну и ту же проекцию (в рамках темы). Более агрессивная конструкция — **проекция для каждого агента**: каждый агент получает представление, настроенное под его роль. Редукторы состояния LangGraph — каноническая реализация 2026 года: функция-редуктор сворачивает глобальное состояние в срез, специфичный для роли.

Проекция для каждого агента масштабируется дальше, но требует схемы. Без неё ad-hoc проекция будет заново строиться в промпте каждого агента.

### Паттерны конкуренции записи

Одновременная запись нескольких агентов — это проблема конкурентности, а не только LLM. Работают три паттерна:

- **Последовательный писатель (единый производитель).** Все записи идут через одного агента-координатора, который сериализует их. Просто, но узкое место.
- **Оптимистичная конкурентность с версионированием.** У каждой записи есть версия; писатели получают отказ при несовпадении версии и повторяют попытку. Классическая техника баз данных.
- **Партиционирование по темам.** Разные агенты владеют разными темами. Нет конкуренции между темами. Требует спроектированных границ партиций.

Большинство фреймворков 2026 года по умолчанию используют последовательного писателя, потому что вызовы LLM достаточно медленные, чтобы конкуренция была редкой, а узкое место не вредило.

### Неперезаписываемый верификатор

Самая несущая митигация — верификатор только для чтения. Правила реализации:

- Верификатор имеет общий доступ к состоянию команды (читает blackboard или пул).
- У верификатора нет handle для записи в общее состояние — только в отдельный канал верификации.
- Верификатор независимо получает источники, на которые ссылаются записи. Отмечает расхождения.
- Собственные выводы верификатора маршрутизируются человеку или отдельному агенту принятия решений, но никогда не возвращаются обратно в пул.

Без такого разделения выводы верификатора становятся новыми записями в пуле, а значит отравленный пул отравляет верификатора, что отравляет его же верификации.

```figure
swarm-blackboard
```

## Построение

`code/main.py` реализует обе топологии на stdlib Python, а также игрушечную атаку отравления и три митигации.

- `MessagePool` — потокобезопасный append-only лог с полным считыванием.
- `Blackboard` — pub/sub по ключу-теме с подписками для каждого агента.
- `ProvenanceEntry` — каждая запись фиксирует (writer, timestamp, prompt_hash, source_uri).
- `PoisoningScenario` — запускает задачу исследования с тремя агентами, где агент A галлюцинирует десятичную точку. Печатает итоговый отчёт.
- `Verifier` — агент только для чтения, который заново получает источники и отмечает несоответствия. Запускает тот же сценарий с присутствующим верификатором.

Запустить:

```
python3 code/main.py
```

Ожидаемый вывод:
- Прогон 1 (без верификатора): галлюцинированные 42% распространяются в итоговый отчёт.
- Прогон 2 (с верификатором): верификатор отмечает несоответствие, пул помечается «flagged», итоговый отчёт содержит опровержение.

## Итог

Для любой конструкции общей памяти:

- Фиксируйте происхождение каждой записи: `(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`.
- Делайте лог append-only. Исправления — это новые записи, ссылающиеся на заменённую.
- Разворачивайте хотя бы одного агента-верификатора только для чтения с независимым доступом к источникам.
- Маршрутизируйте вывод верификатора в отдельный канал, а не обратно в общий пул.
- Логируйте долю записей, являющихся заменами — рост этой доли — раннее свидетельство паттернов галлюцинаций.

## Ключевые термины

| Термин | Как говорят люди | Что на самом деле означает |
|------|----------------|------------------------|
| Message pool | «Общая история чата» | Append-only лог, который читают все агенты. Полная прозрачность, плохое масштабирование. |
| Blackboard | «Общее рабочее пространство» | Pub/sub по ключу-теме. Агенты подписываются на релевантные темы. Масштабируется дальше. |
| Provenance | «Кто что написал» | Метаданные для каждой записи: автор, время, промпт, источники. |
| Memory poisoning | «Распространение галлюцинаций» | Ошибка одного агента попадает в общее состояние, нижестоящие агенты принимают её за факт. |
| Append-only | «Без обновлений на месте» | Исправления — это новые записи, которые заменяют старые. Сохраняется аудиторский след. |
| Unwritable verifier | «Независимый аудитор» | Агент только для чтения, который заново получает источники и отмечает несоответствия. |
| Projection | «Ограниченное представление» | Представление для каждого агента, вычисляемое из глобального состояния. Редукторы LangGraph — канонический случай. |
| Knowledge Source | «Специализированный агент» | Термин Hayes-Roth 1985 года для участника blackboard. |
