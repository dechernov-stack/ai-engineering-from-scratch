# Специализация ролей — Планировщик, Критик, Исполнитель, Верификатор

> Самая распространённая декомпозиция мультиагентных систем 2026 года: один агент планирует, один исполняет, один критикует или проверяет. MetaGPT (arXiv:2308.00352) формализует это как SOP (стандартные операционные процедуры), закодированные в ролевые промпты — Product Manager, Architect, Project Manager, Engineer, QA Engineer — следуя `Code = SOP(Team)`. ChatDev (arXiv:2307.07924) связывает в цепочку designer, programmer, reviewer, tester через "chat chain" с "коммуникативной дегаллюцинацией" (агенты явно запрашивают недостающие детали). Верификатор — несущий элемент: Cemri et al. (MAST, arXiv:2503.13657) показывают, что каждый сбой мультиагентной системы можно свести к отсутствующей или неисправной верификации. PwC сообщила о 7-кратном приросте точности (10% → 70%) благодаря структурированным циклам валидации в CrewAI.

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 16 · 04 (Primitive Model), Phase 16 · 05 (Supervisor)
**Time:** ~60 минут

## Проблема

Универсальные мультиагентные системы выдают универсальный результат. Три кодера в групповом чате пишут три разновидности одного и того же посредственного кода. Можно добавлять агентов, добавлять раунды — и всё равно не преодолеть порог качества.

Решение — не больше агентов, а *разные* агенты. Назначьте отдельные роли. Дайте критику инструменты, которых нет у планировщика. Дайте верификатору объективный набор тестов. Теперь в системе есть внутреннее несогласие с обоснованной коррекцией, а не просто параллельное угадывание.

## Концепция

### Четыре канонические роли

**Планировщик (Planner).** Читает цель, производит список шагов или спецификацию. Инструменты: поиск по знаниям, документация. Результат: структурированный план.

**Исполнитель (Executor).** Читает по одному шагу плана за раз, производит артефакт. Инструменты: реальные рабочие инструменты (компилятор кода, оболочка, API-клиент). Результат: артефакт.

**Критик (Critic).** Сравнивает результат исполнителя с замыслом планировщика. Инструменты: доступ к артефакту только для чтения, статический анализ. Результат: принять/отклонить с обоснованием.

**Верификатор (Verifier).** Читает артефакт и запускает детерминированную проверку. Инструменты: тест-раннер, проверка типов, валидатор схем. Результат: пройдено/не пройдено с доказательствами.

Критик субъективен, имеет мнение, часто основан на LLM. Верификатор объективен, детерминирован, часто основан на коде. Это не одна и та же роль.

### Паттерн SOP в MetaGPT

MetaGPT (arXiv:2308.00352) кодирует SOP разработки ПО как ролевые промпты:

- **Product Manager** пишет PRD.
- **Architect** создаёт системный дизайн.
- **Project Manager** делит задачи.
- **Engineer** реализует.
- **QA Engineer** запускает тесты.

У каждой роли строгая схема входа/выхода. Ролевой промпт описывает, чем роль *является* и что она *обязана произвести*. Формулировка `Code = SOP(Team)` — детерминированные SOP превращают команду LLM в предсказуемый конвейер.

### Коммуникативная дегаллюцинация ChatDev

ChatDev добавляет ключевой приём: когда исполнителю нужна конкретная деталь, отсутствующая в плане, он явно запрашивает её у дизайнера, прежде чем продолжить. Это предотвращает классический сбой LLM — правдоподобное выдумывание детали.

Реализация: ролевой промпт включает фразу "когда вам нужна конкретная информация, которую вам не предоставили, спросите соответствующую роль по имени, прежде чем выдавать результат."

### Почему верификатор важнее всего

Cemri et al. (MAST) проследили 1642 сбоя исполнения мультиагентных систем. 21,3% составили пробелы верификации — система выдала ответ, который никто не проверил. Остальные 79% часто сводятся к тому, что "проверка, которая должна была сработать, либо не прошла молча, либо вообще не запускалась". Верификация — это несущая роль.

PwC сообщила (на развёртываниях CrewAI, 2025), что добавление структурированного цикла валидации подняло точность с 10% до 70%. 7-кратный прирост от одной роли.

### Критик против верификатора

- Критик — это LLM, рецензирующий артефакт на качество. Субъективен. Его можно обмануть правдоподобным текстом.
- Верификатор — это детерминированная программа, выполняющаяся над артефактом. Объективен. Даёт результат пройдено/не пройдено с доказательствами.

Используйте оба. Критик улавливает вопросы вкуса, которые верификатор не может сформулировать. Верификатор ловит ошибки, которые критик не видит, поскольку они проявляются только во время выполнения.

### Антипаттерн

Каждая роль в вашей системе — LLM, и ответ каждой роли — "выглядит нормально для меня". Классический режим сбоя MAST. Добавьте хотя бы одного верификатора, чья оценка пройдено/не пройдено определяется кодом, а не LLM.

### Соответствия фреймворкам

- **CrewAI** — `Agent(role, goal, backstory)` это хрестоматийная поверхность для специализации.
- **LangGraph** — узлы могут иметь специализированные промпты; рёбра обеспечивают соблюдение конвейера.
- **AutoGen** — специфичные для роли ConversableAgents с однословными именами в GroupChat.
- **OpenAI Agents SDK** — инструменты передачи (handoff) между специализированными по роли агентами.

## Постройте это

`code/main.py` реализует конвейер из 4 ролей, строящий простую функцию Python:

- **Планировщик** производит спецификацию.
- **Исполнитель** генерирует строку кода.
- **Критик** (симулированный LLM) отмечает очевидные проблемы.
- **Верификатор** запускает сгенерированный код в песочнице (`exec`) против тестового случая.

Демо запускается дважды: один раз, когда исполнитель производит корректный код (и критик, и верификатор проходят), и один раз, когда исполнитель производит код, не соответствующий спецификации (критик пропускает баг, поскольку он выглядит правдоподобно, верификатор же ловит его, поскольку тест не проходит).

Запуск:

```
python3 code/main.py
```

## Используйте это

`outputs/skill-role-designer.md` принимает задачу и производит роспись ролей (3-5 ролей), схему входа/выхода для каждой роли и проверку верификатора. Используйте это перед подключением агентов во фреймворк.

## Внедрите это

Чек-лист:

- **Хотя бы один детерминированный верификатор.** Никогда не делайте всё на LLM.
- **Явная схема входа/выхода для каждой роли.** Планировщик возвращает спецификацию, а не прозу; исполнитель читает эту схему.
- **Коммуникативная дегаллюцинация.** Исполнитель обязан спрашивать планировщика, если информации не хватает; никогда не выдумывать её.
- **Порядок критик/верификатор.** Сначала запускайте критика (дёшево, улавливает проблемы дизайна), затем верификатора (медленно, ловит баги).
- **Бюджет циклов.** Максимум 2 раунда пересмотра критик-исполнитель, прежде чем эскалировать к человеку.

## Упражнения

1. Запустите `code/main.py` и понаблюдайте, как верификатор ловит баг, который пропустил критик. Добавьте проверку статического анализа (подсчёт вхождений `return`) как дополнительного верификатора. Что она улавливает такого, что упускает тест времени выполнения?
2. Добавьте 5-ю роль: "аналитик требований", которая переводит пожелание пользователя в спецификацию, готовую для планировщика. Какие запросы коммуникативной дегаллюцинации должны подниматься к ней?
3. Прочитайте раздел 3 ("Agents") MetaGPT. Перечислите схему входа/выхода каждой из 5 ролей MetaGPT.
4. Изучите диаграмму chat-chain ChatDev (arXiv:2307.07924, Рисунок 3). Определите, где коммуникативная дегаллюцинация разрывает цикл, который иначе был бы бесконечным.
5. 7-кратный прирост точности PwC получен благодаря циклам верификации. Выдвиньте гипотезу о трёх задачах, где добавление верификатора не поможет — где детерминированная проверка корректности невозможна или чрезмерно дорога.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Специализация ролей | "Разные агенты, разные задачи" | Отдельные системные промпты, настроенные под роли планировщика/исполнителя/критика/верификатора. |
| Паттерн SOP | "Закодированная стандартная операционная процедура" | Подход MetaGPT: строгие схемы входа/выхода для каждой роли превращают команду в конвейер. |
| Коммуникативная дегаллюцинация | "Спроси, прежде чем выдумывать" | Паттерн ChatDev: исполнитель спрашивает планировщика, когда деталь отсутствует, вместо того чтобы её придумать. |
| Критик | "Рецензент-LLM" | Субъективный, предвзятый рецензент. Улавливает вопросы вкуса. Может быть обманут правдоподобной прозой. |
| Верификатор | "Детерминированная проверка" | Проверка пройдено/не пройдено на основе кода. Тест-раннер, проверка типов, валидатор схем. Не может быть обманут. |
| Пробел верификации | "Никто не проверил" | 21,3% сбоев MAST. Ответ выдан без проверки, которая поймала бы баг. |
| Цикл пересмотра | "Критик отправляет обратно" | Отклонение критиком запускает повторный запуск исполнителя с обратной связью. Требует бюджета. |
| Антипаттерн "всё на LLM" | "Выглядит нормально для меня" | Каждая роль — LLM, нет детерминированной проверки. Классический сбой MAST. |
