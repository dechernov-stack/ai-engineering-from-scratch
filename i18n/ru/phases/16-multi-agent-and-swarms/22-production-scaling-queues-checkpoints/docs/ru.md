# Масштабирование в production — очереди, чекпойнты, устойчивость

> Масштабирование многоагентных систем до тысяч одновременных запусков требует **устойчивого выполнения (durable execution)** — очередей работы плюс чекпойнтов, чтобы любой воркер мог возобновить любой запуск после любого сбоя, при условии что реализованы обработка лизов (lease), идемпотентные побочные эффекты и детерминированный повтор (replay). Эталонный пример — runtime LangGraph: он записывает чекпойнт после каждого супершага с ключом `thread_id` (по умолчанию Postgres); при сбое воркера лиз освобождается, и другой воркер продолжает работу. Агенты могут бесконечно «спать», ожидая ввода от человека. **MegaAgent** (arXiv:2408.09955) использовал очередь производитель-потребитель на каждого агента с тремя состояниями (Idle / Processing / Response) и двухуровневой координацией (внутригрупповой чат + межгрупповой административный чат). **Fiber/async** превосходит подход «поток на задачу» для LLM-стриминга: потоки простаивают 99% времени в ожидании токенов, а файберы кооперативно уступают управление при I/O. Контраргумент — в статье Ashpreet Bedi «Scaling Agentic Software» утверждается, что нужны **FastAPI + Postgres и ничего больше**, пока нагрузка не докажет обратное — простые архитектуры тянут дальше, чем кажется. В этом уроке строится устойчивый лог чекпойнтов, очередь работы для каждого агента с переходами состояний, демонстрация async-vs-thread, и закрепляется прагматичное правило «начинай просто».

**Languages:** Python (stdlib, `asyncio`, `sqlite3`)

## Проблема

Прототип многоагентной системы работает на одном ноутбуке с тремя агентами в цикле событий в памяти. Вы переходите в production:

- Агенты иногда работают часами (долгие исследования, ожидания участия человека).
- Рабочие процессы иногда падают. Перезапуск теряет состояние.
- Пиковая нагрузка в 10 раз выше средней; нужно горизонтальное масштабирование.
- Пользователи платят за каждый запуск агента; нужна семантика ровно-одного-раза (exactly-once) для списания средств.

Цикл событий в памяти не решает ни одной из этих задач. Нужен слой устойчивого выполнения под ним. Канонические варианты 2026 года:

1. Движок workflow с чекпойнтами (Temporal, runtime LangGraph).
2. Очередь сообщений с хранилищем состояния (Postgres + SQS/RabbitMQ).
3. Фреймворки на основе модели акторов (producer-consumer на агента в MegaAgent).
4. Самописный FastAPI + Postgres (аргумент Беди).

В этом уроке строится миниатюра каждого из них.

## Концепция

### Устойчивое выполнение: паттерн

Движок устойчивого выполнения сохраняет полное состояние программы после каждого «шага» (супершага, в терминологии LangGraph). При сбое:

```
worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects
```

Требования для работы этого механизма:

- **Сериализуемое состояние.** Всё состояние агента должно быть сохраняемым. Замыкания функций с живыми соединениями к базе данных не переживают сериализацию.
- **Детерминированное возобновление.** При одинаковом состоянии и одинаковых входных данных агент производит одинаковые действия (или делегирует вызовы LLM внешнему детерминированному оракулу).
- **Идемпотентные побочные эффекты.** Внешние вызовы (вызовы инструментов, платежи) должны быть идемпотентными или использовать ключ дедупликации.

LangGraph пишет чекпойнт после каждого супершага; Temporal — после каждой активности; Restate использует журналы на основе event sourcing. Все три реализуют один и тот же паттерн.

### Runtime с чекпойнтом на каждом шаге

Runtime LangGraph — рабочий пример: у каждого агента есть `thread_id`; состояние — типизированный словарь; каждый супершаг записывает строку в таблицу чекпойнтов. При возобновлении runtime проигрывает заново с последнего чекпойнта, а не с нуля. Агенты могут `interrupt()`, ожидая ввода от человека; runtime сохраняет состояние и освобождает воркер. Когда ввод поступает, любой воркер может возобновить работу.

Это эталонный production-дизайн по состоянию на апрель 2026 года.

### Очередь на агента в MegaAgent

arXiv:2408.09955 описывает эксперимент на масштаб: тысячи одновременных агентов в одном кластере. Архитектура:

```
agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)
```

Двухуровневая координация позволяет внутригрупповому общению происходить плотно, в то время как межгрупповое остаётся разреженным — этот паттерн используется для сохранения линейной стоимости при тысячах агентов.

### Async против потока на задачу

Вызовы LLM ограничены вводом-выводом. Поток, ожидающий следующий токен, простаивает 99% времени. Каждый поток стоит ~1 МБ оперативной памяти; при 10 000 одновременных вызовов это 10 ГБ только на стеки.

Файберы (Python `asyncio`, горутины Go, `tokio` в Rust) кооперативно уступают управление при I/O. Те же 10 000 вызовов свободно помещаются в один процесс. На масштабе LLM-агентов async — это не оптимизация, а архитектура.

Исключение: CPU-связанная постобработка (эмбеддинги, трюки токенизатора) всё ещё требует потоков или процессов. Разделяйте слой I/O и слой CPU.

### Контраргумент Беди

«Scaling Agentic Software» (Ashpreet Bedi, 2026) утверждает, что большинство команд чрезмерно усложняют архитектуру до того, как измерили нагрузку. Прагматичный вариант по умолчанию:

- FastAPI + Postgres.
- Каждый запуск агента — строка; состояние обновляется на месте с оптимистичной конкурентностью.
- Фоновые задачи через `pg_notify` или простой воркер Celery.
- Политика повторных попыток в коде приложения.

При нагрузке до ~100 одновременных запусков агентов на управляемых задачах этого часто достаточно. Переходите на более сложное решение, когда измерили, что текущее не справляется.

Правило: принимайте фреймворки устойчивого выполнения, когда сталкиваетесь с конкретной проблемой, которую простые архитектуры решить не могут. Преждевременное внедрение тратит время на церемонии, которые не окупаются.

### Семантика «ровно один раз»

Для платных запусков агентов нужна «эффективная семантика ровно-одного-раза» (доставка минимум-один-раз + идемпотентный потребитель). Инженерные приёмы:

- **Ключ дедупликации на запуск.** Включайте его в каждый вызов побочного эффекта.
- **Паттерн outbox.** Побочные эффекты сначала записываются в таблицу, затем отдельный процесс их выполняет. Оба шага идемпотентны.
- **Компенсирующие транзакции.** Если побочный эффект успешен, но запись об отслеживании не удалась, планируется компенсация.

Это паттерны инженерии баз данных, а не специфика LLM. «Налог» LLM лишь в том, что вызовы LLM медленные; всё остальное — стандартные распределённые системы.

### Rainbow-деплой

Исследовательская многоагентная система Anthropic использует «rainbow-деплои»: несколько версий runtime агента работают одновременно, чтобы долгоживущих агентов не приходилось убивать при каждом деплое кода. Новые версии канарейкой выводятся на часть трафика; старые версии выводятся из эксплуатации, когда их агенты завершают работу.

Это стандартная практика для долгоживущих stateful-систем; адаптация 2026 года в том, что агенты могут жить часами, поэтому циклы деплоя должны это учитывать.

### Канонический production-чеклист

- Устойчивое состояние (чекпойнты, снапшоты или outbox + воспроизводимый лог).
- Идемпотентные побочные эффекты.
- Асинхронный слой I/O для вызовов LLM.
- Доставка минимум-один-раз с дедупликацией.
- Rainbow/canary-деплой для stateful-нагрузок.
- Наблюдаемость: трассировки на агента, аудит супершагов, счётчик повторов.

## Создайте это

`code/main.py` реализует:

- `CheckpointStore` — лог чекпойнтов на базе SQLite с ключами thread-id. Каждый супершаг добавляет строку.
- `run_with_checkpoint(agent, thread_id)` — симулирует сбой посреди выполнения; второй воркер возобновляет работу с последнего чекпойнта.
- `AgentQueue` — конечный автомат состояний Idle / Processing / Response для каждого агента с небольшой очередью работы.
- `demo_async_vs_threads()` — запускает 500 одновременных симулированных «вызовов LLM» через asyncio и через потоки; выводит время выполнения и пиковое потребление памяти (приближённо).

Запуск:

```
python3 code/main.py
```

Ожидаемый результат: возобновление с чекпойнта успешно после симулированного сбоя; версия на async обрабатывает 500 одновременных вызовов менее чем за 1 с; версия на потоках занимает несколько секунд и использует на порядки больше памяти на единицу конкурентности.

## Внедрите в production

Канонические меры усиления production:

- **Начинайте просто (правило Беди).** FastAPI + Postgres, пока не измерили, что это не справляется.
- **Инструментируйте всё перед оптимизацией.** Гистограмма задержки на запуск, время на шаг, счётчик повторов, категоризация сбоев.
- **Паттерн outbox для побочных эффектов.** Особенно для платежей и внешних API-вызовов.
- **Rainbow-деплои.** Никогда не убивайте выполняющиеся запуски агентов во время деплоя.
- **Внедряйте движки устойчивого выполнения (Temporal / LangGraph / Restate), когда** сталкиваетесь с конкретными проблемами: часовые ожидания участия человека, межрегиональная координация, сложные политики повтора/компенсации.
- **Async для слоя I/O.** Потоки только для CPU-связанной постобработки.

## Упражнения

1. Запустите `code/main.py`. Убедитесь, что возобновление с чекпойнта работает; измерьте разницу в конкурентности async против потоков.
2. Реализуйте таблицу **outbox**: каждый вызов инструмента сначала пишется в outbox, затем отдельная горутина/задача его выполняет. Проверьте идемпотентность, выполнив вызов инструмента дважды.
3. Смоделируйте **rainbow-деплой**: две одновременные версии runtime; направьте половину новых thread_id на каждую; убедитесь, что выполняющиеся потоки на старой версии не прерываются.
4. Прочитайте документацию по runtime LangGraph (ссылка ниже). Определите, какие функции runtime займут больше всего времени на воспроизведение в самописной версии на FastAPI + Postgres. Это повод для внедрения или можно отложить?
5. Прочитайте раздел 3 статьи MegaAgent (arXiv:2408.09955). Двухуровневая координация (внутригрупповой + межгрупповой административный чат) описана явно. Набросайте, как вы бы отобразили это на очередь сообщений с двумя семействами очередей.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Durable execution (устойчивое выполнение) | «Сохраняй состояние программы» | Движок записывает состояние после каждого супершага; восстановление после сбоя детерминировано. |
| Супершаг | «Транзакционная граница» | Единица работы между чекпойнтами. Термин LangGraph. |
| thread_id | «Идентификатор запуска агента» | Ключ, связывающий чекпойнты и логику возобновления. |
| Идемпотентность | «Безопасно повторить» | Повторение побочного эффекта даёт тот же результат, что и одна попытка. |
| Паттерн outbox | «Разделение побочных эффектов» | Запись намерения в таблицу; отдельный исполнитель выполняет его и помечает как завершённое. |
| Доставка минимум-один-раз | «Возможны дубликаты» | Семантика очереди сообщений; ключ дедупликации делает потребителя эффективно-однократным. |
| Rainbow-деплой | «Перекрывающиеся версии» | Несколько версий runtime работают одновременно во время долгоживущих нагрузок. |
| Async-файбер | «Кооперативная уступка управления» | Конкурентность в пользовательском режиме; дёшева по сравнению с потоками для I/O-связанных нагрузок. |
| Чекпойнт | «Снапшот состояния» | Сериализованное состояние на границе супершага; ключ для возобновления. |
