# Паттерн Supervisor / Orchestrator-Worker

> Один ведущий агент планирует и делегирует; специализированные воркеры выполняют работу в параллельных контекстах и отчитываются обратно. Это паттерн, лежащий в основе исследовательской системы Anthropic (Claude Opus 4 как ведущий, Sonnet 4 как субагенты), показавший +90,2% прироста относительно одного агента Opus 4 на внутренних исследовательских бенчмарках. В инженерном посте Anthropic сообщается, что 80% дисперсии на BrowseComp объясняется только расходом токенов — мультиагентные системы выигрывают в основном за счёт того, что каждый субагент получает свежее окно контекста. В этом уроке паттерн supervisor строится из примитивов, а также разбираются инженерные уроки 2026 года из продакшн-развёртываний.

**Type:** Изучение + Разработка
**Languages:** Python (stdlib, `threading`)
**Prerequisites:** Фаза 16 · 04 (Примитивная модель)
**Time:** ~75 минут

## Проблема

Исследовательская задача — типичный пример, на котором одноагентные системы терпят неудачу. Вы спрашиваете: «что изменилось в мультиагентных системах между 2023 и 2026 годами?» Один агент последовательно читает пять статей, заполняет половину своего контекста их текстом, а затем должен рассуждать обо всех них сразу. К моменту, когда он доходит до пятой статьи, он забывает первую. Он не может распараллелить работу.

Паттерн supervisor решает эту проблему: один ведущий агент планирует поиск, делегирует каждый подвопрос воркеру и синтезирует результаты. Каждый воркер получает собственное окно в 200 тыс. токенов для узкого вопроса. Ведущий агент никогда не видит сырые статьи — только резюме воркеров.

Продакшн-система Research от Anthropic показывает +90,2% на внутренних исследовательских бенчмарках по сравнению с одним Opus 4. В том же посте отмечается, что 80% дисперсии на BrowseComp объясняется *только расходом токенов*. Свежий контекст на каждого субагента — основной механизм.

## Концепция

### Паттерн

```
                 ┌──────────────┐
                 │   Lead       │  plans, decomposes,
                 │  (Opus 4)    │  synthesizes
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ Worker1 │  │ Worker2 │  │ Worker3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         fresh       fresh        fresh
         context     context      context
```

Ведущий агент никогда не читает сырые материалы. Воркеры никогда не видят работу друг друга, пока ведущий не синтезирует результаты. Каждая стрелка — это передача узкого артефакта.

### Почему это работает

Три механизма:

1. **Свежий контекст на субагента.** Воркер, исследующий «наследие FIPA-ACL», не несёт с собой 40 тыс. токенов, потраченных ведущим на планирование. Он получает окно в 200 тыс. токенов для одного вопроса.
2. **Специализация через промпт.** Промпт ведущего агента — «декомпозировать и синтезировать», а не «исследовать». Промпт каждого воркера узкий: «найди, что изменилось в X». Сфокусированные промпты дают сфокусированные результаты.
3. **Параллелизм.** Воркеры работают одновременно. Фактическое время выполнения примерно равно `max(worker_times) + plan + synthesis`, а не `sum(worker_times)`.

### Инженерные уроки (Anthropic, 2025)

В посте Anthropic перечислен ряд продакшн-уроков, которые актуальны и в 2026 году:

- **Масштабируйте усилия по сложности запроса.** Простые запросы: один агент, 3-10 вызовов инструментов. Сложные запросы: 10+ агентов. Это должен оценивать ведущий агент, а не вызывающая сторона.
- **Сначала широко, потом узко.** Сначала декомпозируйте на широкие подвопросы, затем порождайте больше воркеров на подвопрос, если ответ требует глубины.
- **Rainbow-развёртывания.** Агенты долгоживущие и сохраняют состояние. Традиционный blue-green не работает. Anthropic использует rainbow: постепенный выкат новых версий при плавном отключении старых.
- **Расход токенов доминирует.** Мультиагентная система потребляет примерно в 15× больше токенов, чем одноагентная. Запускайте её, только когда ценность задачи оправдывает затраты.

### Переход к graph-native подходу

LangGraph изначально поставлялся с библиотекой `langgraph-supervisor` и высокоуровневым хелпером `create_supervisor`. В 2025 году LangChain сместил рекомендацию в сторону реализации паттерна supervisor напрямую через вызовы инструментов (tool-calling), потому что вызовы инструментов дают больше контроля над тем, *что видит supervisor* (инженерия контекста). Библиотека всё ещё работает; документация теперь рекомендует форму на основе tool-calling.

### Режимы отказа

- **Ведущий агент галлюцинирует план.** Если ведущий агент генерирует подвопросы, которые не декомпозируют реальный вопрос, воркеры проводят точное исследование не той цели.
- **Воркеры чрезмерно углубляются в исследование.** Без явных границ области воркеры отклоняются от назначенного подвопроса и загрязняют этап синтеза.
- **Конфликты синтеза.** Два воркера возвращают противоречащие друг другу факты. Ведущий агент должен либо переспросить (добавить раунд), либо явно отметить расхождение. Молчаливый выбор одной из сторон — худший сбой: пользователь никогда не узнает, что было расхождение.

### Когда supervisor — неверный выбор

- **Последовательные задачи.** Если шаг 2 буквально нуждается в результате шага 1, параллелизм ничего не даёт. Используйте конвейер (CrewAI Sequential, линейный граф LangGraph).
- **Простые запросы.** Одноагентная система справляется с ними быстрее и дешевле. Используйте проверку «масштабирования усилий» ведущего агента перед порождением воркеров.
- **Строгий детерминизм.** Supervisor использует делегирование, выбираемое LLM. Статические графы лучше, когда аудит/воспроизведение важнее адаптивности.

## Соберите это

`code/main.py` реализует supervisor с тремя параллельными воркерами, используя `threading`. Ведущий агент декомпозирует запрос на подвопросы, воркеры работают одновременно над каждым подвопросом, а ведущий агент синтезирует результаты. Реальных LLM нет — воркеры запрограммированы на имитацию получения и резюмирования данных.

Ключевая структура:

- `Lead.plan(query)` разбивает запрос на 3 подвопроса.
- `Worker.run(sub_q)` возвращает фейковое резюме (в продакшне это мог бы быть любой агент, использующий инструменты).
- `Lead.run(query)` запускает воркеров в потоках, дожидается их завершения и синтезирует результаты.

Запуск:

```
python3 code/main.py
```

Вывод показывает план, параллельные трассировки воркеров с временными метками старта/завершения и итоговый синтез. Вы можете увидеть выигрыш по фактическому времени: три воркера по 0,3 секунды выполняются за ~0,35 секунды, а не за 0,9.

## Примените это

`outputs/skill-supervisor-designer.md` принимает запрос пользователя и выдаёт дизайн паттерна supervisor: системный промпт ведущего агента, роли воркеров, правила декомпозиции на подвопросы и шаблон синтеза. Используйте это перед созданием новой исследовательской агентной системы.

## Внедрение

Чек-лист перед развёртыванием паттерна supervisor:

- **Подбор моделей.** Ведущий агент на модели уровня reasoning (класс Opus, класс `o3`). Воркеры на более быстрой и дешёвой модели (Sonnet, `o4-mini`).
- **Таймаут воркера.** Любой воркер, превышающий 2× медианное время выполнения, завершается принудительно; ведущий агент либо порождает заново с более узкой областью, либо продолжает без него.
- **Лимит токенов на воркера.** Жёсткий лимит (скажем, 10× ожидаемого объёма входных данных для синтеза) предотвращает перерасход бюджета неконтролируемым воркером.
- **Наблюдаемость.** Отслеживайте план ведущего агента, вызовы инструментов каждого воркера и синтез. Это основа для любой последующей отладки.
- **Rainbow-развёртывание.** Долгоживущим агентам с состоянием нужен постепенный переход между версиями, а не горячая замена.

## Упражнения

1. Запустите `code/main.py`, затем измените ведущего агента так, чтобы он порождал 5 воркеров вместо 3. Понаблюдайте за эффектом на фактическое время выполнения. При каком количестве воркеров накладные расходы на порождение превышают выигрыш от параллелизма в этой демонстрации?
2. Реализуйте таймаут воркера: завершайте любого воркера, работающего дольше 0,5 секунды, и пусть ведущий агент синтезирует оставшиеся результаты. Какая наблюдаемость нужна, чтобы узнать, что воркер был прерван?
3. Добавьте шаг обнаружения конфликтов в синтез ведущего агента: если два воркера возвращают противоречащие ответы, ведущий агент отмечает расхождение, вместо того чтобы выбрать один из них. Как обнаружить противоречие без вызова LLM?
4. Прочитайте инженерный пост Anthropic о системе Research. Перечислите три практики, которые этой игрушечной демонстрации нужно было бы перенять для работы в продакшне.
5. Сравните `create_supervisor` LangGraph (устаревший) с новой рекомендацией на основе tool-calling. Какой подход даёт лучший контроль над тем, что видит supervisor? Почему Anthropic явно передаёт в синтез только подответы, а не сырой контекст воркеров?

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Supervisor | «Ведущий агент» | Оркестратор-агент, который планирует, делегирует и синтезирует. Сам работу не выполняет. |
| Worker | «Субагент» | Сфокусированный агент, вызываемый supervisor с узкой областью задачи и собственным окном контекста. |
| Orchestrator-worker | «Паттерн supervisor» | То же самое, другое название. В литературе 2026 года используются оба термина. |
| Fresh context | «Чистое окно» | Контекст воркера начинается с его системного промпта и назначенного вопроса, а не с истории ведущего агента. |
| Rainbow deployment | «Постепенный выкат» | Долгоживущим агентам с состоянием нужна версионированная поэтапная замена, а не blue-green. |
| Token dominance | «Контекст — переменная» | По данным Anthropic, 80% дисперсии исследовательских бенчмарков объясняется общим расходом токенов, а не выбором модели. |
| Scale effort | «Соответствие числа агентов сложности» | Ведущий агент оценивает сложность запроса, порождая соответственно 1 или 10+ воркеров. |
| Synthesis conflict | «Воркеры расходятся во мнениях» | Два воркера возвращают противоречащие факты; ведущий агент должен обозначить расхождение, а не молча выбрать одну из сторон. |
