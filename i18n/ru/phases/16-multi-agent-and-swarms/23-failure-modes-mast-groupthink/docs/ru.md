# Режимы отказов — MAST, Groupthink, монокультура, каскадные ошибки

> Эталонная таксономия на 2026 год — **MAST** (Cemri et al., NeurIPS 2025, arXiv:2503.13657), выведенная из 1642 трасс исполнения из 7 современных мультиагентных систем с открытым исходным кодом, показывающих **41–86,7% частоты отказов**. Три корневые категории: **проблемы спецификации** (41,77%) — неоднозначность ролей, нечёткое определение задач; **сбои координации** (36,94%) — разрывы коммуникации, рассинхронизация состояния; **пробелы верификации** (21,30%) — отсутствие валидации, отсутствие проверок качества. Семейство **Groupthink** (arXiv:2508.05687) добавляет: коллапс монокультуры (одна базовая модель → коррелированные отказы), конформистское смещение (агенты усиливают ошибки друг друга), дефицитная теория сознания (theory of mind), динамика смешанных мотивов, каскадные отказы надёжности. Пример каскада: штормы повторных попыток, когда сбой платежа вызывает повторы заказов, которые вызывают повторы инвентаризации, которые перегружают сервис инвентаризации (10-кратная нагрузка за секунды — нужны предохранители). Отравление памяти: галлюцинация одного агента попадает в общую память, нижестоящие агенты принимают её за факт; точность постепенно деградирует, что затрудняет диагностику первопричины. **STRATUS** (NeurIPS 2025) сообщает о 1,5-кратном улучшении успешности смягчения за счёт специализированных агентов обнаружения / диагностики / валидации. Этот урок рассматривает режимы отказов как полноценные инженерные цели.

**Type:** Learn
**Languages:** Python (stdlib)
**Prerequisites:** Phase 16 · 13 (Shared Memory), Phase 16 · 14 (Consensus and BFT), Phase 16 · 15 (Voting and Debate Topology)

## Проблема

Мультиагентные системы отказывают в 41–86,7% случаев на реальных задачах (Cemri et al. 2025 измерили это на 7 MAS с открытым исходным кодом). Это не отлаживается «просто добавлением ещё агентов». У отказов есть структурные причины. Таксономия MAST даёт категории. Этот урок сопоставляет каждую категорию с конкретным паттерном обнаружения, диагностики и смягчения, чтобы цифры перестали выглядеть произвольными.

Практика production 2026 года — рассматривать режимы отказов как входные данные для проектирования. Ваша архитектура не «достаточно хороша», пока вы не можете указать на каждую категорию MAST и назвать развёрнутое вами смягчение.

## Концепция

### Категории MAST

**Проблемы спецификации (41,77% отказов).** Задача агента не определена достаточно строго. Примеры:

- Неоднозначность ролей: два агента думают, что оба являются рецензентом.
- Недоопределённая задача: «суммируй это», когда пользователь хотел конкретный ракурс.
- Неявные критерии успеха: агент не может определить, преуспел ли он.

Смягчения:
- Пишите явные контракты ролей. Промпт каждого агента указывает, что он делает *и чего не делает*.
- Критерии приёмки для каждой задачи. Перед началом работы агента определите, как выглядит «готово X».
- Предварительная проверка спецификации: отдельный агент проверяет определение задачи перед диспетчеризацией.

**Сбои координации (36,94%).** Разрывы коммуникации или состояния.

Примеры:
- Два агента обновляют общее состояние без синхронизации.
- Сообщение потеряно между агентами (сбой очереди, тайм-аут).
- Дрейф состояния: агент A считает, что задача выполнена; агент B всё ещё выполняет её.

Смягчения:
- Версионированное общее состояние с оптимистичной конкурентностью.
- Явное подтверждение для критических сообщений (повтор до подтверждения).
- Периодические контрольные точки синхронизации состояния; раннее обнаружение дрейфа.

**Пробелы верификации (21,30%).** Отсутствие независимой проверки выходных данных.

Примеры:
- Один агент заявляет об успехе; никто не проверяет.
- Цепочка агентов, каждый из которых доверяет выходу предыдущего.
- Отсутствует покрытие тестами эмерджентного составного поведения.

Смягчения:
- Независимый агент-верификатор (Урок 13). Доступ только для чтения, независимый источник данных.
- Явный контракт передачи: «Выход A должен пройти проверку C, прежде чем начнёт B».
- Логирование результатов для последующего анализа.

### Семейство Groupthink (arXiv:2508.05687)

Пять связанных отказов, возникающих, когда агенты гомогенизируются или имитируют друг друга:

**Коллапс монокультуры.** Одна базовая модель или данные обучения → коррелированные ошибки. Когда три агента используют одну LLM, они разделяют её галлюцинации.

**Конформистское смещение.** Агенты подстраиваются под самого громкого или наиболее уверенного партнёра, даже когда тот неправ.

**Дефицитная теория сознания.** Агенты не могут моделировать убеждения друг друга; координация распадается (Урок 18).

**Динамика смешанных мотивов.** Агенты с частично совпадающими стимулами дрейфуют к компромиссной середине, которая не удовлетворяет никого.

**Каскадные отказы надёжности.** Паттерн ошибки одного компонента вызывает паттерны ошибок в зависимых компонентах.

### Пример каскада — шторм повторных попыток

Классический паттерн инцидентов 2026 года:

```
payment service fails 10% of requests
   ↓
order agent retries payment (exponential backoff but naive)
   ↓
each retry is a new order-inventory check
   ↓
inventory service sees 2x normal load
   ↓
inventory service starts timing out
   ↓
every order retries inventory check
   ↓
inventory service sees 10x normal load
   ↓
cluster goes down
```

Решение классическое: **предохранители (circuit breakers)**. Когда частота ошибок вниз по потоку превышает порог, выполняется короткое замыкание с кэшированными или дефолтными результатами. Плюс ограниченные бюджеты повторов на запрос.

Предохранители — один из немногих паттернов смягчения мультиагентных отказов, который вы заимствуете напрямую из распределённых систем без изменений.

### Отравление памяти (повторно)

Из Урока 13: галлюцинация одного агента становится фактом в общей памяти; нижестоящие агенты рассуждают на основе отравлённого факта. В терминах MAST это пробел верификации на уровне общей памяти.

Постепенная деградация точности — симптом. Вы не получаете сбоя; вы получаете медленный дрейф, причину которого трудно установить.

Смягчение: журнал только для добавления, происхождение (provenance), неперезаписываемый верификатор. Уже рассмотрено в Уроке 13.

### STRATUS — специализированные агенты для обнаружения отказов

STRATUS (NeurIPS 2025) сообщает о 1,5-кратном улучшении успешности смягчения при развёртывании:

- **Агент обнаружения.** Следит за паттернами симптомов (высокое расхождение, всплески повторов, дрейф точности).
- **Агент диагностики.** По симптомам выводит вероятную первопричину из таксономии MAST.
- **Агент валидации.** После применения смягчения проверяет, что симптомы исчезли.

Это реагирование на инциденты в стиле SRE, применённое к агентным системам. Все три роли могут быть LLM-агентами со специализированными промптами.

### Аудит режимов отказов

Лучшая практика 2026 года — ежегодный (или при каждом крупном релизе) аудит режимов отказов:

1. **Выборка трасс.** Соберите ~1000 реальных трасс исполнения.
2. **Категоризация.** Для отказов каждой трассы сопоставьте с категориями MAST + Groupthink.
3. **Вычислите частоту отказов по категориям.** Какие категории доминируют в вашей системе?
4. **Ранжируйте смягчения.** Какое исправление устранит больше всего отказов?
5. **Выберите 2-3 смягчения.** Реализуйте; повторите аудит в следующем квартале.

Дисциплина важнее конкретных выборов. Без аудитов отказы сливаются с шумом и никогда не решаются системно.

### Когда системы отказывают молча

Самая опасная категория отказов — тихий отказ корректности. Систему, которая отказывает громко (сбой, исключение, оповещение), можно мониторить. Систему, выдающую правдоподобные, но неверные результаты, нельзя обнаружить по логам исключений. Поэтому пробелы верификации — самая дорогая категория в пересчёте на отказ, даже несмотря на то, что по количеству они составляют лишь 21,30%.

Инвестируйте в:
- Выборочный ручной обзор.
- Регрессионные тесты на золотом датасете.
- Взаимную перекрёстную проверку между агентами для важных выходных данных.

### Отказ против медленного отказа

Некоторые отказы мгновенны; некоторые медленны. Мгновенные отказы (тайм-аут, несоответствие схемы, ошибка авторизации) дёшево обнаружить. Медленные отказы (отравление памяти, дрейф монокультуры, неоднозначность ролей) дорого обнаружить и предотвратить.

Инженерный ход 2026 года: инструментируйте прокси-метрики медленных отказов, чтобы ловить дрейф до того, как он станет видимой ошибкой. Частота согласия, частота повторов, распределение длины выходных данных и редакционное расстояние между последовательными версиями агента — всё это полезные прокси.

## Внедрение

Дисциплина режимов отказов в production:

- **Аудит MAST каждый квартал.** Не раз в год. Категории меняются по мере роста вашей системы.
- **Предохранители везде.** Для каждого исходящего вызова к любому зависимому сервису. Порог срабатывания по умолчанию — 5-10% частоты ошибок.
- **Золотые датасеты.** Небольшие, высококачественные, проверенные вручную. Регрессионное тестирование против них еженедельно.
- **Трио STRATUS.** Агенты обнаружения + диагностики + валидации, мониторящие production. Начните только с агента обнаружения; добавьте диагностику, когда симптомы станут шумными.
- **Бюджет отказов.** Явное SLO для частоты отказов по категориям. Превышение бюджета запускает разговор об остановке поставок.

## Упражнения

1. Запустите `code/main.py`. Подтвердите, что предохранитель ограничивает шторм повторов. Варьируйте порог отказа и наблюдайте компромисс.
2. Реализуйте **прокси медленного отказа**: частоту согласия среди 3 параллельных агентов. Когда она резко падает, запускайте оповещение. Симулируйте дрейф монокультуры, постепенно коррелируя выходы агентов.
3. Прочитайте Cemri et al. (arXiv:2503.13657). Выберите одну из их 7 MAS-систем и сопоставьте её топ-3 категории отказов. Как они соотносятся с предсказаниями MAST?
4. Прочитайте статью Groupthink (arXiv:2508.05687). Определите, какой из пяти паттернов труднее всего обнаружить в production. Предложите прокси-метрику.
5. Спроектируйте трио обнаружение-диагностика-валидация в стиле STRATUS для конкретной мультиагентной системы, которую вы знаете. За какими симптомами следит обнаружение? Какие смягчения рекомендует диагностика? Как валидация подтверждает их работу?
