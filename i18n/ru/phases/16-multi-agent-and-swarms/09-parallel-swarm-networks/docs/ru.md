# Параллельные / роевые / сетевые архитектуры

> Контраст с супервизором: нет центрального принимающего решения. Агенты читают общую шину событий, асинхронно забирают работу, записывают результаты обратно. LangGraph явно поддерживает «роевую архитектуру» (Swarm Architecture) для децентрализованных, динамических сред. Matrix (arXiv:2511.21686) представляет и управляющий, и информационный поток в виде сериализованных сообщений, передаваемых через распределённые очереди, чтобы устранить узкое место оркестратора. Компромисс явный: детерминизм и прослеживаемость против масштабируемости. Рой подходит для задач со множеством независимых подзадач; он не подходит для задач, требующих единого согласованного плана.

**Type:** Learn + Build
**Languages:** Python (stdlib, `threading`, `queue`)
**Prerequisites:** Phase 16 · 05 (Supervisor Pattern), Phase 16 · 04 (Primitive Model)
**Time:** ~75 минут

## Проблема

Супервизор масштабируется на несколько воркеров. А что насчёт сотен? Сам супервизор становится узким местом: каждое решение о том, кто что делает, проходит через одного агента. Один медленный шаг плана останавливает всю систему.

Роевые архитектуры переворачивают дизайн. Вместо центрального планировщика, раздающего работу, воркеры сами забирают работу из общей очереди. «Координация» встроена в семантику шины событий. Нет оркестратора; система масштабируется, пока масштабируется очередь.

## Концепция

### Форма

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

Нет оркестратора. Каждый воркер повторяет: забрать задачу, обработать, записать результат (и, опционально, поставить в очередь последующие задачи).

### Когда рой подходит

- **Много независимых задач.** Скрейпинг, преобразование, классификация. Задачи не зависят друг от друга.
- **Работа переменной длительности.** Если одни задачи занимают 100 мс, а другие — 10 с, рой автоматически балансирует нагрузку — быстрые воркеры забирают следующие задания. Супервизору же приходится заранее предугадывать длительность.
- **Пропускная способность важнее детерминизма.** Вас волнует общее время завершения, а не строгий порядок.

### Когда рой не работает

- **Упорядоченные рабочие процессы.** Если шаг 3 нуждается в результате шага 2, рой рискует запустить шаг 3 до завершения шага 2.
- **Задачи с глобальным планом.** Сложные исследовательские вопросы выигрывают от наличия планировщика. Рой исследователей выдаёт независимые факты, а не связный отчёт.
- **Отладка.** Без центрального журнала и при асинхронной работе воспроизведение бага обходится дорого.

### Matrix (arXiv:2511.21686)

Matrix — статья 2025 года, доводящая идею роя до логического завершения: и управляющий поток, и поток данных представлены сериализованными сообщениями в распределённых очередях. Нет центрального координатора. Отказоустойчивость обеспечивается долговечностью сообщений. Масштабируемость — забота брокера сообщений, а не системы.

Вклад работы: программная модель, в которой координация многоагентной системы сводится к вопросу «на какую тему сообщений подписан этот агент?», а не «какого агента супервизор выберет следующим?». Это делает систему похожей на сеть событий pub/sub.

### Рой в графовых фреймворках

Документация LangGraph 2025 года явно описывает «роевую архитектуру» как один из паттернов многоагентных систем: агенты — это узлы, но рёбра образуют направленный граф с циклами, и любой узел может быть активирован из общего пула. Воркер выбирает доступную работу по условию, а не по назначению супервизора.

### Режим отказа: голодание и горячие точки

Если все воркеры забирают самую быструю из доступных задач, долгие задачи никогда не будут выбраны, пока не останутся единственными. Классическое голодание очереди.

Способы смягчения:
- Очереди с приоритетами и явным «старением» (увеличение приоритета по мере ожидания).
- Специализация воркеров: некоторые воркеры берут только «долгие» задачи.
- Обратное давление (back-pressure): ограничение числа быстрых задач, поступающих в очередь.

### Связь с маршрутизацией по содержимому

Рой естественно сочетается с маршрутизацией по содержимому (Урок 22). Вместо одной общей очереди — по очереди на каждый тип сообщения. Специализированные воркеры подписываются только на свой тип. Это основа архитектур на базе шины сообщений, масштабируемых до тысяч агентов.

## Соберите это

`code/main.py` реализует рой из 4 рабочих потоков, забирающих задачи из общей `queue.Queue`. Задачи имеют переменную длительность (некоторые быстрые, некоторые медленные). Демонстрация сравнивает:

- **Последовательный базовый вариант:** один воркер обрабатывает все задачи по очереди.
- **Фиксированное назначение:** каждая задача заранее закреплена за конкретным воркером (в стиле супервизора).
- **Рой:** воркеры забирают задачи из общей очереди.

Рой автоматически балансирует нагрузку; при фиксированном назначении быстрые воркеры простаивают, если их задача оказывается медленной.

Запуск:

```
python3 code/main.py
```

Вывод показывает количество задач на воркера (рой распределяет их неравномерно, но оптимально) и время выполнения в реальном времени.

## Используйте это

`outputs/skill-swarm-fit.md` оценивает, следует ли для задачи использовать рой или супервизора. Входные данные: независимость задач, дисперсия длительности, требования к порядку, потребности в отлаживаемости.

## Готовим к продакшену

Чек-лист:

- **Очередь с приоритетами и старением.** Предотвращает голодание долгих задач.
- **Идемпотентность воркеров.** Задача может быть забрана повторно, если воркер упал в середине выполнения. Воркеры должны быть идемпотентны.
- **Долговечная очередь.** Используйте Kafka, Redis Streams или очередь на основе базы данных для продакшена. `queue.Queue` работает только в памяти.
- **Наблюдаемость на уровне задачи.** У каждой задачи есть trace ID; каждый воркер логирует начало/конец выполнения с ним.
- **Обратное давление.** Если очередь растёт быстрее, чем воркеры её разгружают, замедлите производителя.

## Упражнения

1. Запустите `code/main.py`. Насколько рой быстрее последовательного варианта на нагрузке с переменной длительностью? Насколько быстрее фиксированного назначения?
2. Добавьте вариант с очередью приоритетов (используйте `queue.PriorityQueue`). Назначайте приоритет по полю «важность» задачи. Понаблюдайте, голодают ли задачи с низким приоритетом при непрерывной нагрузке.
3. Реализуйте детектор горячих точек: логируйте, когда какой-либо воркер обрабатывает в 3 раза больше задач, чем самый медленный воркер. О чём это говорит в отношении распределения длительности задач?
4. Прочитайте аннотацию и раздел 3 статьи Matrix (arXiv:2511.21686). Определите один конкретный компромисс, на который идёт Matrix (выигрыш в масштабируемости), и один, от которого отказывается (прослеживаемость, детерминизм).
5. Преобразуйте демонстрацию роя для использования `queue.Queue` кортежей (task_type, payload), где воркеры подписываются только на определённые типы. Какие правила маршрутизации имеют смысл при неоднородных задачах?

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Роевая архитектура | «Децентрализованные агенты» | Воркеры забирают задачи из общей очереди; нет центрального оркестратора. |
| Шина событий | «Агенты подписываются на темы» | Брокер сообщений, направляющий задачи воркерам по типу или содержимому. |
| Голодание | «Задача никогда не выполняется» | Задача с низким приоритетом никогда не выбирается, потому что постоянно поступает работа с более высоким приоритетом. |
| Горячая точка | «Один воркер захлёбывается» | Дисбаланс нагрузки, при котором один воркер получает большинство задач. |
| Обратное давление | «Замедлить производителя» | Механизм, сигнализирующий вышестоящему звену прекратить производство при заполнении очереди. |
| Идемпотентный воркер | «Безопасно перезапускать» | Задача, обработанная дважды, даёт одинаковый результат. Требуется, поскольку воркеры могут упасть в середине выполнения. |
| Долговечная очередь | «Переживает сбои» | Очередь, подкреплённая диском или реплицированным хранилищем; задачи не теряются при сбое воркера. |
| Фреймворк Matrix | «Полноценный рой с передачей сообщений» | И данные, и управляющий поток представлены сериализованными сообщениями в распределённых очередях. |
