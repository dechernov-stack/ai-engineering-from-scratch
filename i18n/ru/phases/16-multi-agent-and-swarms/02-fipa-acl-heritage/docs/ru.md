# Наследие FIPA-ACL и речевых актов

> До MCP, до A2A был FIPA-ACL. В 2000 году IEEE Foundation for Intelligent Physical Agents ратифицировал язык общения агентов с двадцатью перформативами, двумя языками содержимого и набором протоколов взаимодействия — contract net, subscribe/notify, request-when. Он утратил индустриальную значимость, потому что накладные расходы на онтологию оказались слишком тяжёлыми для веба, но возрождение мультиагентных систем на базе LLM тихо переизобретает те же идеи без формальной семантики: JSON-контракты заменяют перформативы, естественный язык заменяет онтологии. Этот урок всерьёз разбирает FIPA-ACL, чтобы вы могли увидеть, какие решения протоколов 2026 года являются переизобретением, какие — действительно новыми, и где текущая волна заново столкнётся с проблемами, уже решёнными в 2000-х.

**Type:** Learn
**Languages:** Python (stdlib)
**Prerequisites:** Phase 16 · 01 (Why Multi-Agent)
**Time:** ~60 минут

## Проблема

Ландшафт протоколов агентов 2026 года переполнен: MCP для инструментов, A2A для агентов, ACP для корпоративного аудита, ANP для децентрализованного доверия, NLIP для содержимого на естественном языке, плюс CA-MCP и ещё пара десятков исследовательских предложений. Каждая спецификация заявляет себя как основополагающую.

Честное прочтение состоит в том, что большинство из них заново открывают весьма конкретное дерево решений двадцатилетней давности. Теория речевых актов Остина (1962) и Сёрла (1969) дала нам идею «высказывания — это действия». KQML (1993) превратил это в сетевой протокол. FIPA-ACL (ратифицирован в 2000) дал эталонную стандартизацию: двадцать перформативов, языки содержимого SL0/SL1, протоколы взаимодействия для contract-net и subscribe-notify. JADE и JACK были эталонными платформами на Java. Усилия угасли примерно к 2010 году, потому что накладные расходы на онтологию оказались слишком тяжёлыми, а побеждал веб.

Когда вы смотрите на `tools/call` в MCP, жизненный цикл задачи в A2A или общее хранилище контекста в CA-MCP, вы смотрите на более мягкую, JSON-native переработку решений FIPA. Знание этого наследия даёт две вещи: понимание, какие новые «инновации» на самом деле являются переизобретениями, и какие старые режимы отказа новые спецификации заново откроют.

## Концепция

### Речевые акты, в одном абзаце

Остин заметил, что некоторые предложения не описывают мир — они его меняют. «Я обещаю». «Я прошу». «Я заявляю». Он назвал это перформативными высказываниями. Сёрл формализовал пять категорий: ассертивы, директивы, комиссивы, экспрессивы, декларативы. KQML (Finin et al., 1993) сделал это операциональным для программных агентов: сообщение — это перформатив (действие) плюс содержимое (о чём это действие). FIPA-ACL устранил пробелы KQML и стандартизировал двадцать перформативов.

### Двадцать перформативов FIPA (частичный список)

| Перформатив | Намерение |
|---|---|
| `inform` | «Я говорю вам, что P истинно» |
| `request` | «Я прошу вас сделать X» |
| `query-if` | «Истинно ли P?» |
| `query-ref` | «Каково значение X?» |
| `propose` | «Я предлагаю сделать X» |
| `accept-proposal` | «Я принимаю предложение» |
| `reject-proposal` | «Я отклоняю предложение» |
| `agree` | «Я соглашаюсь сделать X» |
| `refuse` | «Я отказываюсь делать X» |
| `confirm` | «Я подтверждаю, что P истинно» |
| `disconfirm` | «Я отрицаю P» |
| `not-understood` | «Ваше сообщение не распарсилось» |
| `cfp` | «Запрос предложений по X» |
| `subscribe` | «Уведоми меня, когда X изменится» |
| `cancel` | «Отмени текущее выполнение X» |
| `failure` | «Я попытался выполнить X и не смог» |

Полный список в `fipa00037.pdf` (FIPA ACL Message Structure). Суть не в том, чтобы заучить его, а в том, что каждому из них соответствует примитив, который рано или поздно заново добавляется в протокол на основе LLM.

### Каноническое сообщение FIPA-ACL

```
(inform
  :sender       agent1@platform
  :receiver     agent2@platform
  :content      "((price IBM 83))"
  :language     SL0
  :ontology     finance
  :protocol     fipa-request
  :conversation-id   conv-42
  :reply-with   msg-17
)
```

Семь полей переносят оболочку протокола; одно поле (`content`) переносит полезную нагрузку. Остальные поля — это именно то, что вы переизобретаете каждый раз, когда прикручиваете повторные попытки, потоки (threading) и онтологию к JSON-протоколу.

### Две устаревшие платформы

**JADE** (Java Agent DEvelopment framework, 1999–2020-е) был наиболее широко используемой FIPA-совместимой средой выполнения. Агенты расширяли базовый класс, обменивались ACL-сообщениями, работали внутри контейнеров и координировались с помощью «поведений» (behaviors). Библиотека протоколов взаимодействия поставлялась с contract-net, subscribe-notify, request-when и propose-accept.

**JACK** (Agent Oriented Software, коммерческий) делал акцент на рассуждениях BDI (Belief-Desire-Intention — убеждение-желание-намерение) поверх сообщений FIPA. Более формальный, менее распространённый.

Оба пришли в упадок, когда веб-стек поглотил мультиагентные сценарии использования. MCP и A2A — это «контейнеры» времени выполнения 2026 года.

### Почему FIPA угас

- **Накладные расходы на онтологию.** FIPA требовал общей онтологии для разбора `content`. Согласование онтологий — многолетний процесс стандартизации. Веб просто использовал HTTP + JSON.
- **Формальная семантика, которой никто не пользовался.** SL (Semantic Language) давал строгие условия истинности, но большинство промышленных систем использовали произвольное содержимое и игнорировали формализм.
- **Привязка к инструментарию.** JADE работал только на Java; JACK был коммерческим. Разноязыкие команды обходили оба.
- **Интернет выиграл стек.** REST, затем JSON-RPC, затем gRPC заменили транспорт ACL.

### Возрождение на базе LLM — это облегчённый FIPA

Сравните FIPA `request` с MCP `tools/call`:

```
(request                                {
  :sender  agent1                         "jsonrpc": "2.0",
  :receiver tool-server                   "method":  "tools/call",
  :content "(lookup stock IBM)"           "params":  {"name":"lookup_stock",
  :ontology finance                                   "arguments":{"symbol":"IBM"}},
  :conversation-id c42                    "id": 42
)                                        }
```

Одна и та же оболочка, разный синтаксис. Оба передают: от кого, кому, намерение, полезную нагрузку, идентификатор корреляции. Ни один из них не является революцией по отношению к другому — это разные компромиссы в рамках одного и того же замысла.

Обзор 2025 года Liu et al. («A Survey of Agent Interoperability Protocols: MCP, ACP, A2A, ANP», arXiv:2505.02279) делает эту преемственность явной: MCP соответствует речевым актам использования инструментов, A2A — речевым актам между равноправными агентами, ACP — речевым актам аудиторского следа, ANP — расширениям децентрализованной идентификации. Новые спецификации — это потомки ACL с JSON-синтаксисом и более свободной семантикой.

### Компромисс, сформулированный прямо

**Что давал FIPA и что отбрасывают современные спецификации:**

- Формальная семантика — вы можете доказать, что `inform` подразумевает, что отправитель верит в содержимое.
- Канонический каталог перформативов — вам не нужно заново спорить, «нужен ли нам `cancel`?».
- Десятилетия паттернов протоколов взаимодействия — contract-net, subscribe-notify, propose-accept — с известными свойствами корректности.

**Что дают современные спецификации, чего не было у FIPA:**

- JSON-native полезные нагрузки, совместимые с любым современным инструментом.
- Содержимое на естественном языке, которое LLM могут интерпретировать без ручно закодированной онтологии.
- Транспорт на базе веб-стека (HTTP, SSE, WebSocket).
- Обнаружение возможностей через живые MCP `server/discover` и A2A Agent Cards.

Более свободная семантика намерений ради более простой реализации. Это и есть точный компромисс.

### Протоколы взаимодействия, которые стоит перенести

FIPA поставлял около 15 протоколов взаимодействия. Три из них стоит перенести в мультиагентные системы на базе LLM:

1. **Contract Net Protocol (CNP).** Менеджер выпускает `cfp` (запрос предложений); участники торгов отвечают `propose`; менеджер принимает/отклоняет. Это канонический паттерн «рынка задач» (Phase 16 · 16 Negotiation).
2. **Subscribe/Notify.** Подписчик отправляет `subscribe`; издатель отправляет `inform` при каждом изменении темы. Это любая событийная шина в 2026 году.
3. **Request-When.** «Сделай X, когда выполнится условие Y». Отложенное действие с предусловиями. Аналог 2026 года — отложенные задачи в надёжных (durable) движках рабочих процессов (Phase 16 · 22 Production Scaling).

Каждый из них чисто отображается на современные очереди сообщений, HTTP + опрос или потоковую передачу SSE.

### Что ломается при отказе от онтологии

Без общей онтологии агенты выводят смысл из содержимого на естественном языке. Задокументированный режим отказа 2026 года — это **семантический дрейф**: два агента используют одно и то же слово (`"customer"`) для чуть разных понятий, агент-получатель действует на основе неверной интерпретации, и ни один валидатор схемы этого не улавливает. Требование онтологии в FIPA отклонило бы такое сообщение ещё на этапе разбора.

Смягчение без перехода к полноценной онтологии:

- JSON Schema на `content` — отклоняет структурные ошибки на уровне передачи.
- Типизированные артефакты (A2A) — отклоняет неверную модальность.
- Явный перформатив в оболочке — делает намерение однозначным, даже когда содержимое — естественный язык.

### Спецификации 2026 года, сопоставленные с наследием речевых актов

| Современная спецификация | Аналог в FIPA | Что сохраняет | Что отбрасывает |
|---|---|---|---|
| MCP `tools/call` | `request` | явное намерение, идентификатор корреляции | формальная семантика, онтология |
| MCP `resources/read` | `query-ref` | явное намерение, идентификатор корреляции | формальная семантика |
| Жизненный цикл задачи A2A | contract-net + request-when | асинхронный жизненный цикл, переходы состояний | формальные гарантии полноты |
| Потоковые события A2A | subscribe/notify | асинхронная рассылка | типизированная предикатная подписка |
| Общий контекст CA-MCP | blackboard (Hayes-Roth, 1985) | общая память с несколькими писателями | модель логической согласованности |
| NLIP | содержимое на естественном языке | LLM-native | схема |

Читая таблицу сверху вниз, можно увидеть закономерность: структурный примитив сохраняется, формализм отбрасывается, а LLM заглаживают неоднозначность.

## Постройте это

`code/main.py` реализует транслятор FIPA-ACL на чистом stdlib. Он кодирует и декодирует каноническую оболочку ACL и показывает, как каждая форма сообщения MCP / A2A сводится к тем же семи полям. Демонстрация:

- Кодирует пять сообщений в стиле MCP и A2A как FIPA-ACL.
- Декодирует FIPA-ACL обратно в современный эквивалент.
- Запускает игрушечные переговоры Contract Net между одним менеджером и тремя участниками торгов с использованием `cfp`, `propose`, `accept-proposal`, `reject-proposal`.

Запустите:

```
python3 code/main.py
```

Вывод представляет собой параллельную трассировку, показывающую каждое современное сообщение одновременно в его JSON-форме 2026 года и в форме FIPA-ACL, а затем — цикл заявки на contract-net «туда и обратно». Одни и те же протокольные примитивы переживают этот цикл; меняется только синтаксис.

## Примените на практике

Не возвращайте FIPA-ACL обратно. Верните его чек-лист:

- Каков примитив намерения (перформатив) каждого сообщения?
- Есть ли идентификатор корреляции для запроса-ответа и отмены?
- Есть ли явный язык содержимого (JSON-RPC, обычный текст, структурированный типизированный артефакт)?
- Являются ли протоколы взаимодействия полноценными сущностями, или вы заново реализуете contract-net с нуля?
- Что происходит, когда два агента расходятся во мнении о значении содержимого (семантический дрейф)?

Задокументируйте эти пять вопросов для любого нового протокола, прежде чем вводить его в промышленную эксплуатацию.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Речевой акт (Speech act) | «Высказывание, которое что-то делает» | Остин/Сёрл: высказывания как действия. Теоретический предок ACL. |
| FIPA | «Та старая XML-штука» | IEEE Foundation for Intelligent Physical Agents. Стандартизировал ACL в 2000 году. |
| ACL | «Agent Communication Language» | Формат оболочки FIPA: перформатив + содержимое + метаданные. |
| Перформатив (Performative) | «Глагол» | Класс намерения сообщения: `inform`, `request`, `propose`, `cfp` и т. д. |
| KQML | «Предшественник FIPA» | Knowledge Query and Manipulation Language (1993). Проще, уже по охвату. |
| Онтология | «Общий словарь» | Формальное определение понятий, о которых говорит язык содержимого. |
| SL0 / SL1 | «Языки содержимого FIPA» | Semantic Language уровней 0 и 1 — семейство формальных языков содержимого. |
| Contract Net | «Рынок задач» | Менеджер выпускает cfp; участники торгов предлагают; менеджер принимает. Канонический протокол взаимодействия. |
| Протокол взаимодействия | «Шаблон сообщений» | Последовательность перформативов с известной корректностью: request-when, subscribe-notify и т. д. |
