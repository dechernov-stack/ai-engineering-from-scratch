# Janus-Pro: разделённые энкодеры для унифицированных мультимодальных моделей

> В унифицированных мультимодальных моделях есть неизбежное противоречие. Понимание требует семантических признаков — выходных векторов SigLIP или DINOv2, насыщенных информацией на уровне концепций. Генерация требует кодов, удобных для реконструкции, — VQ-токенов, которые собираются обратно в чёткие пиксели. Эти две цели несовместимы в рамках одного энкодера. Janus (DeepSeek, октябрь 2024) и Janus-Pro (DeepSeek, январь 2025) утверждают, что решение — перестать пытаться их совместить: разделить два энкодера. Разделить тело трансформера между задачами, но направлять понимание через SigLIP, а генерацию — через VQ-токенизатор. При 7B параметрах Janus-Pro превосходит DALL-E 3 на GenEval, одновременно не уступая LLaVA на MMMU. Этот урок объясняет, почему два энкодера работают там, где один терпит неудачу.

**Type:** Build
**Languages:** Python (stdlib, маршрутизация между двумя энкодерами + сигнал общего тела)
**Prerequisites:** Phase 12 · 13 (Transfusion), Phase 12 · 14 (Show-o)
**Time:** ~120 минут

## Цели обучения

- Объяснить, почему единый общий энкодер жертвует либо качеством понимания, либо качеством генерации.
- Описать маршрутизацию в Janus-Pro: признаки SigLIP на входной стороне для понимания, VQ-токены на входе и выходе для генерации.
- Проследить масштабирование смеси данных, которое позволило Janus-Pro добиться успеха там, где Janus не смог.
- Сравнить разделённую (Janus-Pro), совмещённо-непрерывную (Transfusion) и совмещённо-дискретную (Show-o) архитектуры.

## Проблема

Унифицированные модели используют общее тело трансформера как для понимания, так и для генерации. Предыдущие попытки (Chameleon, Show-o, Transfusion) используют один визуальный токенизатор для обоих направлений. Токенизатор — это компромисс:

- Оптимизирован для реконструкции (генерация): VQ-VAE захватывает мелкие детали пикселей, но производит токены со слабой семантической связностью.
- Оптимизирован для семантики (понимание): эмбеддинги SigLIP группируют изображения "кота" рядом с токенами "кот", но не позволяют качественно реконструировать изображение.

Show-o и Transfusion платят за это заметным падением качества в одном из направлений. Janus-Pro задаёт вопрос: зачем требовать единый токенизатор, если у задач разные потребности?

## Концепция

### Разделённое визуальное кодирование

Архитектура Janus-Pro разделяет два энкодера:

- Путь понимания. Входное изображение → SigLIP-SO400m → 2-слойный MLP → тело трансформера.
- Путь генерации. Входное изображение (если идёт обусловливание на существующем изображении) → VQ-токенизатор → ID токенов → тело трансформера.
- Генерация выхода. Токены изображения, предсказанные трансформером → VQ-декодер → пиксели.

Тело трансформера общее. Всё, что находится до и после тела, специфично для задачи.

Входы различаются по формату промпта: тег `<understand>` направляет через SigLIP; `<generate>` — через VQ. Либо маршрутизация подразумевается самой задачей.

### Почему это работает

Функция потерь для понимания получает признаки SigLIP, которые CLIP-подобное предобучение настроило под семантическое сходство. Показатели восприятия модели улучшаются по сравнению с Show-o / Transfusion, поскольку входные признаки лучше подходят под задачу.

Функция потерь для генерации получает VQ-токены, которые токенизатор настроил под реконструкцию. Качество изображений улучшается по сравнению с Show-o, поскольку коды VQ чисто собираются обратно в пиксели.

Общее тело трансформера видит два распределения входных данных (SigLIP и VQ) и учится работать с обоими. Утверждение таково: при достаточном объёме данных и параметров тело усваивает переключение между распределениями.

### Масштабирование данных — Janus против Janus-Pro

Janus (оригинал, arXiv 2410.13848) ввёл разделение, но в малом масштабе (1,3B параметров, ограниченные данные). Janus-Pro (arXiv 2501.17811) масштабировал:

- 7B параметров (против 1,3B).
- 90M пар изображение-текст для этапа 1 (выравнивание), по сравнению с 72M.
- 72M для этапа 2 (унификация), по сравнению с 26M.
- Добавлено 200 тыс. инструктивных образцов генерации изображений для этапа 3.

Результат: Janus-Pro-7B не уступает LLaVA на MMMU (60,3 против ~58) и превосходит DALL-E 3 на GenEval (0,80 против 0,67). Одна открытая модель, конкурентоспособная по обоим направлениям унифицированного спектра.

### JanusFlow — вариант с rectified flow

JanusFlow (arXiv 2411.07975) заменяет путь генерации VQ на путь генерации rectified flow (непрерывный). Разделение становится таким: SigLIP для понимания + rectified flow для генерации. Потолок качества поднимается ещё выше. Архитектура остаётся в парадигме разделённых энкодеров с общим телом.

### Задача общего тела

Тело трансформера обрабатывает единую последовательность, но с двумя распределениями входных данных. Его задача:

- Для понимания: потреблять признаки SigLIP + текстовые токены → генерировать текст авторегрессионно.
- Для генерации: потреблять текстовые токены + (опционально) VQ-токены изображения → генерировать VQ-токены изображения авторегрессионно.

У тела нет весов, специфичных для модальности, в каждом блоке. Это текстовый трансформер того же типа, который вы ожидали бы найти внутри Qwen или Llama, плюс два входных адаптера.

Интересно, что это означает: тело Janus-Pro могло бы быть инициализировано из предобученной LLM. Janus-Pro действительно инициализируется из DeepSeek-MoE-7B. Этот выбор важен: LLM привносит способность к рассуждению, которую унифицированные модели, обучаемые с нуля, с трудом достигают.

### Сравнение с InternVL-U

InternVL-U (Урок 12.10) — это продолжение 2026 года. Она сочетает:

- Нативное мультимодальное предобучение (бэкбон InternVL3).
- Маршрутизацию с разделёнными энкодерами (SigLIP на входе, VQ + диффузионные головы на выходе).
- Унифицированное понимание + генерацию + редактирование.

InternVL-U включает архитектурное решение Janus-Pro в более крупный фреймворк. Идея разделённых энкодеров теперь является стандартом для унифицированных моделей в большом масштабе.

### Ограничения

Разделённые энкодеры добавляют архитектурную сложность. Два токенизатора для обучения, два входных пути для поддержки, два набора режимов отказа. Для продуктов, которым не нужна генерация, Janus-Pro избыточно сложен — выбирайте модель понимания семейства LLaVA.

Для продуктов, которым не нужно понимание, Janus-Pro избыточно квалифицирован — выбирайте модель Stable Diffusion 3 / Flux.

Для продуктов, которым нужно и то, и другое, Janus-Pro теперь является эталонной открытой архитектурой.

## Примените это на практике

`code/main.py` симулирует маршрутизацию Janus-Pro:

- Два мок-энкодера: SigLIP-подобный (производит 256-мерные семантические векторы) и VQ-подобный (производит целочисленные коды).
- Маршрутизатор промптов, выбирающий энкодер на основе тега задачи.
- Общее тело (заглушка), обрабатывающее последовательности токенов независимо от того, каким энкодером они были произведены.
- Переключение от этапа 1 (выравнивание) к расписанию взвешенной выборки этапа 3 (инструктивная настройка).

Выведите маршрутизированные пути для 3 примеров: QA по изображению, T2I, редактирование изображения.

## Упражнения

1. Janus-Pro-7B превосходит DALL-E 3 на GenEval. Объясните, почему открытая модель на 7B параметров может сравняться с проприетарной фронтирной моделью по генерации, но не по пониманию.

2. Реализуйте функцию маршрутизации: по тексту промпта классифицировать его как `understand` или `generate`. Как обрабатывать неоднозначные промпты вроде "опиши, а затем нарисуй"?

3. JanusFlow заменяет путь VQ на rectified flow. Что теперь выдаёт тело трансформера, и что меняется в функции потерь?

4. Предложите четвёртую задачу, которую архитектура Janus-Pro могла бы решать с ещё одним разделённым энкодером. Примеры: сегментация изображений (в стиле DINO), глубина (в стиле MiDaS).

5. Прочитайте раздел 4.2 Janus-Pro о масштабировании данных. Какой этап данных вносит наибольший вклад в прирост качества T2I по сравнению с Janus?

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|-----------------|------------------------|
| Разделённое кодирование | "Два визуальных энкодера" | Отдельный токенизатор или энкодер для каждого направления: семантический для понимания, реконструктивный для генерации |
| Общее тело | "Один трансформер" | Единый трансформер обрабатывает выход любого из энкодеров; нет весов, специфичных для модальности |
| SigLIP для понимания | "Семантические признаки" | Визуальная башня семейства CLIP, обеспечивающая богатые концептуальные признаки, но слабую реконструкцию |
| VQ для генерации | "Коды реконструкции" | Векторно-квантованные токены, которые чисто декодируются обратно в пиксели |
| JanusFlow | "Вариант с rectified flow" | Janus-Pro с непрерывной головой генерации на основе flow-matching вместо VQ |
| Тег маршрутизации | "Тег задачи" | Маркер промпта (`<understand>` / `<generate>`), выбирающий входной энкодер |
