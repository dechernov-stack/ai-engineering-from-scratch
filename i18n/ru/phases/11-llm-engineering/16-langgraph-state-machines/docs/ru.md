# Агентные конечные автоматы — графы, узлы, контрольные точки

> ReAct-цикл, написанный вручную, — это `while True`. Тот же цикл, написанный как явный граф, — это то, что можно поставить на контрольную точку, прервать, разветвить и прокрутить назад во времени. Агент не изменился. Изменилась обвязка вокруг него.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 11 · 09 (Function Calling), Phase 11 · 14 (Model Context Protocol)
**Time:** ~75 минут

## Проблема

Вы выпускаете агента с function calling. Он работает три хода, а затем что-то идёт не так: модель пытается вызвать инструмент, который возвращает 500, пользователь передумывает посреди задачи, или агент решает оформить возврат заказа без одобрения человека. У `while True:`-цикла нет хуков. Вы не можете его приостановить, не можете отмотать назад и не можете разветвить его на «а что, если бы модель выбрала другой инструмент». В тот момент, когда вы выводите это за пределы демо, агент становится чёрным ящиком, который либо сработал, либо нет.

Следующий шаг очевиден, как только вы его увидите. Агент уже является конечным автоматом — системный промпт плюс история сообщений плюс ожидающие вызовы инструментов плюс следующее действие. Сделайте конечный автомат явным: узлы для «модель думает», «инструмент выполняется», «человек одобряет», и рёбра для условных переходов между ними. Как только граф становится явным, обвязка бесплатно получает четыре вещи: контрольные точки (сохранение состояния между шагами), прерывания (пауза для участия человека), потоковую передачу (стриминг токенов и промежуточных событий) и перемещение во времени (отмотка к предыдущему состоянию и попытка другой ветви).

Эталонная реализация этой абстракции — LangGraph. Это не агентный фреймворк в смысле LangChain («вот вам AgentExecutor, удачи»). Это графовый рантайм с полноценным состоянием, полноценной персистентностью и полноценными прерываниями как базовыми концепциями. Агентный цикл — это то, что вы рисуете, а не то, что пишете вручную.

## Концепция

![LangGraph StateGraph: nodes, edges, and the checkpointer](../assets/langgraph-stategraph.svg)

У `StateGraph` есть три составляющие.

1. **Состояние.** Типизированный словарь (TypedDict или модель Pydantic), который протекает через граф. Каждый узел получает полное состояние и возвращает частичное обновление, которое LangGraph объединяет с помощью *редьюсера* для каждого поля — `operator.add` для списков, которые должны накапливаться, по умолчанию — перезапись.
2. **Узлы.** Python-функции `state -> partial_state`. Каждая — это дискретный шаг: «вызвать модель», «выполнить инструменты», «подвести итог».
3. **Рёбра.** Переходы между узлами. Статические рёбра ведут в одно место. Условные рёбра принимают функцию-маршрутизатор `state -> next_node_name`, чтобы граф мог разветвляться в зависимости от вывода модели.

Вы компилируете граф. Компиляция связывает топологию, подключает чекпоинтер (опционально, но критически важно для продакшена) и возвращает runnable-объект. Вы вызываете его с начальным состоянием и `thread_id`. Каждый шаг выполнения сохраняет контрольную точку, ключом для которой служит `(thread_id, checkpoint_id)`.

### Четыре суперспособности

**Контрольные точки.** Каждый переход узла записывает новое состояние в хранилище (in-memory для тестов, Postgres/Redis/SQLite для продакшена). Возобновите, вызвав граф снова с тем же `thread_id`. Граф продолжит с того места, где остановился.

**Прерывания.** Пометьте узел `interrupt_before=["human_review"]`, и выполнение остановится перед запуском этого узла. Состояние сохраняется. Ваш API отвечает пользователю «ожидается одобрение». Последующий запрос к тому же `thread_id` с `Command(resume=...)` возобновляет выполнение.

**Потоковая передача.** `graph.stream(state, mode="updates")` выдаёт дельты состояния по мере их возникновения. `mode="messages"` стримит токены LLM внутри узлов модели. `mode="values"` выдаёт полные снэпшоты. Вы выбираете, что отображать в своём UI.

**Перемещение во времени.** `graph.get_state_history(thread_id)` возвращает полный журнал контрольных точек. Передайте любой предыдущий `checkpoint_id` в `graph.invoke` — и вы разветвитесь с этого момента. Отлично подходит для отладки («что, если бы модель выбрала инструмент B вместо этого?») и для регрессионных тестов, воспроизводящих продакшен-трассы.

### Редьюсеры — это самое важное

У каждого поля состояния есть редьюсер. Большинство значений по умолчанию подходят — новое значение перезаписывает старое. Но спискам сообщений нужен `operator.add`, чтобы новые сообщения добавлялись, а не заменяли. Параллельные рёбра объединяют свои обновления через редьюсер. Если два узла оба обновляют `messages`, а вы забыли про `Annotated[list, add_messages]`, второй побеждает молча, и вы теряете половину хода. Редьюсер — единственная тонкая вещь в библиотеке; настройте её правильно, и всё остальное сложится само.

### ReAct-граф в четырёх узлах

Продакшен-агент ReAct — это четыре узла и два ребра:

1. `agent` — вызывает LLM с текущей историей сообщений. Возвращает сообщение ассистента (которое может содержать tool_calls).
2. `tools` — выполняет любые tool_calls из последнего сообщения ассистента, добавляет результаты инструментов как сообщения-инструменты.
3. Условное ребро из `agent`, которое маршрутизирует к `tools`, если в последнем сообщении есть tool_calls, иначе к `END`.
4. Статическое ребро из `tools` обратно к `agent`.

Вот и всё. Вы получаете полный цикл ReAct (Мысль → Действие → Наблюдение → Мысль → …) с контрольными точками, прерываниями и потоковой передачей примерно в 40 строках кода.

### StateGraph против Send (fanout)

`Send(node_name, state)` позволяет узлу запускать параллельные подграфы. Пример: агент решает одновременно опросить три ретривера. Каждый `Send` порождает параллельное выполнение целевого узла; их выводы объединяются через редьюсер состояния. Именно так LangGraph выражает паттерн «оркестратор-воркеры» без примитивов потоков.

### Подграфы

Скомпилированный граф может быть узлом в другом графе. Внешний граф видит единственный узел; внутренний граф имеет собственное состояние и собственные контрольные точки. Так команды строят агентов типа «супервизор-воркер»: граф-супервизор маршрутизирует намерение пользователя в подграф-воркер для конкретного домена.

## Построим это

### Шаг 1: состояние и узлы

```python
from typing import Annotated, TypedDict
from langchain_core.messages import AnyMessage, HumanMessage, AIMessage
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

def agent_node(state: State) -> dict:
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state: State) -> str:
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END

tool_node = ToolNode(tools=[search_web, read_file])

graph = StateGraph(State)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.set_entry_point("agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")

app = graph.compile(checkpointer=MemorySaver())
```

`add_messages` — это редьюсер, который заставляет список сообщений накапливаться, а не перезаписываться. Забыть про него — самая частая ошибка в LangGraph.

### Шаг 2: запуск с потоком (thread)

```python
config = {"configurable": {"thread_id": "user-42"}}
for event in app.stream(
    {"messages": [HumanMessage("find the Anthropic headquarters address")]},
    config,
    stream_mode="updates",
):
    print(event)
```

Каждое обновление — это словарь `{node_name: state_delta}`. Ваш фронтенд может стримить их в UI, чтобы пользователи видели «агент думает… вызывает search_web… получен результат… отвечает».

### Шаг 3: добавление прерывания с участием человека

Пометьте узел так, чтобы выполнение приостанавливалось перед его запуском.

```python
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["tools"],  # pause before every tool call
)

state = app.invoke({"messages": [HumanMessage("delete the production database")]}, config)
# state["__interrupt__"] is set. Inspect proposed tool calls.
# If approved:
from langgraph.types import Command
app.invoke(Command(resume=True), config)
# If denied: write a rejection message and resume
app.update_state(config, {"messages": [AIMessage("Blocked by human reviewer.")]})
```

Состояние, контрольная точка и поток — всё это сохраняется на время прерывания. В памяти ничего не остаётся, кроме как во время выполнения.

### Шаг 4: перемещение во времени для отладки

```python
history = list(app.get_state_history(config))
for snapshot in history:
    print(snapshot.values["messages"][-1].content[:80], snapshot.config)

# Fork from a prior checkpoint
target = history[3].config  # three steps back
for event in app.stream(None, target, stream_mode="values"):
    pass  # replay from that point forward
```

Передача `None` в качестве входных данных воспроизводит выполнение с заданной контрольной точки; передача значения добавляет его как обновление к состоянию этой контрольной точки перед возобновлением. Так вы воспроизводите неудачный прогон агента, не перезапуская весь разговор заново.

### Шаг 5: замена чекпоинтера для продакшена

```python
from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string("postgresql://...") as checkpointer:
    checkpointer.setup()
    app = graph.compile(checkpointer=checkpointer)
```

SQLite, Redis и Postgres поставляются «из коробки». `MemorySaver` предназначен для тестов. Всё, что должно сохраняться между перезапусками, требует реального хранилища.

## Навык

> Вы строите агентов как графы, а не как `while True`-циклы.

Прежде чем браться за LangGraph, проведите 60-секундное проектирование:

1. **Назовите узлы.** Каждое дискретное решение или действие с побочным эффектом — это узел. «Агент думает», «инструмент выполняется», «рецензент одобряет», «ответ стримится». Если вы не можете их перечислить, задача ещё не имеет «агентной» формы.
2. **Объявите состояние.** Минимальный TypedDict с редьюсером для каждого поля-списка. Не запихивайте всё в `messages`; выносите специфичные для задачи поля (рабочий `plan`, счётчик `budget`, список `retrieved_docs`) на верхний уровень.
3. **Нарисуйте рёбра.** Статические, если следующий шаг не зависит от вывода модели. Каждому условному ребру нужна функция-маршрутизатор с именованными ветвями.
4. **Выберите чекпоинтер заранее.** `MemorySaver` для тестов, Postgres/Redis/SQLite для всего остального. Не выпускайте без него — отсутствие чекпоинтера означает отсутствие возобновления, прерываний и перемещения во времени.
5. **Решайте о прерываниях до запуска инструментов, а не после.** Одобрения размещаются на ребре, ведущем в узел с побочным эффектом, чтобы можно было отменить до нанесения вреда; валидация размещается на ребре, выходящем из модели, чтобы можно было дёшево отклонить плохой вызов.
6. **По умолчанию используйте потоковую передачу.** `mode="updates"` для UI, `mode="messages"` для потоковой передачи на уровне токенов внутри узлов модели, `mode="values"` для полных снэпшотов во время оценки.

Откажитесь выпускать агента LangGraph без чекпоинтера. Откажитесь выпускать такой, который прерывается *после* побочного эффекта. Откажитесь выпускать поле `messages` без `add_messages` в качестве его редьюсера.

## Упражнения

1. **Лёгкое.** Реализуйте четырёхузловой граф ReAct выше с инструментом-калькулятором и инструментом веб-поиска. Убедитесь, что `list(app.get_state_history(config))` возвращает не менее четырёх контрольных точек для диалога из двух ходов.
2. **Среднее.** Добавьте узел `planner`, который запускается перед `agent` и записывает структурированный `plan: list[str]` в состояние. Пусть `agent` помечает шаги плана как выполненные. Провалите тест, если `plan` теряется при возобновлении из контрольной точки (неверный редьюсер).
3. **Сложное.** Постройте граф-супервизор, который маршрутизирует между тремя подграфами (`researcher`, `writer`, `reviewer`) с помощью `Send`. У каждого подграфа — своё состояние и свой чекпоинтер. Добавьте `interrupt_before=["writer"]` на внешнем графе, чтобы человек мог одобрить исследовательское резюме. Убедитесь, что перемещение во времени из предыдущей контрольной точки заново прогоняет только разветвлённую ветвь.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|-----------------|-----------------------|
| StateGraph | «Граф LangGraph» | Объект-билдер, в который вы добавляете узлы и рёбра перед компиляцией. |
| Reducer (редьюсер) | «Как поле объединяется» | Функция `(old, new) -> merged`, применяемая, когда узел возвращает обновление для этого поля; по умолчанию — перезапись, `add_messages` — добавление. |
| Thread (поток) | «ID разговора» | Строка `thread_id`, определяющая область всех контрольных точек для одной сессии. |
| Checkpoint (контрольная точка) | «Приостановленное состояние» | Сохранённый снэпшот полного состояния графа после перехода узла, с ключом `(thread_id, checkpoint_id)`. |
| Interrupt (прерывание) | «Пауза для участия человека» | `interrupt_before` / `interrupt_after` останавливают выполнение на границе узла; возобновление с помощью `Command(resume=...)`. |
| Time-travel (перемещение во времени) | «Разветвление с предыдущего шага» | `graph.invoke(None, config_with_old_checkpoint_id)` воспроизводит выполнение с этой контрольной точки вперёд. |
| Send | «Параллельная диспетчеризация подграфа» | Конструктор, который узел может вернуть, чтобы запустить N параллельных выполнений целевого узла. |
| Subgraph (подграф) | «Скомпилированный граф как узел» | Скомпилированный StateGraph, используемый как узел в другом графе; сохраняет собственную область состояния. |
