# Протокол контекста модели (MCP)

> MCP предоставляет AI-хосту единый протокол для обнаружения и вызова инструментов, ресурсов и промптов. Редакция от 2026-07-28 делает этот протокол бессостоятельным (stateless): контекст возможностей и версии передаётся с каждым запросом, а не хранится в привязанном к соединению рукопожатии.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 11 · 09 (Function Calling), Phase 11 · 03 (Structured Outputs)
**Time:** ~75 минут

## Цели обучения

- Различать AI-хост MCP, клиент, сервер, транспорт и примитив сервера.
- Строить JSON-RPC запрос с метаданными, требуемыми MCP 2026-07-28.
- Использовать `server/discover` для проверки версий, идентичности и возможностей.
- Возвращать типизированные и кэш-ориентированные результаты из инструментов, ресурсов и промптов.
- Объяснять, как современный бессостоятельный MCP взаимодействует с серверами эпохи рукопожатия.
- Выбирать безопасные границы состояния, транспорта и подтверждения для сервера.

## Проблема

Вашему приложению нужны запрос к базе данных, операция с календарём и чтение файла. Без общего протокола каждому AI-хосту потребуется собственная логика обнаружения, вызова, обработки ошибок, транспорта и авторизации для этих же возможностей.

MCP уменьшает эту матрицу интеграции. Сервер публикует стандартную поверхность JSON-RPC. Совместимый клиент может обнаружить эту поверхность, представить её модели или пользователю, вызвать её и интерпретировать результат без адаптера, специфичного для сервера.

Важную границу легко упустить. MCP стандартизирует коммуникацию. Он не решает, какой инструмент должна вызвать модель, не делает ненадёжный контент безопасным и не превращает бессостоятельный запрос в устойчивое состояние приложения. Эти решения по-прежнему остаются за вашим хостом и сервером.

## Концепция

![MCP host, stateless request, and server primitives](../assets/mcp-architecture.svg)

### Три примитива сервера

1. **Инструменты (Tools)** — вызываемые действия. У каждого инструмента есть имя, описание, JSON Schema входных данных и обработчик.
2. **Ресурсы (Resources)** — именованный контент, адресуемый по URI, который клиент может прочитать.
3. **Промпты (Prompts)** — переиспользуемые шаблоны, которые хост может предоставить пользователю.

Хост — это AI-приложение. Клиент MCP внутри этого хоста взаимодействует с одним сервером. Транспорт переносит между ними JSON-RPC сообщения.

### Бессостоятельные запросы заменяют рукопожатие

MCP 2026-07-28 убирает `initialize` и `notifications/initialized`. Также убираются сессии на уровне протокола. Каждый запрос несёт контекст, необходимый для его интерпретации, в `params._meta`:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "lesson-client",
        "version": "1.0.0"
      }
    }
  }
}
```

Версия протокола и возможности клиента обязательны. Идентичность клиента рекомендуется. Отсутствующий `_meta`, отсутствующее обязательное поле или обязательное поле неверного типа считаются некорректным запросом и возвращают Invalid Params (`-32602`). Корректно сформированная строка версии, которую сервер не поддерживает, возвращает `UnsupportedProtocolVersionError` (`-32022`). Сервер может обработать валидный запрос, не восстанавливая запись о предыдущем согласовании.

Бессостоятельность не означает, что приложение никогда не может поддерживать состояние. Это означает, что состояние не скрыто за MCP-соединением или `Mcp-Session-Id`. Если рабочему процессу нужна непрерывность, сервер создаёт непрозрачный идентификатор, и клиент передаёт этот идентификатор как обычный аргумент инструмента в последующих вызовах. Авторизация всё равно должна проверяться на каждом запросе.

### Обнаружение и выбор версии

Каждый современный сервер реализует `server/discover`. Результат объявляет поддерживаемые версии, возможности и идентичность сервера:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": {
      "tools": {},
      "resources": {},
      "prompts": {}
    },
    "ttlMs": 3600000,
    "cacheScope": "public",
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "demo-server",
        "version": "1.0.0"
      }
    }
  }
}
```

Клиент может напрямую вызвать другой метод и обработать ошибку версии, но обнаружение делает отображение возможностей и выбор версии явными. Неподдерживаемая версия возвращает `UnsupportedProtocolVersionError` с кодом `-32022`. Её данные содержат `supported` — массив ревизий сервера — и `requested` — отклонённую ревизию.

По stdio клиент двойной эпохи выполняет зондирование с помощью `server/discover`. Результат обнаружения или распознанная современная ошибка, такая как `UnsupportedProtocolVersionError`, идентифицирует современный сервер. Любая ошибка или тайм-аут, не распознанные как современные, допускают откат к потоку 2025-11-25 `initialize`. Устаревшее поведение — это код совместимости, а не современное поведение по умолчанию.

### Результаты явны

Каждый основной результат в 2026-07-28 имеет `resultType`:

- `complete` означает, что операция завершена.
- `input_required` означает, что серверу требуется ещё один раунд через паттерн Multi Round-Trip Requests. Основные серверы могут возвращать это только из `tools/call`, `resources/read` или `prompts/get`.

Клиенты должны считать устаревший результат, в котором отсутствует `resultType`, завершённым.

Серверы должны включать `io.modelcontextprotocol/serverInfo` в `_meta` каждого результата. Эта идентичность заявляется самим сервером и предназначена для отображения, журналирования и отладки, а не для решений по безопасности.

Результаты list и read также несут `ttlMs` и `cacheScope`. Детерминированный порядок `tools/list` плюс подсказка о свежести позволяют клиентам безопасно кэшировать обнаружение и улучшают стабильность кэша промптов. `cacheScope: public` допускает общее кэширование; `private` ограничивает переиспользование вызывающим контекстом.

### Формат передачи данных и транспорт

MCP использует JSON-RPC 2.0 поверх stdio или Streamable HTTP.

- Запрос содержит `jsonrpc`, `id`, `method` и `params`.
- Ответ содержит соответствующий `id` и либо `result`, либо `error`.
- Уведомление не содержит `id` и не ожидает ответа.

Современный Streamable HTTP предоставляет одну конечную точку, принимающую POST. Каждое сообщение JSON-RPC получает собственный POST. POST-запрос получает в ответ либо один JSON-объект, либо поток Server-Sent Events, привязанный к запросу, который завершается финальным ответом. Принятый POST-уведомление получает HTTP 202 без тела ответа; эта основная редакция не определяет уведомления от клиента к серверу через Streamable HTTP.

В 2026-07-28 нет отдельного MCP GET-потока, конечной точки DELETE для сессии, `Mcp-Session-Id` или воспроизведения `Last-Event-ID`. Долгоживущие уведомления об изменениях используют POST-запрос `subscriptions/listen`, ответ на который остаётся открытым как поток SSE.

### Ввод от клиента без инициируемых сервером запросов

Более старые редакции позволяли серверу отправлять запросы, такие как `sampling/createMessage`, `roots/list` или `elicitation/create`, через поток. Текущий протокол вместо этого использует Multi Round-Trip Requests. Подходящий вызов инструмента, чтение ресурса или получение промпта возвращает `resultType: input_required` с как минимум одним из `inputRequests` или `requestState`. Клиент собирает запрошенный ввод, повторяет исходный метод с новым JSON-RPC ID и соответствующим `inputResponses`, и повторяет точный `requestState`, если он был предоставлен. Если `inputRequests` отсутствовали, повтор опускает `inputResponses`.

Roots, Sampling и Logging остаются функциональными, но объявлены устаревшими, поэтому новые реализации не должны их использовать. Существующие запросы Roots или Sampling передаются внутри MRTR `inputRequests`, а не как независимые JSON-RPC запросы от сервера к клиенту. Предпочитайте явные параметры файла или директории, URI ресурсов, конфигурацию сервера и прямую интеграцию с провайдером модели. Используйте stderr для диагностики stdio и OpenTelemetry для производственной телеметрии.

## Создание

### Шаг 1: регистрация поверхности сервера

Регистрация остаётся простой, хотя контракт запроса изменился:

```python
server = MCPServer("demo-server")

@server.tool(
    "add",
    "Add two integers.",
    {
        "type": "object",
        "properties": {
            "a": {"type": "integer"},
            "b": {"type": "integer"}
        },
        "required": ["a", "b"]
    }
)
def add(a: int, b: int) -> dict:
    return {"sum": a + b}
```

Реализация, поставляемая в `code/main.py`, также регистрирует ресурс и промпт. Она намеренно использует стандартную библиотеку, чтобы вы видели каждый конверт, а не делегировали протокол SDK.

### Шаг 2: прикрепление метаданных к каждому запросу

```python
def request(method, params=None):
    body_params = dict(params or {})
    body_params["_meta"] = {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {
            "name": "demo-client",
            "version": "1.0.0"
        }
    }
    return {
        "jsonrpc": "2.0",
        "id": 1,
        "method": method,
        "params": body_params
    }
```

Не кэшируйте эти метаданные только в объекте соединения. Сервер проверяет их при каждом запросе.

### Шаг 3: опциональное обнаружение перед листингом

Вызовите `server/discover`, выберите поддерживаемую версию, затем вызовите `tools/list`. Прямой вызов `tools/list` также допустим, если вы уже знаете версию и можете обработать `-32022`.

Демонстрация возвращает списки инструментов в порядке имени и прикрепляет `ttlMs`, `cacheScope`, `resultType` и идентичность сервера. Вызов инструмента возвращает полный, не кэшируемый результат, поскольку его вывод может зависеть от текущего состояния.

### Шаг 4: отображение того же запроса на HTTP

Удалённый POST-запрос `tools/call` включает заголовки, отражающие тело JSON-RPC:

```http
POST /mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: add
```

Заголовок `MCP-Protocol-Version` должен соответствовать версии в `_meta`. `Mcp-Method` обязателен для каждого JSON-RPC запроса и должен соответствовать `method`. `Mcp-Name` требуется только для `tools/call`, `resources/read` и `prompts/get`, где он должен соответствовать имени инструмента, URI ресурса или имени промпта. Отсутствующий обязательный заголовок или несоответствие возвращает HTTP 400 с кодом `HeaderMismatch` `-32020`.

### Шаг 5: обеспечение безопасности вне состояния протокола

- Проверяйте авторизацию и аудиторию при каждом HTTP-запросе.
- Привязывайте локальные серверы к localhost и проверяйте `Origin` в Streamable HTTP.
- Помечайте изменяющие инструменты как `destructiveHint: true` и требуйте подтверждения от хоста.
- Передавайте область действия директорий и файлов явно, не полагаясь на устаревшие Roots.
- Рассматривайте ресурсы и вывод инструментов как ненадёжные данные.
- Держите stdout зарезервированным для JSON-RPC при использовании stdio; пишите диагностику в stderr.

Запустите урок из его директории:

```bash

cd code
python3 -m unittest discover tests -v
```

Первая строка должна сообщить об обнаружении `demo-server` по протоколу `2026-07-28`. Затем изучите `MCPClient.request`: он восстанавливает `_meta` для каждого вызова. Удалите метаданные из одного запроса и понаблюдайте, как сервер его отклоняет.

Этот урок даёт вам модель протокола. Фаза 13 превращает четыре производственные границы в отдельные уроки по созданию и проверке:

1. [MCP Tool Contracts and Content](../../../13-tools-and-protocols/28-mcp-tool-contracts-and-content/docs/en.md) охватывает закрытые входные схемы, структурированный контент, метаданные маршрутизации, непрозрачную пагинацию, авторизацию завершения и разницу между ошибками протокола и предметной области инструмента.
2. [MCP Reliability, Cancellation, and Flow Control](../../../13-tools-and-protocols/29-mcp-reliability-cancellation-and-flow-control/docs/en.md) охватывает отмену запроса, отмену устойчивых задач, дедлайны, идемпотентность, обратное давление, буферизацию прокси и поведение при переподключении.
3. [MCP Registry Supply Chain, Admission, Drift, and Rollback](../../../13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift/docs/en.md) охватывает доказательство пространства имён, происхождение артефактов, неизменяемые привязки, живой дрейф, статус реестра, свидетельства допуска и откат.
4. [MCP Conformance Engineering](../../../13-tools-and-protocols/31-mcp-conformance-versioning-and-operations/docs/en.md) охватывает эталонные и негативные транскрипты передачи данных, строгие эры версий, дифференциалы SDK, свидетельства прокси, редактирование, шлюзы здоровья и откат релиза.

Следуйте им по порядку, когда сервер пересекает границу команды или доверия. Вместе они переводят состояние от «метод работает» к «контракт остаётся безопасным и диагностируемым на протяжении развёртывания».

## Упражнения

1. Добавьте инструмент `subtract` и убедитесь, что `tools/list` остаётся упорядоченным по алфавиту.
2. Удалите ключ версии протокола и проверьте Invalid Params (`-32602`). Затем отправьте корректно сформированную, но неподдерживаемую версию `2025-11-25`, проверьте `-32022`, убедитесь, что `requested` повторяет эту ревизию, и выберите из `supported`.
3. Добавьте созданный сервером `draftId` к операции создания, затем потребуйте его в качестве аргумента для обновления. Объясните, почему это состояние приложения, а не сессия протокола.
4. Верните `input_required` из инструмента, которому требуется подтверждение пользователя. Повторите исходный вызов с новым ID, записью `inputResponses` и точным `requestState`, вместо того чтобы изобретать JSON-RPC запрос от сервера к клиенту.
5. Набросайте клиент stdio двойной эпохи. Считайте результат или распознанную современную ошибку современными и допускайте откат к `initialize` только для нераспознанной ошибки или тайм-аута.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|-----------------|------------------------|
| MCP | «Протокол инструментов для LLM» | Протокол JSON-RPC для обнаружения серверов, инструментов, ресурсов, промптов и расширений |
| Host (Хост) | «AI-приложение» | Владеет моделью и интерфейсом и подключает один или несколько клиентов MCP |
| Client (Клиент) | «Коннектор» | Общается по MCP с одним сервером от имени хоста |
| Stateless MCP (Бессостоятельный MCP) | «Нет сессии» | Каждый запрос несёт версию и возможности; состояние протокола не привязано к соединению |
| `server/discover` | «Зондирование возможностей» | Обязательный метод сервера, объявляющий версии, возможности и идентичность |
| `resultType` | «Состояние результата» | Отмечает результат как `complete` или `input_required` |
| State handle (Идентификатор состояния) | «ID рабочего процесса» | Идентификатор приложения, созданный сервером, передаваемый как обычный аргумент |
| Streamable HTTP | «Удалённый транспорт» | Одна POST-конечная точка с JSON- или привязанными к запросу SSE-ответами |
| MRTR | «Спроси и повтори» | Запрос ввода, встроенный в результат, за которым следует повтор исходной операции |
