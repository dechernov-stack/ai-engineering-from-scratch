# AI-шлюзы — LiteLLM, Portkey, Kong AI Gateway, Bifrost

> Шлюз располагается между вашими приложениями и провайдерами моделей. Ключевые функции — маршрутизация между провайдерами, фолбэк, повторные попытки, ограничение частоты запросов, ссылки на секреты, observability, guardrails. Расклад на рынке в 2026 году: **LiteLLM** — MIT OSS со 100+ провайдерами, совместим с OpenAI, но «ломается» примерно при ~2000 RPS (8 ГБ памяти, каскадные сбои в опубликованных бенчмарках); лучше всего подходит для Python, <500 RPS, разработки/прототипирования. **Portkey** позиционируется как control plane (guardrails, редактирование PII, обнаружение jailbreak, журналы аудита), стал Apache 2.0 открытым исходным кодом в марте 2026 года, накладные расходы на задержку 20-40 мс, цена $49/mo production tier. **Kong AI Gateway** built on Kong Gateway — Kong's own benchmark on same 12 CPUs: 228% faster than Portkey, 859% faster than LiteLLM; $100/модель/месяц (максимум 5 на тарифе Plus); подходит для enterprise, если вы уже используете Kong. **Bifrost** (Maxim AI) — автоматические повторные попытки с настраиваемым бэкоффом, фолбэк на Anthropic при 429 от OpenAI. **Cloudflare / Vercel AI Gateways** — управляемые, без необходимости администрирования, базовый retry. Резидентность данных определяет решение о self-host; Portkey и Kong занимают промежуточную позицию с OSS + опциональным управляемым сервисом.

**Type:** Изучение
**Languages:** Python (stdlib, игрушечный симулятор маршрутизации шлюза)
**Prerequisites:** Phase 17 · 01 (Managed LLM Platforms), Phase 17 · 16 (Model Routing)

## Цели обучения

- Перечислить шесть ключевых функций шлюза (маршрутизация, фолбэк, повторные попытки, ограничение частоты запросов, секреты, observability, guardrails).
- Сопоставить четыре шлюза 2026 года (LiteLLM, Portkey, Kong AI, Bifrost) с потолками масштабируемости и сценариями использования.
- Привести бенчмарк Kong (228% против Portkey, 859% против LiteLLM) и объяснить, почему это важно при >500 RPS.
- Выбрать между self-hosted и managed, исходя из резидентности данных и бюджета на эксплуатацию.

## Проблема

Ваш продукт обращается к OpenAI, Anthropic и самостоятельно размещённой Llama. У каждого провайдера свой SDK, модель ошибок, ограничение частоты запросов и схема аутентификации. Вам нужен отказоустойчивый фолбэк (если OpenAI отвечает 429, попробовать Anthropic), единое хранилище учётных данных, унифицированный observability и ограничения частоты запросов для каждого арендатора.

Переизобретать всё это на уровне приложения означает жёстко связать каждый сервис с каждым провайдером. Слой шлюза консолидирует это в одном процессе с единым API (как правило, совместимым с OpenAI), который распределяет запросы между провайдерами.

## Концепция

### Шесть ключевых функций

1. **Маршрутизация между провайдерами** — OpenAI, Anthropic, Gemini, самостоятельно размещённые модели и т. д. за единым API.
2. **Фолбэк** — при 429, 5xx или сбое качества повторить попытку в другом месте.
3. **Повторные попытки** — экспоненциальный бэкофф, ограниченное число попыток.
4. **Ограничение частоты запросов** — на арендатора, на ключ, на модель.
5. **Ссылки на секреты** — получение учётных данных из хранилища во время выполнения (никогда не хранятся в приложении).
6. **Observability** — OTel + атрибуты GenAI (Phase 17 · 13) + атрибуция стоимости.
7. **Guardrails** — редактирование PII, обнаружение jailbreak, фильтры разрешённых тем.

### LiteLLM — MIT OSS, Python

- 100+ провайдеров, совместим с OpenAI, конфигурация маршрутизатора, фолбэк, базовый observability.
- «Ломается» примерно при 2000 RPS в бенчмарке Kong; потребление памяти 8 ГБ, каскадные сбои при устойчивой нагрузке.
- Лучше всего подходит: приложение на Python, <500 RPS, шлюзы для dev/staging, экспериментальная маршрутизация.
- Стоимость: $0 для OSS; существует бесплатный облачный тариф.

### Portkey — позиционирование как control plane

- Apache 2.0 OSS с марта 2026 года. Guardrails, редактирование PII, обнаружение jailbreak, журналы аудита.
- Накладные расходы на задержку 20-40 мс на запрос.
- $49/мес за продакшн-тариф с хранением данных + SLA.
- Лучше всего подходит: регулируемые отрасли, которым нужны guardrails + observability в одном пакете.

### Kong AI Gateway — ставка на масштаб

- Построен на Kong Gateway (зрелый продукт-шлюз API, lua+OpenResty).
- Собственный бенчмарк Kong на эквиваленте 12 CPU: на 228% быстрее Portkey, на 859% быстрее LiteLLM.
- Цены: $100/модель/месяц, максимум 5 на тарифе Plus.
- Лучше всего подходит: если вы уже используете Kong; >1000 RPS; готовность платить за лицензию.

### Bifrost (Maxim AI)

- Автоматические повторные попытки с настраиваемым бэкоффом.
- Фолбэк на Anthropic при 429 от OpenAI — каноничный рецепт.
- Более новый игрок; коммерческий.

### Cloudflare AI Gateway / Vercel AI Gateway

- Управляемые, без необходимости администрирования. Базовый retry и observability.
- Лучше всего подходит: JavaScript-приложения, обслуживаемые на edge в Cloudflare/Vercel.
- Ограниченные возможности по сравнению с Kong/Portkey в части guardrails и ограничения частоты запросов.

### Self-hosted против managed

Резидентность данных — определяющий фактор. Здравоохранение и финансы по умолчанию выбирают self-host (LiteLLM, Portkey OSS или Kong). Потребительские продукты по умолчанию выбирают managed (Cloudflare AI Gateway) или промежуточный уровень (Portkey managed). Гибридный вариант: self-hosted для регулируемого арендатора, managed для остальных.

### Бюджет задержки

- LiteLLM: обычно 5-15 мс накладных расходов.
- Portkey: 20-40 мс накладных расходов.
- Kong: 3-8 мс накладных расходов.
- Cloudflare/Vercel: 1-3 мс накладных расходов (преимущество edge).

Задержка шлюза напрямую добавляется к TTFT. Для SLA TTFT P99 < 100 мс — Kong или Cloudflare. Для P99 < 500 мс — подойдёт любой.

### Семантика ограничения частоты запросов имеет значение

Простой token-bucket работает до умеренного масштаба. Для многоарендной среды требуется sliding-window + допуск на всплески + тарификация по арендатору. LiteLLM поставляется с token-bucket; Kong — со sliding-window; Portkey — с тарифицированным подходом.

### Шлюз + observability + маршрутизация образуют единое целое

Phase 17 · 13 (observability) + 16 (маршрутизация моделей) + 19 (шлюзы) — это один и тот же слой в продакшене. Выберите один инструмент, покрывающий все три направления, либо тщательно свяжите их между собой: в большинстве развёртываний 2026 года Helicone (observability) или Portkey (guardrails) комбинируют с Kong (масштаб) для разделения ролей.

### Цифры, которые стоит запомнить

- LiteLLM: «ломается» при ~2000 RPS, 8 ГБ памяти.
- Portkey: накладные расходы 20-40 мс; Apache 2.0 с марта 2026 года.
- Kong: на 228% быстрее Portkey, на 859% быстрее LiteLLM.
- Цены Kong: $100/модель/месяц, максимум 5 на тарифе Plus.
- Cloudflare/Vercel: 1-3 мс накладных расходов на edge.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Gateway (шлюз) | «API-брокер» | Процесс между приложениями и провайдерами |
| LiteLLM | «тот самый MIT» | Python OSS, 100+ провайдеров, «ломается» при 2K RPS |
| Portkey | «шлюз с guardrails» | Control plane + observability, Apache 2.0 |
| Kong AI Gateway | «тот самый масштабный» | Построен на Kong Gateway, лидер бенчмарков |
| Bifrost | «шлюз от Maxim» | Рецепт retries + фолбэк на Anthropic |
| Cloudflare AI Gateway | «управляемый edge» | Управляемый шлюз, развёрнутый на edge, без администрирования |
| PII redaction | «очистка данных» | Маскирование Regex + NER перед отправкой в модель |
| Jailbreak detection | «защита от prompt injection» | Классификатор пользовательского ввода |
| Audit trail | «регулируемый лог» | Неизменяемая запись каждого вызова LLM |
| Token-bucket | «простое ограничение частоты запросов» | Лимитер на основе пополнения |
| Sliding-window | «точное ограничение частоты запросов» | Лимитер с временными окнами; лучшая справедливость распределения |
