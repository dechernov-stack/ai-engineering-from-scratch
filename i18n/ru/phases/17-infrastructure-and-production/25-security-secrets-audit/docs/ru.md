# Безопасность — секреты, ротация API-ключей, аудит-логи, guardrails

> Устраните разрастание секретов с помощью централизованных хранилищ (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault). Никогда не храните учётные данные в конфигурационных файлах, env-файлах в VCS, таблицах. Используйте роли IAM вместо статических ключей; OIDC для CI/CD. Паттерн AI-gateway — решение 2026 года: приложения → шлюз → провайдер модели, при этом шлюз получает учётные данные из хранилища во время выполнения. Ротация в хранилище — и все приложения подхватывают изменения за минуты, без передеплоя, без сообщений в Slack «у кого новый ключ». Политика ротации ≤90 дней; сканирование TruffleHog / GitGuardian / Gitleaks при каждом коммите. Нулевое доверие: MFA, SSO, RBAC/ABAC, короткоживущие токены, проверка состояния устройства. Очистка PII использует распознавание сущностей для маскирования PHI/PII перед отправкой; согласованная токенизация (подход Mesh) отображает чувствительные значения в стабильные плейсхолдеры, так что LLM сохраняет семантику кода/связей. Сетевой исходящий трафик: сервисы LLM в выделенной подсети VPC/VNet с whitelist только для `api.openai.com`, `api.anthropic.com` и т. д.; блокировка всего остального исходящего трафика. Инцидент 2026 года, определивший повестку: атака на цепочку поставок Vercel через скомпрометированные учётные данные CI/CD привела к утечке env-переменных в тысячах развёртываний клиентов.

- Назвать инцидент с цепочкой поставок Vercel 2026 года и что он показал в части гигиены учётных данных CI/CD.

## Проблема

Стажёр коммитит `.env` с API-ключами. Он быстро удаляет его. Ключи уже в истории git — сканирование GitGuardian их обнаруживает, а ваш процесс ротации — это «написать команде в Slack, обновить 40 конфигурационных файлов, передеплоить все сервисы». Через 8 часов половина ваших сервисов в строю, а половина ждёт окна деплоя.

Отдельно пользовательские промпты содержат «Мой SSN — 123-45-6789». Промпт уходит в OpenAI. У вас есть BAA, но внутренняя политика требует маскировать PII перед отправкой. Вы этого не сделали.

Отдельно под в вашем кластере EKS с LLM может обратиться к любому хосту в интернете. Кто-то экс­фильтрует данные через DNS-запрос на домен, контролируемый атакующим. Ничего это не заблокировало.

Безопасность для LLM-сервисов должна учитывать все три вектора. Учётные данные на основе хранилища. Очистка PII. Фильтрация исходящего сетевого трафика. Аудит-логи.

## Концепция

### Централизованное хранилище + получение через роль IAM

**Хранилище (vault)**: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager. Единый источник истины.

**Роль IAM**: приложение/шлюз аутентифицируется через свою IAM-идентичность, а не статический ключ. Хранилище возвращает секрет на время жизни токена.

**Паттерн AI-gateway**: шлюз получает `OPENAI_API_KEY` из хранилища в момент запроса. Ротация в хранилище — следующий запрос получает новый ключ. Без передеплоя.

### Политика ротации ≤ 90 дней

Все API-ключи, корневые токены хранилища, учётные данные CI/CD. По возможности — автоматическая ротация. Ручная ротация логируется и отслеживается.

### Сканирование секретов

- **TruffleHog** — регулярные выражения + энтропия для коммитов.
- **GitGuardian** — коммерческий, высокая точность.
- **Gitleaks** — open source, работает в CI.

Запускается при каждом коммите. Блокировка PR при обнаружении нового секрета.

### Позиция нулевого доверия

- MFA обязательна для всех аккаунтов.
- SSO через SAML/OIDC.
- RBAC (на основе ролей) или ABAC (на основе атрибутов) для тонкого контроля доступа.
- Короткоживущие токены (часы, а не дни).
- Проверка состояния устройства — только корпоративные устройства с шифрованием диска.

### Очистка PII / PHI

Перед тем как промпт покинет вашу инфраструктуру:

1. Распознавание сущностей (spaCy NER, Presidio, коммерческие решения).
2. Маскирование найденных сущностей: `"My SSN is 123-45-6789"` → `"My SSN is [SSN_TOKEN_A3F]"`.
3. Согласованная токенизация (подход Mesh): одно и то же значение отображается в один и тот же плейсхолдер, так что LLM сохраняет связи.
4. Опциональное обратное отображение для ответа LLM.

Статические регулярные фильтры ловят базовые паттерны; NER ловит больше. Используйте оба.

### Guardrails на входе и выходе

Вход: блокировка известных джейлбрейков, запрещённых тем; ограничение частоты запросов на пользователя.

Выход: regex-очистка от утечек секретов (паттерны API-ключей, email-паттерны в контекстах отказа), классификатор нарушений политики.

### Whitelist исходящего сетевого трафика

LLM-сервисы в выделенной подсети:
- Whitelist: `api.openai.com`, `api.anthropic.com`, эндпоинты векторной БД, эндпоинты хранилища.
- Всё остальное: отбрасывается.
- DNS только через резолвер с allowlist (предотвращает эксфильтрацию через DNS-туннелирование).

### Аудит-лог

Неизменяемый лог каждого вызова LLM с:
- Временной меткой.
- Пользователем / тенантом.
- Хешем промпта (не сырым промптом — для приватности).
- Моделью + версией.
- Количеством токенов.
- Стоимостью.
- Хешем ответа.
- Любыми срабатываниями guardrails.

Хранение согласно регуляторным требованиям (SOC 2 — 1 год, HIPAA — 6 лет).

### Инцидент Vercel 2026 года

Атака на цепочку поставок: скомпрометированные учётные данные CI/CD привели к утечке env-переменных в тысячах развёртываний клиентов. Урок: учётные данные CI/CD эквивалентны продакшену. Хранить в хранилище. Ограничивать по области действия. Ротировать агрессивно.

### Цифры, которые стоит запомнить

- Политика ротации: ≤ 90 дней.
- Сканирование при каждом коммите: TruffleHog / GitGuardian / Gitleaks.
- Vercel 2026: скомпрометированные учётные данные CI/CD → утечка тысяч env-переменных клиентов.
- Хранение аудит-логов: SOC 2 = 1 год, HIPAA = 6 лет.

## Упражнения

1. Запустите `code/main.py`. Отправьте два промпта со ссылкой на один и тот же SSN. Убедитесь, что оба получают один и тот же плейсхолдер.
2. Спроектируйте политику исходящего сетевого трафика для развёртывания vLLM на EKS, обращающегося к OpenAI + Anthropic + Weaviate.
3. Вы обнаружили ключ в истории git (двухлетней давности). Какая реакция верна — ротация ключа, очистка истории, или и то и другое? Обоснуйте.
4. Ваш аудит-лог растёт на 10 ГБ/день. Спроектируйте уровни хранения (горячий — 30 дней, тёплый — 12 месяцев, холодный — 6 лет).
5. Обоснуйте, стоит ли обратная токенизация (подстановка реальных значений обратно в ответ LLM) дополнительной сложности по сравнению с сохранением видимых плейсхолдеров.

## Ключевые термины

| Термин | Как говорят | Что это на самом деле означает |
|------|----------------|------------------------|
| Vault (хранилище) | «хранилище секретов» | Централизованный сервис управления учётными данными |
| Роль IAM | «аутентификация на основе идентичности» | Роль, принимаемая приложением; возвращает короткоживущие учётные данные |
| OIDC для CI/CD | «токены, выпускаемые облаком» | Нет статических ключей в CI — идентичность через OIDC |
| TruffleHog / GitGuardian / Gitleaks | «сканеры секретов» | Обнаружение секретов в момент коммита |
| RBAC / ABAC | «контроль доступа» | На основе ролей против на основе атрибутов |
| Очистка PII | «маскирование данных» | Удаление или токенизация чувствительных сущностей |
| Согласованная токенизация | «стабильные плейсхолдеры» | Одно и то же значение → один и тот же токен каждый раз |
| Подход Mesh | «токенизация Mesh» | Паттерн токенизации с сохранением семантики |
| Egress whitelist | «allowlist исходящего трафика» | Доступны только разрешённые домены |
| Аудит-лог | «неизменяемая история» | Запись только на добавление для соответствия требованиям |
