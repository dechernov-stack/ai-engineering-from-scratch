# Выбор self-hosted инференса — подбор движка под железо и масштаб

> Выбор движка — это функция от железа, масштаба и экосистемы, а не чтение таблицы лидеров. В 2026 году в self-hosted инференсе доминируют четыре движка: llama.cpp, Ollama, vLLM, SGLang, а TGI отстаёт, находясь в режиме поддержки. **llama.cpp** быстрее всех на CPU — самая широкая поддержка моделей, полный контроль над квантованием и многопоточностью. **Ollama** — установка в одну команду для разработческого ноутбука, на ~15-30% медленнее, чем llama.cpp (Go + CGo + HTTP-сериализация), разрыв в пропускной способности 3x при прод-подобной нагрузке. **TGI перешёл в режим поддержки 11 декабря 2025 года** — только исправления багов, сырая пропускная способность примерно на 10% ниже, чем у vLLM, но исторически лучшая наблюдаемость и интеграция с экосистемой HF. Такой статус поддержки делает его рискованной долгосрочной ставкой — SGLang или vLLM являются более безопасным выбором по умолчанию для новых проектов. **vLLM** — универсальный продакшн-движок по умолчанию — v0.15.1 (февраль 2026) добавляет PyTorch 2.10, RTX Blackwell SM120, оптимизацию под H200. **SGLang** — специалист по агентным многошаговым сценариям и работе с префиксами — 400 000+ GPU в продакшене (xAI, LinkedIn, Cursor, Oracle, GCP, Azure, AWS). Ограничения по железу: CPU-first → llama.cpp. AMD / не-NVIDIA → vLLM — наиболее надёжный путь (TRT-LLM привязан к NVIDIA). Паттерн пайплайна 2026 года: dev = Ollama, staging = llama.cpp, prod = vLLM или SGLang. Движки используют разные форматы весов — GGUF для семейства llama.cpp, HF safetensors для GPU-движков — поэтому между этапами может потребоваться конвертация формата.

## Проблема

Ваша команда начинает новый self-hosted LLM-проект. Один инженер говорит — Ollama, другой — vLLM, третий спрашивает: «а разве TGI не работает из коробки?» Все трое правы в разных контекстах. Никто не прав для всех случаев.

В 2026 году важно само дерево выбора: сначала железо, затем масштаб, затем тип нагрузки. И одно конкретное событие 2025 года — переход TGI в режим поддержки 11 декабря — меняет вариант по умолчанию для новых проектов.

## Концепция

### Пять движков

| Движок | Лучше всего для | Примечания |
|--------|----------|-------|
| **llama.cpp** | CPU / edge / минимум зависимостей / самая широкая поддержка моделей | Быстрее всех на CPU, полный контроль |
| **Ollama** | Разработческие ноутбуки, один пользователь, установка одной командой | На 15-30% медленнее, чем llama.cpp; разрыв в пропускной способности 3x в проде |
| **TGI** | Экосистема HF, регулируемые отрасли | **Режим поддержки с 11 дек. 2025** |
| **vLLM** | Универсальный продакшн, 100+ пользователей | Широкий вариант по умолчанию для продакшена; v0.15.1, февраль 2026 |
| **SGLang** | Агентные многошаговые сценарии, нагрузки с интенсивным переиспользованием префиксов | 400 000+ GPU в продакшене |

### Решение «железо в первую очередь»

**CPU-first** → llama.cpp. Ollama тоже работает, но медленнее. Ни один другой движок не конкурентоспособен на CPU.

**AMD GPU** → vLLM — наиболее надёжный путь (поддержка AMD ROCm). SGLang тоже работает. TRT-LLM привязан к NVIDIA, так что он не подходит.

**NVIDIA Hopper (H100 / H200)** → vLLM, SGLang или TRT-LLM. Все три — топ-уровня.

**NVIDIA Blackwell (B200 / GB200)** → TRT-LLM — лидер по пропускной способности (Phase 17 · 07). vLLM и SGLang идут следом, с небольшим отставанием.

**Apple Silicon (M-серия)** → llama.cpp (Metal). Ollama оборачивает это.

### Решение «масштаб во вторую очередь»

**1 пользователь / локальная разработка** → Ollama. Одна команда, первый токен за секунды.

**10-100 пользователей / небольшая команда** → vLLM на одном GPU.

**100-10 тыс. пользователей / продакшен** → vLLM production-stack (Phase 17 · 18) или SGLang.

**10 тыс.+ пользователей / enterprise** → vLLM production-stack + дизагрегация (Phase 17 · 17) + LMCache (Phase 17 · 18).

### Решение «нагрузка в третью очередь»

**Обычный чат / вопрос-ответ** → vLLM побеждает как широкий вариант по умолчанию.

**Агентные многошаговые сценарии (инструменты, планирование, память)** → доминирует RadixAttention в SGLang (Phase 17 · 06).

**RAG с интенсивным переиспользованием префиксов** → SGLang.

**Генерация кода** → vLLM подходит хорошо; SGLang чуть лучше за счёт кеша.

**Длинный контекст (128K+)** → vLLM + chunked prefill; SGLang + многоуровневый KV.

### Ловушка режима поддержки TGI

Hugging Face TGI перешёл в режим поддержки 11 декабря 2025 года — дальше только исправления багов. Исторически: наблюдаемость топ-уровня, лучшая в своём классе интеграция с экосистемой HF (карточки моделей, инструменты безопасности), немного отстаёт от vLLM по сырой пропускной способности.

Для новых проектов в 2026 году: по умолчанию избегайте TGI. Существующие развёртывания TGI могут продолжать работать, но со временем их стоит мигрировать. SGLang и vLLM — более безопасные варианты по умолчанию.

### Паттерн пайплайна

Dev (Ollama) → staging (llama.cpp) → prod (vLLM). Движки используют разные форматы весов — GGUF для семейства llama.cpp, HF safetensors для GPU-движков — поэтому между этапами может потребоваться конвертация формата. Инженеры быстро итерируют на ноутбуках; staging отражает продакшн-квантование; prod — целевая среда обслуживания.

### Оговорка про Ollama

Ollama отлично подходит для разработки. Но не очень хорош для совместного продакшена: HTTP-сериализация на Go добавляет накладные расходы, управление параллелизмом проще, чем в vLLM, поддержка OpenTelemetry отстаёт. Используйте Ollama там, где он блистает — один пользователь, одна команда — и переходите на vLLM для совместного использования.

### Self-hosted против managed — отдельное решение

Phase 17 · 01 (managed-гиперскейлеры), · 02 (платформы инференса) освещают managed-варианты. Этот урок предполагает, что вы уже решили развёртывать self-hosted. Причины для self-hosted: резидентность данных, кастомный fine-tune, совокупная стоимость владения при масштабе, доменная модель, недоступная в размещённом варианте.

### Цифры, которые стоит запомнить

- Режим поддержки TGI: 11 декабря 2025 года.
- vLLM v0.15.1: февраль 2026; PyTorch 2.10; поддержка Blackwell SM120.
- Продакшн-база SGLang: 400 000+ GPU.
- Разрыв пропускной способности Ollama относительно llama.cpp: на 15-30% медленнее; 3x при прод-нагрузке.
