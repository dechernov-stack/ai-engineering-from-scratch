# Disaggregated Prefill/Decode — NVIDIA Dynamo и llm-d

> Prefill — операция, ограниченная вычислениями; decode — операция, ограниченная пропускной способностью памяти. Запуск обоих на одном GPU расходует впустую один из ресурсов. Дизагрегация разносит их по отдельным пулам и передаёт KV-кэш между ними через NIXL (RDMA/InfiniBand или откат на TCP). NVIDIA Dynamo (анонс GTC 2025, 1.0 GA) располагается поверх vLLM/SGLang/TRT-LLM — её Planner Profiler + SLA Planner автоматически подбирают соотношение prefill:decode для соблюдения SLO. NVIDIA публикует прирост throughput примерно в этих пределах — developer.nvidia.com (2025-06) показывает ~6x улучшение для DeepSeek-R1 MoE на GB200 NVL72 + Dynamo в режиме средней задержки, а страница продукта Dynamo (developer.nvidia.com, без даты) заявляет до 50x throughput на MoE на GB300 NVL72 + Dynamo против Hopper. Цифра "30x" — это агрегированная оценка сообщества по отчётам о полном стеке Blackwell + Dynamo + DeepSeek-R1; мы не нашли единого первоисточника, заявляющего ровно 30x, поэтому считайте её ориентировочной оценкой направления. llm-d (Red Hat + AWS) ориентирован на Kubernetes: prefill / decode / router — независимые Services с per-role HPA. llm-d 0.5 добавляет иерархическую выгрузку KV, кэш-ориентированную маршрутизацию LoRA, сетевой слой UCCL, scale-to-zero. Экономика: внутренний сводный анализ нескольких раскрытий данных заказчиков указывает на 30–40% экономии на $2M-class inference spend (i.e., $600-800K/год) при переходе с совместно размещённого обслуживания на дизагрегированное с Dynamo при сохранении постоянного SLA; конкретная цифра $2M→$600-800K является внутренним композитным показателем, а не отдельным опубликованным кейсом — используйте её как ориентир порядка величины, а не как цитируемый источник. Короткие промпты (<512 токенов, короткий вывод) не оправдывают затрат на передачу.

## Learning Objectives

- Объяснить, почему prefill и decode имеют разные оптимальные конфигурации распределения GPU, и количественно оценить потери при совместном размещении (colocation).
- Схематично изобразить дизагрегированную архитектуру: пул prefill, пул decode, передача KV через NIXL, роутер.
- Назвать условие, при котором дизагрегация НЕ окупается (короткие промпты, короткий вывод).
- Различать NVIDIA Dynamo (слой поверх стека) и llm-d (Kubernetes-native) и соотносить каждый с операционным контекстом.

## The Problem

Вы запускаете Llama 3.3 70B на 8 H100. При смешанной нагрузке (длинные промпты + короткий вывод) GPU простаивают во время decode, потому что основные вычисления были потрачены на prefill. При другой нагрузке (короткие промпты + длинный вывод) происходит обратное. Совместное размещение prefill + decode означает избыточное резервирование обоих ресурсов.

Влияние на бюджет: 20-40% времени GPU тратится впустую на неподходящий ресурс. Вы платите за вычислительную мощность H100 для запуска decode, ограниченного памятью, или платите за пропускную способность HBM H100 для запуска prefill, ограниченного вычислениями. Оба варианта — дорогостоящие потери.

Дизагрегация разносит prefill и decode по отдельным пулам, размер которых подобран под узкое место каждого из них. KV-кэш передаётся из пула prefill в пул decode через высокоскоростной интерконнект.

## The Concept

### Почему узкие места различаются

**Prefill** — прогон трансформера по всему входному промпту за один forward-проход. Доминируют матричные умножения; ограничено вычислениями. H100 FP8 даёт ~2000 TFLOPS полезной производительности. Эффективность батчинга хорошая — один forward-проход обрабатывает множество токенов.

**Decode** — генерация по одному токену за итерацию, с чтением всех весов на каждой итерации. Ограничено пропускной способностью памяти. HBM3 даёт ~3 ТБ/с. Эффективность батчинга хорошая только при высокой конкурентности — чтение весов амортизируется по батчу.

Совместное размещение: вы покупаете GPU, оптимизированные под оба сценария. H100 хорош в обоих, но стоит одинаково в любом случае. В масштабе вам нужен пул prefill на H100 / с упором на вычисления; пул decode на H200 / с упором на память, либо с агрессивной квантизацией.

### Архитектура

```
            ┌──────────────┐
  Request → │    Router    │ ───────────────────────┐
            └──────┬───────┘                        │
                   │                                │
                   ▼ (prompt only)                  │
            ┌──────────────┐    KV cache    ┌───────▼──────┐
            │ Prefill pool │ ─── NIXL ────► │ Decode pool  │
            │  (compute)   │                │  (memory)    │
            └──────────────┘                └──────┬───────┘
                                                   │ tokens
                                                   ▼
                                                 Client
```

NIXL — это межузловой транспорт NVIDIA. Использует RDMA/InfiniBand, если доступно, иначе откатывается на TCP. Задержка передачи реальна — обычно 20-80 мс для KV-кэша промпта в 4K токенов на 70B FP8. Именно поэтому короткие промпты не оправдывают дизагрегацию: налог на передачу превышает экономию.

### Dynamo против llm-d

**NVIDIA Dynamo** (анонс GTC 2025, 1.0 GA):
- Располагается поверх vLLM, SGLang, TRT-LLM как оркестратор.
- Planner Profiler измеряет нагрузку, SLA Planner автоматически настраивает соотношения prefill:decode.
- Ядро на Rust, расширяемость на Python.
- Прирост throughput: NVIDIA сообщает о 6x для DeepSeek-R1 MoE на GB200 NVL72 + Dynamo в режиме средней задержки (developer.nvidia.com, 2025-06); сообщения сообщества "до 30x" по полным стекам Blackwell + Dynamo + DeepSeek-R1 не имеют единого первоисточника, и их следует рассматривать как ориентировочные.
- GB300 NVL72 + Dynamo: до 50x throughput на MoE против Hopper согласно странице продукта Dynamo (developer.nvidia.com, без даты).

**llm-d** (Red Hat + AWS, Kubernetes-native):
- Prefill / decode / router — независимые Services Kubernetes.
- Per-role HPA по сигналам глубины очереди (prefill) / загрузки KV (decode).
- `topologyConstraint packDomain: rack` упаковывает клики prefill+decode на одной стойке для высокоскоростной передачи KV.
- llm-d 0.5 (2026): иерархическая выгрузка KV, кэш-ориентированная маршрутизация LoRA, сетевой слой UCCL, scale-to-zero.

Используйте Dynamo, если хотите управляемый оркестратор поверх стека. Используйте llm-d, если нужны Kubernetes-native примитивы и вы привязаны к экосистеме CNCF.

### Экономика

Внутренний композитный показатель (не единичный опубликованный кейс — ориентир порядка величины):

- $2М/год расходов на inference при совместно размещённом обслуживании.
- Переход на дизагрегированную конфигурацию с Dynamo.
- Тот же объём запросов, тот же SLA по P99-задержке.
- Заявленная экономия: $600K–$800K/год (сокращение на 30–40%).
- Без нового оборудования.

Мы синтезируем эту цифру из нескольких раскрытий данных заказчиков, а не из единого цитируемого кейса; ближайшая опубликованная точка данных — у Baseten: 2x более быстрый TTFT / 61% более высокий throughput при KV-маршрутизации Dynamo (baseten.co, 2025-10), и прогноз VAST + CoreWeave о 60–130% большем количестве токенов на доллар при hit rate KV 40–60% (vastdata.com, 2025-12). Экономия достигается за счёт правильного подбора размеров каждого пула; нагрузки, тяжёлые на prefill (RAG с префиксами 8K+), выигрывают больше, чем сбалансированные.

### Когда НЕ стоит дизагрегировать

- Промпты < 512 токенов и вывод < 200 токенов: налог на передачу перекрывает выигрыш.
- Небольшой кластер (< 4 GPU): недостаточно разнообразия пулов.
- Команда не может управлять двумя пулами GPU с масштабированием по ролям: Dynamo помогает, но не тривиально.
- Нет RDMA-фабрики: налог на передачу по TCP тяжелее.

### Роутер интегрируется с Phase 17 · 11

Дизагрегированные роутеры осведомлены о KV-кэше (Phase 17 · 11). Запрос попадает в пул decode, хранящий его префикс — если совпадения нет, запрос проходит путь prefill → decode. Hit rate и дизагрегация взаимно усиливаются — кэш-ориентированный роутер определяет, нужен ли вообще новый prefill.

### MoE на Blackwell — вот где реальные цифры

GB300 NVL72 + Dynamo показывает 50x throughput на MoE по сравнению с базовыми показателями Hopper. Маршрутизация экспертов MoE тяжела по вычислениям на prefill, но тяжела по памяти на decode (кэши экспертов), поэтому дизагрегация даёт двойной выигрыш. Обслуживание передовых моделей 2026 года доминируется архитектурой MoE (DeepSeek-V3, будущие варианты GPT-5).

### Цифры, которые стоит запомнить

Цифры бенчмарков меняются — NVIDIA и стек инференса публикуют обновлённые результаты каждый квартал. Перепроверяйте перед цитированием.

- DeepSeek-R1 на GB200 NVL72 + Dynamo: ~6x throughput относительно базового уровня в режиме средней задержки (developer.nvidia.com, 2025-06); заявления сообщества "до 30x" по полным стекам Blackwell + Dynamo являются ориентировочными агрегатами без единого первоисточника.
- GB300 NVL72 + Dynamo: до 50x throughput на MoE против Hopper (developer.nvidia.com, без даты).
- Ориентир экономии (внутренний композитный показатель, не единичный кейс): $600-800K/year off a $2М годовых расходов при постоянном SLA.
- Порог дизагрегации: промпты >512 токенов + вывод >200 токенов.
- Передача KV через NIXL: 20-80 мс для KV промпта 4K на 70B FP8.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Disaggregated serving | «разделить prefill/decode» | Отдельные пулы GPU для каждой фазы |
| NIXL | «транспорт NVIDIA» | Межузловая передача KV у Dynamo (RDMA/TCP) |
| NVIDIA Dynamo | «оркестратор» | Координатор поверх стека для vLLM/SGLang/TRT-LLM |
| llm-d | «Kubernetes native» | Дизагрегированный стек Red Hat + AWS для K8s |
| Planner Profiler | «автонастройка Dynamo» | Измеряет нагрузку, настраивает соотношения пулов |
| SLA Planner | «политика Dynamo» | Автоматически подбирает соотношение prefill:decode для соблюдения SLO |
| `packDomain: rack` | «топология llm-d» | Упаковывает prefill+decode на одной стойке для быстрой передачи KV |
| UCCL | «унифицированный коллектив» | Сетевой слой llm-d 0.5 для scale-to-zero |
| MoE expert routing | «эксперт на токен» | Паттерн DeepSeek-V3; дизагрегация помогает |
