# Производственный стек инференса — выгрузка KV-кэша и маршрутизация с учётом кэша

> Производственный стек инференса объединяет роутер, движки и систему наблюдаемости в один деплоймент Kubernetes — и рассматривает KV-кэш как ресурс, который может покидать GPU. Выгрузка KV-кэша извлекает его из памяти GPU и переиспользует между запросами и движками (сначала CPU DRAM, затем диск/Ceph). production-stack vLLM — это эталонный деплоймент; LMCache — слой выгрузки. KV Offloading Connector в vLLM 0.11.0 (январь 2026) делает этот процесс асинхронным и подключаемым через Connector API (v0.9.0+). Путь выгрузки обычно скрыт от пути обработки запроса, хотя промахи кэша и повышения (promotions) могут добавлять сквозную задержку. LMCache полезен даже без общих префиксов — когда у GPU заканчиваются KV-слоты, вытесненные запросы можно восстановить из CPU вместо повторного вычисления prefill. Опубликованные бенчмарки на 16x H100 (80 ГБ HBM) на 4 a3-highgpu-4g: когда KV-кэш превышает объём HBM, и нативная выгрузка на CPU, и LMCache существенно улучшают пропускную способность; при малом объёме KV все конфигурации соответствуют базовому уровню с небольшими накладными расходами.

**Type:** Learn
**Languages:** Python (stdlib, игрушечный симулятор вытеснения KV)
**Prerequisites:** Phase 17 · 04 (Serving Engine Internals), Phase 17 · 06 (SGLang/RadixAttention)

## Цели обучения

- Изобразить схемой слои production-stack vLLM: роутер, движки, выгрузка KV, наблюдаемость.
- Объяснить KV Offloading Connector API (v0.9.0+) и то, как асинхронный путь в 0.11.0 скрывает задержку выгрузки.
- Количественно оценить, когда LMCache CPU-DRAM помогает (KV > HBM), а когда добавляет накладные расходы (KV достаточно мал, чтобы поместиться в HBM).
- Выбирать между нативной выгрузкой vLLM на CPU и коннектором LMCache с учётом ограничений деплоймента.

## Проблема

Ваш инференс на vLLM показывает загрузку GPU по HBM на 100% с событиями вытеснения при росте конкурентности. Запросы вытесняются, ставятся обратно в очередь, и один и тот же промпт в 2К токенов повторно прогоняется через prefill четыре раза за минуту. Вычислительные ресурсы GPU тратятся на избыточные prefill; goodput значительно ниже сырой пропускной способности.

Добавление GPU стоит линейно. Добавить HBM невозможно. Но CPU DRAM дёшев — один сокет имеет 512 ГБ+ с латентностью на порядки хуже HBM, но вполне приемлемой для «временно тёплого» KV-кэша.

LMCache извлекает KV-кэш в CPU DRAM, так что вытесненные запросы восстанавливаются быстро, а повторяющиеся префиксы между движками переиспользуют кэш без повторного prefill на каждом движке.

## Концепция

### Production-stack vLLM

`github.com/vllm-project/production-stack` — это эталонный деплоймент Kubernetes:

- **Роутер** — с учётом кэша (Phase 17 · 11). Потребляет события KV.
- **Движки** — воркеры vLLM. Один на GPU или на группу TP/PP.
- **Выгрузка KV-кэша** — деплоймент LMCache или нативный коннектор.
- **Наблюдаемость** — сбор метрик Prometheus, дашборды Grafana, трейсы OTel.
- **Control plane** — service discovery, конфигурация, скользящие обновления.

Поставляется как Helm chart + оператор.

### KV Offloading Connector API (v0.9.0+)

vLLM 0.9.0 ввёл Connector API для подключаемых бэкендов KV-кэша. Ваш движок выгружает блоки в коннектор; коннектор хранит их (RAM, диск, объектное хранилище, LMCache). Когда запросу нужен блок, коннектор загружает его обратно.

vLLM 0.11.0 (январь 2026) добавляет асинхронный путь выгрузки — выгрузка может происходить в фоне, так что в типичном случае движок на ней не блокируется. Сквозная задержка и пропускная способность всё же зависят от формы нагрузки, процента попаданий в KV-кэш и системной нагрузки; в собственных заметках vLLM отмечается, что выгрузка через кастомные ядра может снижать пропускную способность при низком проценте попаданий, а у асинхронного планирования есть известные проблемы взаимодействия со спекулятивным декодированием.

### Нативная выгрузка на CPU против LMCache

**Нативная выгрузка vLLM на CPU**: локальна для движка. Хранит блоки KV в RAM хоста. Быстро реализуется, нулевой сетевой переход. Не работает между движками.

**Коннектор LMCache**: масштаб кластера. Хранит блоки на общем сервере LMCache (CPU DRAM + уровень Ceph/S3). Блоки доступны любому движку. Опубликованы бенчмарки на 16x H100.

Выбирайте нативную выгрузку, когда давление на HBM испытывает один движок. Выбирайте LMCache, когда несколько движков разделяют префиксы (RAG с общими системными промптами, мультиарендность с общими шаблонами).

### Поведение в бенчмарках

Тест на 16x H100 (80 ГБ HBM), распределённых по 4 a3-highgpu-4g:

- Малый объём KV (короткие промпты, низкая конкурентность): все конфигурации соответствуют базовому уровню, LMCache добавляет ~3-5% накладных расходов.
- Умеренный объём: LMCache начинает помогать за счёт переиспользования префиксов между движками.
- KV превышает HBM: и нативная выгрузка на CPU, и LMCache существенно улучшают пропускную способность; у LMCache прирост больше за счёт совместного использования между движками.

### Когда LMCache решает исход дела

- Мультиарендный инференс, где системные промпты общие для арендаторов.
- RAG, где фрагменты документов повторяются между запросами.
- Дообученные варианты (LoRA) на одной базовой модели, где переиспользование KV базовой модели сокращает избыточную работу.
- Нагрузки с интенсивным вытеснением: восстановление из CPU дешевле повторного prefill.

### Когда НЕ включать

- Небольшое давление на HBM — вы платите накладные расходы без выгоды.
- Короткие контексты (<1К токенов) — время передачи больше, чем время повторного prefill.
- Нагрузка с одним арендатором и одним промптом — нечего переиспользовать.

### Интеграция с дизагрегированным инференсом

Дизагрегированный инференс из Phase 17 · 17 в сочетании с LMCache даёт накопительный эффект: KV, передаваемый из пула prefill в пул decode, попадает в LMCache, если не используется; последующие запросы забирают его из LMCache. Роутер с учётом кэша из Phase 17 · 11 может маршрутизировать к движку, чей локальный ИЛИ общий кэш LMCache совпадает.

### Цифры, которые стоит запомнить

- vLLM 0.9.0: вышел Connector API.
- vLLM 0.11.0 (январь 2026): асинхронный путь выгрузки; влияние на сквозную задержку зависит от нагрузки, процента попаданий в KV и системной нагрузки (не абсолютная гарантия).
- Бенчмарк на 16x H100: LMCache помогает, когда объём KV превышает HBM.
- Небольшое давление на HBM: 3-5% накладных расходов без выгоды.

## Ключевые термины

| Термин | Что говорят | Что это на самом деле означает |
|------|----------------|------------------------|
| Production-stack | «эталонный деплоймент» | Helm chart + оператор Kubernetes от vLLM |
| Connector API | «интерфейс KV-бэкенда» | Подключаемый интерфейс KV-хранилища vLLM 0.9.0+ |
| Нативная выгрузка на CPU | «сброс внутри движка» | Хранение KV в RAM хоста того же движка |
| LMCache | «кластерный KV-кэш» | Сервер KV-кэша между движками на CPU DRAM + диск |
| Асинхронность в 0.11.0 | «неблокирующая выгрузка» | Выгрузка скрыта за потоком движка |
| Preemption (вытеснение) | «вытеснение для освобождения места» | Перетасовка KV-кэша при заполнении HBM |
| Переиспользование префикса | «тот же системный промпт» | Несколько запросов разделяют начало; попадание в кэш |
| Уровень Ceph | «дисковый уровень» | Надёжное хранилище ниже DRAM в иерархии кэша |
