# Многорегиональный сервинг LLM и локальность KV-кэша

> Циклический (round-robin) балансировщик нагрузки активно вредит кэшированному инференсу LLM. Запрос, не попавший на узел, хранящий его префикс, платит полную стоимость prefill — около 800 мс на P50 для длинного промпта против ~80 мс при попадании в кэш. В 2026 году продакшн-паттерн — это маршрутизатор с учётом кэша (vLLM Router на Rust, llm-d router), который потребляет события KV-кэша и маршрутизирует по совпадению хэша префикса. Недавние исследования (GORGO) делают межрегиональную сетевую задержку явным членом в целевой функции маршрутизации. Коммерческие предложения «межрегионального инференса» (Bedrock cross-region inference, GKE multi-cluster gateways) трактуют инференс как чёрный ящик — они обеспечивают доступность, а не TTFT. JPMorgan и Mayo Clinic выполняли отказоустойчивый переход (failover) для us-east-1 в ноябре 2024 года за ~22 минуты. Реальность аварийного восстановления (DR): 32% сбоев DR для LLM происходят из-за того, что команды резервировали веса, но забыли файлы токенизатора или конфигурации квантования.

**Type:** Learn

## Цели обучения

- Объяснить, почему циклический балансировщик нагрузки ломает кэшированный инференс, и количественно оценить штраф по TTFT.
- Изобразить схему маршрутизатора с учётом кэша: входы (события KV-кэша), алгоритм (совпадение хэша префикса), разрешение ничьи (загрузка GPU).
- Назвать причину 32% сбоев DR для LLM (отсутствие файлов токенизатора / конфигураций квантования) и сформулировать чек-лист DR из трёх файлов.
- Отличать коммерческие межрегиональные предложения (Bedrock CRI, GKE Multi-Cluster Gateway) от маршрутизации с учётом KV-кэша.

## Проблема

Ваш сервис работает в us-east-1, us-west-2 и eu-west-1. Вы ставите перед ним ALB с циклической маршрутизацией. Коэффициент попадания в префиксный кэш в продакшене падает до 8%. P50 TTFT утраивается. Логи vLLM показывают, что каждый запрос платит полную стоимость prefill.

Циклическая маршрутизация оптимальна для stateless-сервисов. Инференс LLM по своей природе stateful — KV-кэш кодирует всё, что модель уже видела. Маршрутизация вслепую означает маршрутизацию не в тот кэш.

Отдельно у вашей команды есть план DR. Вы резервируете веса модели в S3 в другом регионе. Происходит сбой региона; вы пытаетесь выполнить failover; реплика отказывается запускаться. Вы забыли, что tokenizer.json, конфигурация квантования и конфигурация масштабирования RoPE находились в отдельном бакете, который вы не синхронизировали.

Многорегиональный сервинг LLM — это проблема кэша, проблема маршрутизации и проблема гигиены DR, а не проблема балансировщика нагрузки.

## Концепция

### Маршрутизация с учётом кэша

Запрос приходит с промптом. Маршрутизатор хэширует префикс (скажем, первые 512 токенов); он спрашивает каждую реплику: «у тебя закэширован этот префикс?». Реплики публикуют события KV-кэша в канал pub/sub по мере выделения и вытеснения блоков. Маршрутизатор выбирает реплику с совпадением, при отсутствии совпадения переходит к разрешению ничьи на основе загрузки GPU.

**vLLM Router** (Rust, production-stack 2026 года): подписывается на события `kv.cache.block_added`, поддерживает индекс хэш-префикс → реплика, маршрутизирует с поиском O(1). При отсутствии совпадения переходит к реплике с наименьшей глубиной очереди.

**llm-d router**: тот же паттерн, нативно для Kubernetes. Публикует события через API ControlPlane.

**SGLang RadixAttention** (Phase 17 · 06) — это внутриреплический эквивалент. Межреплическая маршрутизация строго находится выше по стеку.

### Цифры

TTFT P50 на промпте в 2К токенов, Llama 3.3 70B FP8, H100:
- Попадание в кэш (та же реплика, префикс резидентен): ~80 мс.
- Промах кэша (холодный prefill): ~800 мс.

Разрыв в 10 раз. Если ваш маршрутизатор попадает в 60-80% префиксного кэша среди реплик, вы приближаетесь к производительности одной реплики при мощности N реплик. Если попадание — 10%, вы приближаетесь к наивному масштабированию.

### У межрегиональной маршрутизации есть новое ограничение — сетевая задержка

Межрегиональный RTT:
- us-east-1 ↔ us-west-2: ~65 мс.
- us-east-1 ↔ eu-west-1: ~75 мс.
- us-east-1 ↔ ap-southeast-1: ~220 мс.

Если маршрутизация переносит запрос из us-east-1 к горячему префиксу в ap-southeast-1, экономия на prefill (800 → 80 мс) теряется на фоне 440 мс кругового пробега (round-trip). GORGO (исследование 2026 года) делает это явным — минимизировать `prefill_time + network_latency` совместно, а не только prefill по отдельности. Часто правильный ответ — держать маршрутизацию региональной, кроме случаев массивных многомегабайтных префиксов, где prefill доминирует.

### Коммерческий «межрегиональный инференс» здесь не помогает

AWS Bedrock cross-region inference автоматически маршрутизирует запросы в другие регионы при нехватке мощности. Он оптимизирует доступность, а не TTFT, и трактует инференс как чёрный ящик. GKE Multi-Cluster Gateway аналогичен — это failover на уровне сервиса, без осведомлённости о KV-кэше.

Вам по-прежнему нужен маршрутизатор с учётом кэша на уровне приложения, даже при использовании этих решений. Они обрабатывают случай «us-east-1 горит». Маршрутизация с учётом кэша обрабатывает случай TTFT.

### Гигиена DR — проблема 32% отсутствующих файлов

Широко цитируемая статистика 2026 года: 32% сбоев DR для LLM происходят из-за того, что команды резервировали веса, но забыли:

- `tokenizer.json` или `tokenizer.model`
- Конфигурации квантования (`quantize_config.json`, масштабы AWQ, нулевые точки GPTQ)
- Конфигурации, специфичные для модели (масштабирование RoPE, маски внимания, шаблоны чата)
- Конфигурацию движка (`vllm_config.yaml`, значения семплирования по умолчанию, манифесты адаптеров LoRA)

Решение — минимальный манифест DR из трёх файлов:

1. Все файлы в репозитории модели HF (веса + конфигурации + токенизатор).
2. Конфигурация сервинга, специфичная для движка.
3. Манифест развёртывания (K8s YAML, Dockerfile, lock-файл зависимостей).

Плюс: проводите учения по DR ежеквартально. Учения JPMorgan для us-east-1 уложились в 22 минуты восстановления в ноябре 2024 года только потому, что план действий был отрепетирован.

### Резидентность данных — ортогональное измерение

PHI европейских клиентов не может покидать ЕС. Если ваш маршрутизатор с учётом кэша отправляет запрос, пришедший из Парижа, в us-east-1 ради совпадения префикса, вы нарушили GDPR независимо от выигрыша в TTFT. Разделяйте маршрутизаторы по границам резидентности до оптимизации под кэш.

### Цифры, которые стоит запомнить

- Разрыв TTFT между попаданием и промахом кэша: ~10x (80 мс против 800 мс на промпте в 2К).
- Межрегиональный RTT US-EU: ~75 мс.
- Сбои DR: 32% — отсутствие конфигураций токенизатора/квантования.
- Failover JPMorgan для us-east-1 в ноябре 2024: 22 минуты (SLA 30 минут).

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Маршрутизация с учётом кэша | «умный LB» | Маршрутизация по совпадению хэша префикса к реплике, хранящей KV-кэш |
| События KV-кэша | «pub-sub кэша» | Реплики публикуют добавление/вытеснение блоков; маршрутизатор индексирует |
| Хэш префикса | «ключ кэша» | Хэш первых N токенов, используемый как ключ поиска маршрутизатора |
| GORGO | «исследование межрегиональной маршрутизации» | arXiv 2602.11688; сетевая задержка как явный член |
| Межрегиональный инференс | «Bedrock CRI» | Продукт AWS; failover доступности, без осведомлённости о TTFT |
| Манифест DR | «список резервных копий» | Все файлы, необходимые для восстановления — не только веса |
| Резидентность данных | «граница GDPR» | Юридическое ограничение на то, какой регион видит данные пользователя |
| RTT | «время кругового пробега» | Сетевая задержка; 75 мс US-EU, 220 мс US-APAC |
| LLM-aware LB | «LB с учётом попаданий в кэш» | Маршрутизатор с учётом кэша как категория продукта |
