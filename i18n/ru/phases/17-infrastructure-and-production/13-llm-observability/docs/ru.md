# Выбор стека для observability LLM

> Рынок observability в 2026 году делится на две категории. Платформы разработки (LangSmith, Langfuse, Comet Opik) объединяют мониторинг с evals, управлением промптами, воспроизведением сессий. Инструменты шлюза/инструментирования (Helicone, SigNoz, OpenLLMetry, Phoenix) фокусируются на телеметрии. Langfuse — ядро под лицензией MIT с сильным балансом OSS (50K событий/месяц бесплатно в облаке). Phoenix — нативен для OpenTelemetry под лицензией Elastic License 2.0 — отлично подходит для визуализации дрейфа/RAG, но не является постоянным продакшен-бэкендом. Arize AX использует интеграцию с нулевым копированием Iceberg/Parquet, заявляя о цене в 100 раз ниже монолитного observability. LangSmith лидирует для LangChain/LangGraph, $39/пользователь/мес, self-host только в Enterprise. Helicone — на базе прокси, настройка за 15-30 минут, 100K запросов/мес бесплатно, но меньше глубины в трассировке агентов. Распространённый продакшен-паттерн: шлюз (Helicone/Portkey) + платформа evals (Phoenix/TruLens), склеенные через OpenTelemetry.

**Type:** Learn
**Languages:** Python (stdlib, игрушечный симулятор сэмплирования трасс)
**Prerequisites:** Phase 17 · 08 (Inference Metrics), Phase 14 (Agent Engineering)
**Time:** ~60 минут

## Цели обучения

- Отличать платформы разработки (объединяющие evals + промпты + сессии) от инструментов шлюза/телеметрии (только трассы + метрики).
- Сопоставить шесть основных инструментов (Langfuse, LangSmith, Phoenix, Arize AX, Helicone, Opik) с их лицензированием, ценой и оптимальными сценариями использования.
- Объяснить паттерн склейки через OpenTelemetry, позволяющий сочетать инструмент-шлюз с отдельной платформой evals.
- Назвать ключевой ценовой дифференциатор 2026 года (подход Arize AX с нулевым копированием против монолитного ingest) и сформулировать примерный множитель в 100 раз.

## Проблема

Вы выпустили LLM-функцию. Она работает. У вас нет видимости в отказы промптов, зацикливания инструментов, регрессии задержек, скачки стоимости или коэффициент попаданий в prompt-кэш. Вы гуглите "LLM observability" и находите восемь инструментов, каждый из которых утверждает, что решает ту же проблему по трём разным ценовым категориям.

Они не решают одну и ту же проблему. LangSmith отвечает на вопрос "почему этот прогон LangGraph завершился неудачей?" Phoenix отвечает на вопрос "дрейфует ли мой RAG-пайплайн?" Helicone отвечает на вопрос "какое приложение сжигает токены?" Langfuse отвечает на вопрос "могу ли я self-host всё целиком?" Разные инструменты, разная аудитория.

Выбор включает четыре оси: стек (LangChain? сырой SDK? мульти-вендорный?), допустимость лицензии (только MIT? Elastic ОК? коммерческая устраивает?), бюджет (бесплатный тариф? $100/mo? $1000/мес?), и self-host (обязательно? желательно? никогда?).

## Концепция

### Две категории

**Платформы разработки** объединяют observability с evals, управлением промптами, версионированием датасетов, воспроизведением сессий. Вы запускаете эксперименты, смотрите, какой промпт сработал, проводите регрессионное тестирование нового промпта на датасете против предыдущих победителей. LangSmith, Langfuse, Comet Opik.

**Инструменты шлюза/телеметрии** инструментируют вызовы инференса — промпт, ответ, токены, задержку, модель, стоимость. Helicone, SigNoz, OpenLLMetry, Phoenix. Минималистичны. Могут сочетаться с отдельным инструментом evals через OpenTelemetry.

### Langfuse — баланс OSS

- Ядро под лицензией Apache / MIT; self-host через Docker.
- Бесплатный облачный тариф: 50K событий/месяц. Платный: $29/мес для команды.
- Evals, управление промптами, трассы, датасеты. Разумное покрытие всех четырёх функций платформы разработки.
- Оптимальный сценарий: вам нужны функции уровня LangSmith, но необходим self-host или OSS-лицензия.

### Phoenix (Arize) — ориентирован на телеметрию, нативен для OpenTelemetry

- Лицензия Elastic License 2.0; self-host тривиален.
- Отлично подходит для визуализации RAG и дрейфа. Диаграммы рассеяния в embedding-пространстве поставляются как основная функция.
- Не предназначен как постоянный продакшен-бэкенд — преимущественно observability на этапе разработки.
- Оптимальный сценарий: разработка RAG-пайплайна, отладка дрейфа, в паре с отдельным шлюзом для продакшена.

### Arize AX — ставка на масштаб

- Коммерческий. Интеграция с нулевым копированием данных через Iceberg/Parquet.
- Заявляет цену примерно в 100 раз ниже монолитного observability (уровня Datadog) на масштабе. Математика: вы храните трассы в собственном Parquet на S3; Arize читает напрямую.
- Оптимальный сценарий: >10М трасс/день, существующий дата-лейк, нужны специфичные для LLM дашборды без ценника Datadog.

### LangSmith — приоритет LangChain/LangGraph

- Коммерческий, $39/пользователь/месяц. Self-host только в Enterprise.
- Лучший в своём классе для стеков LangChain и LangGraph. Если вы не используете ни то, ни другое, менее привлекателен.
- Оптимальный сценарий: команда, приверженная LangChain, готова платить.

### Helicone — минимально жизнеспособный вариант на базе прокси

- Настройка за 15-30 минут путём замены вашего `OPENAI_API_BASE` на прокси Helicone.
- Лицензия MIT; 100K запросов/мес бесплатно, платный от $20/мес.
- Включает failover, кэширование, ограничения частоты запросов — работает и как шлюз.
- Меньше глубины в трассировке агентов / многошаговых процессов.
- Оптимальный сценарий: быстрый старт, приложение на одном стеке, нужны шлюз + observability в одном флаконе.

### Opik (Comet) — платформа разработки с открытым кодом

- Apache 2.0, полностью OSS.
- Набор функций, похожий на Langfuse, с наследием Comet.
- Оптимальный сценарий: ML-команды, уже использующие Comet, хотят LLM observability в той же панели.

### SigNoz — полноценный APM, ориентированный на OpenTelemetry

- Apache 2.0. Обрабатывает общий APM плюс LLM через OpenTelemetry.
- Оптимальный сценарий: единая observability по сервисам и LLM-вызовам.

### Склейка: OpenTelemetry + семантические соглашения GenAI

OpenTelemetry опубликовал семантические соглашения GenAI в конце 2025 года (`gen_ai.system`, `gen_ai.request.model`, `gen_ai.usage.input_tokens`). Инструменты, потребляющие OTel, могут взаимодействовать между собой. Формирующийся продакшен-паттерн:

1. Отправлять OTel с соглашениями GenAI из каждого LLM-вызова.
2. Направлять в шлюз (Helicone / Portkey) для повседневной работы.
3. Дублировать отправку в платформу evals (Phoenix / Langfuse) для отслеживания регрессий.
4. Архивировать в дата-лейке (Iceberg) для долгосрочного анализа через Arize AX или DuckDB.

### Ловушка: инструментирование не на том уровне

Инструментирование внутри вашего агентского фреймворка (например, добавление трасс LangSmith) привязывает вас к этому фреймворку. Инструментирование на уровне HTTP/OpenAI-SDK (через OpenLLMetry или ваш шлюз) переносимо.

### Сэмплирование — нельзя хранить всё

При >1М запросов/день полное хранение трасс стоит дороже, чем сами вызовы LLM. Сэмплируйте по правилам: 100% ошибок, 100% высокой стоимости, 5% успешных. Агрегаты держите всегда; сырые данные — только для длинного хвоста.

### Числа, которые стоит запомнить

- Бесплатный облачный Langfuse: 50K событий/месяц.
- LangSmith: $39/пользователь/месяц.
- Бесплатный Helicone: 100K запросов/месяц.
- Заявление Arize AX: ~в 100 раз дешевле монолитного решения на масштабе.
- Семантические соглашения OpenTelemetry GenAI: публикация в 2025, широкое распространение в 2026.

## Применить

`code/main.py` симулирует день с 1М трасс при разных стратегиях хранения (100% ingest, сэмплирование, сэмплирование + ошибки). Отчёт показывает стоимость хранения и что теряется в каждом случае.

## Упражнения

1. Ваша команда на LangChain хочет OSS self-hosted observability. Выберите Langfuse или Opik и обоснуйте выбор.
2. При 5М трасс/день с ценой Datadog в $150K/месяц рассчитайте точку безубыточности для Arize AX.
3. Спроектируйте набор атрибутов OpenTelemetry GenAI, который руководство вашей организации должно требовать для каждого LLM-вызова.
4. Обоснуйте, достаточно ли одного Phoenix для продакшена. Когда его недостаточно?
5. Helicone даёт 20 мс накладных расходов прокси. При P99 TTFT 300 мс, это приемлемо? А если SLA составляет 100 мс?
