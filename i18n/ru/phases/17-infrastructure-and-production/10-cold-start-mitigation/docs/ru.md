# Снижение времени холодного старта для бессерверных LLM

> Образ модели весом 20 ГБ переходит из холодного состояния в рабочее за 5-10 минут (7B) или более 20 минут (70B). В по-настоящему бессерверном мире это не разогрев — это отказ в обслуживании. Меры смягчения работают на пяти уровнях: предзагруженные образы узлов (Bottlerocket на AWS, архитектура с двумя томами), потоковая загрузка моделей (NVIDIA Run:ai Model Streamer, встроен в vLLM), снимки памяти GPU (чекпоинты Modal, до 10x ускорение перезапуска), прогретые пулы (`min_workers=1`), многоуровневая загрузка (конвейер ServerlessLLM NVMe→DRAM→HBM, снижение задержки в 10-200 раз) и живая миграция, которая переносит входные токены (КБ), а не KV-кеш (ГБ). Modal заявляет холодный старт 2-4с как нижнюю границу; Baseten — 5-10с по умолчанию, менее секунды с предварительным прогревом. Этот урок научит вас измерять, планировать бюджет и комбинировать все пять уровней.

**Type:** Обучение
**Languages:** Python (стандартная библиотека, упрощённый симулятор пути холодного старта)
**Prerequisites:** Этап 17 · 02 (Экономика платформы инференса), Этап 17 · 03 (Автомасштабирование GPU)
**Time:** ~60 минут

## Цели обучения

- Перечислить пять уровней смягчения холодного старта и назвать по одному инструменту или паттерну для каждого уровня.
- Рассчитать общее время холодного старта как сумму (выделение узла) + (загрузка весов) + (загрузка весов в HBM) + (инициализация движка) для модели 70B.
- Объяснить, почему живая миграция переносит входные токены (КБ), а не KV-кеш (ГБ), и в чём заключается штраф (пересчёт).
- Назвать компромисс прогретых пулов (платить за простаивающий GPU или мириться с хвостом холодного старта) и порог SLA, при котором `min_workers > 0` становится обязательным.

## Проблема

Ваш бессерверный LLM-эндпоинт за ночь масштабируется до нуля. В 8 утра происходит всплеск трафика. Первый запрос ждёт, пока:

1. Karpenter выделяет узел с GPU: 45-60с.
2. Контейнер скачивает образ весом 30 ГБ с весами: 120-300с.
3. Движок загружает веса в HBM: 45-120с в зависимости от размера модели и скорости хранилища.
4. vLLM или TRT-LLM инициализирует CUDA-графы, пул KV-кеша, токенизатор: 10-30с.

Итого: 220-510с (примерно 3-8 минут) до возврата первого токена. Ваш SLA — 2с. Вы разворачиваете прогретый пул (`min_workers=1`), и проблема, кажется, исчезает — но теперь вы платите за один простаивающий GPU круглосуточно. Если ваш сервис содержит 5 продуктов, каждый с одной прогретой репликой, это 5 × 24 × 30 = 3600 GPU-часов в месяц независимо от того, вызвал ли сервис хоть один пользователь.

Смягчение холодного старта — это способ сохранить экономику бессерверных вычислений, приближаясь по задержке к режиму постоянной готовности.

## Концепция

### Уровень 1 — предзагруженные образы узлов (Bottlerocket)

На AWS архитектура Bottlerocket с двумя томами разделяет ОС и данные. Сделайте снимок тома данных с предварительно загруженным образом контейнера; укажите ID снимка в вашем `EC2NodeClass`. Новые узлы загружаются с уже имеющимися на локальном NVMe весами — шаг 2 и часть шага 3 исчезают. Нативно работает с Karpenter. Типичная экономия: 2-4 минуты на каждый холодный старт для крупных моделей.

Эквивалент на GCP: пользовательские образы VM с предварительно встроенными слоями контейнера. На Azure: снимки управляемых дисков с тем же паттерном.

### Уровень 2 — потоковая загрузка моделей (Run:ai Model Streamer)

Вместо загрузки всего файла перед ответом на первый запрос веса передаются в память GPU послойно, и обработка начинается, как только в памяти оказывается первый блок трансформера. NVIDIA Run:ai Model Streamer встроен нативно в vLLM 2026. Работает с S3, GCS и локальным NVMe. Сокращает время загрузки весов примерно вдвое для крупных моделей за счёт совмещения ввода-вывода с настройкой вычислений.

### Уровень 3 — снимки памяти GPU (Modal)

Modal создаёт чекпоинт состояния GPU (веса, CUDA-графы, область KV-кеша) после первой загрузки. Последующие перезапуски десериализуются напрямую в HBM — в 10 раз быстрее повторной инициализации. Это ближе всего к идее «запустить прогретый GPU за 2 секунды». Компромисс: снимки привязаны к конкретной топологии GPU, поэтому если Karpenter перемещает вас на другую модель SKU, потребуется новый чекпоинт.

### Уровень 4 — прогретые пулы (min_workers=1)

Простейшее решение: держать одну реплику постоянно готовой. Стоимость — почасовая ставка одного GPU круглосуточно. Арифметика беспощадна для маленьких моделей (вы платите $0.85-$1.50/час, чтобы избежать холодного старта в 30с) и щадяща для крупных (платите $4/час, чтобы избежать 5-минутного холодного старта). Порог SLA, при котором прогретые пулы становятся обязательными: обычно TTFT P99 < 60с для модели 70B+.

### Уровень 5 — многоуровневая загрузка (ServerlessLLM)

ServerlessLLM рассматривает хранилище как иерархию: NVMe (быстро, но большой объём), DRAM (средне по обоим параметрам), HBM (маленький объём, но мгновенный доступ). Веса предварительно загружаются в DRAM; по требованию загружаются в HBM. В статье заявлено снижение задержки в 10-200 раз при холодной загрузке по сравнению с наивным путём диск→HBM. Промышленное внедрение пока на раннем этапе, но интеграции с vLLM существуют.

### Уровень 6 — живая миграция (дополнительный паттерн)

Когда узел становится недоступным (вытеснение спот-инстанса, дренаж узла), традиционный паттерн — холодный старт другой реплики и дренаж очереди запросов. Живая миграция переносит входные токены (килобайты) на узел назначения, где модель уже загружена, и пересчитывает KV-кеш на этом узле. Пересчёт дешевле передачи гигабайтов KV-кеша по сети. Применимо к дезагрегированным развёртываниям.

### Математика прогретых пулов

Для сервиса с SLA P99 TTFT 2с вопрос не в том, «нужен ли прогретый пул», а в том, «сколько прогретых реплик нужно и каким путям они полагаются».

- Высокоценные интерактивные пути (живой чат, голосовой агент): `min_workers=1-2`.
- Фоновые пакетные пути (ночная классификация): допустимо масштабирование до нуля, холодный старт 5-10 минут приемлем.
- Премиум-уровень: `min_workers` на каждого клиента с выделенной мощностью.

### Измеряйте перед оптимизацией

Анатомия холодного старта для модели 70B на свежем узле (иллюстративно):

| Фаза | Время | Смягчение |
|-------|------|-----------|
| Выделение узла | 50с | Bottlerocket + предзагруженный образ, прогретый пул |
| Скачивание образа | 180с | Предзагруженный том данных (исключается) |
| Загрузка весов в HBM | 75с | Потоковая загрузка (вдвое меньше); снимок GPU (исключается) |
| Инициализация движка | 20с | Постоянный кеш CUDA-графов |
| Первый прямой проход | 3с | Минимальная неустранимая задержка |
| **Итого холодный старт** | **328с** | |
| **Итого со смягчением** | **~15с** | снижение в 22 раза |

### Цифры, которые стоит запомнить

- Холодный старт Modal: 2-4с (со снимками GPU).
- Холодный старт Baseten по умолчанию: 5-10с; менее секунды с предварительным прогревом.
- Холодный старт модели 70B без оптимизации: 3-8 минут.
- Run:ai Model Streamer: ~2x ускорение загрузки весов.
- Многоуровневая загрузка ServerlessLLM: снижение задержки в 10-200 раз (данные из статьи).

4. Ваш бессерверный провайдер предлагает снимки GPU (Modal), а ваша команда отказывается, потому что «снимки могут утечь персональные данные». Приведите аргументы обеих сторон — каков реальный риск и какая мера смягчения (эфемерные снимки, шифрование, изоляция пространств имён)?

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Холодный старт | «большая пауза» | Время от запроса до первого токена на свежей реплике |
| Прогретый пул | «минимум постоянной готовности» | `min_workers >= 1` для поддержания хотя бы одной готовой реплики |
| Предзагруженный образ | «запечённый AMI» | Образ узла с заранее имеющимися весами контейнера |
| Bottlerocket | «ОС узла AWS» | Оптимизированная для контейнеров ОС AWS с поддержкой снимков с двумя томами |
| Потоковая загрузка моделей | «потоковая загрузка» | Совмещение ввода-вывода весов с настройкой вычислений |
| Снимок GPU | «чекпоинт в HBM» | Сериализация состояния GPU после загрузки; десериализация при перезапуске |
| Многоуровневая загрузка | «NVMe + DRAM + HBM» | Иерархия уровней хранения; загрузка по требованию |
| Живая миграция | «перенос токенов» | Передача входных данных (КБ), пересчёт KV на узле назначения |
| `min_workers` | «прогретые реплики» | Минимальное количество постоянно активных экземпляров в бессерверной среде |
| Масштабирование до нуля | «полностью бессерверный режим» | Отсутствие затрат при простое; принятие полного «налога» холодного старта |
