# Нагрузочное тестирование LLM API — почему k6 и Locust врут

> Традиционные инструменты нагрузочного тестирования не проектировались для потоковых ответов, переменной длины вывода, метрик на уровне токенов или насыщения GPU. В две ловушки попадает большинство команд. Ловушка GIL: измерение на уровне токенов в Locust выполняет токенизацию под Python GIL, которая конкурирует с генерацией запросов при высокой конкурентности; накопившаяся очередь токенизации затем раздувает отчётную межтокенную задержку — узким местом становится ваш клиент, а не сервер. Ловушка единообразия промптов: идентичные промпты в цикле тестируют одну точку распределения токенов; реальный трафик имеет переменную длину и разнообразные совпадения префиксов. LLMPerf решает это с помощью `--mean-input-tokens` + `--stddev-input-tokens`. Карта инструментов на 2026 год: специализированные для LLM (GenAI-Perf, LLMPerf, LLM-Locust, guidellm) — для точности на уровне токенов; **k6 v2026.1.0** + **k6 Operator 1.0 GA (сентябрь 2025)** — учитывает потоковую передачу, распределённое тестирование нативно для Kubernetes через CRD TestRun/PrivateLoadZone, лучше всего подходит для шлюзов CI/CD; Vegeta — для насыщения с постоянной скоростью на Go; Locust 2.43.3 — только с расширением LLM-Locust для потоковой передачи. Шаблоны нагрузки: устойчивое состояние, нарастание, всплеск (тест автомасштабирования), длительный прогон (утечки памяти).

**Type:** Build
**Languages:** Python (stdlib, игрушечный генератор реалистичных промптов + сборщик задержек)
**Prerequisites:** Phase 17 · 08 (Inference Metrics), Phase 17 · 03 (GPU Autoscaling)

## Цели обучения

- Объяснить два антипаттерна (ловушка GIL, ловушка единообразия промптов), из-за которых универсальные инструменты нагрузочного тестирования врут для LLM API.
- Выбрать инструмент под конкретную задачу: LLMPerf (прогон бенчмарка), k6 + расширение для потоковой передачи (шлюз CI), guidellm (синтетика большого масштаба), GenAI-Perf (эталон от NVIDIA).
- Спроектировать четыре шаблона нагрузки (устойчивое состояние, нарастание, всплеск, длительный прогон) и назвать режим отказа, который ловит каждый из них.
- Построить реалистичное распределение промптов, используя среднее + стандартное отклонение числа входных токенов, а не фиксированную длину.

## Проблема

Вы протестировали ваш LLM-эндпоинт с помощью k6 на 500 одновременных пользователей. Он выдержал. Вы выкатили в продакшн. В продакшне при 200 реальных пользователях сервис рухнул — P99 TTFT взлетел, GPU упёрлись в потолок.

Произошли две вещи. Во-первых, k6 отправил 500 идентичных промптов — объединение запросов (request-coalescing) и кеширование префиксов создали видимость обработки 500 одновременных декодирований, тогда как фактически обрабатывалось одно. Во-вторых, k6 не отслеживает межтокенную задержку в потоковых ответах так, как её воспринимает глаз: он видит одно HTTP-соединение, а не 500 токенов, приходящих с разными интервалами.

Нагрузочное тестирование для LLM — отдельная дисциплина.

## Концепция

### Ловушка GIL (Locust)

Locust использует Python и выполняет токенизацию на стороне клиента под GIL. При высокой конкурентности токенизатор встаёт в очередь позади генерации запросов. Отчётная межтокенная задержка включает накопившуюся задержку клиентской токенизации. Вы думаете, что медленный сервер; на самом деле — тестовый стенд.

Исправление: расширение LLM-Locust переносит токенизацию в отдельные процессы, либо используйте стенд на компилируемом языке (k6, LLMPerf с tokenizers.rs).

### Ловушка единообразия промптов

Все известные инструменты нагрузочного тестирования позволяют настроить один промпт. В тесте из 10 000 итераций один и тот же промпт отправляется каждый раз. Сервер видит один и тот же префикс каждый раз — доля попаданий в кеш префиксов приближается к 100%, пропускная способность выглядит отлично.

Исправление: выборка из распределения промптов. LLMPerf использует `--mean-input-tokens 500 --stddev-input-tokens 150` — разнообразные длины, разнообразное содержимое.

### Четыре шаблона нагрузки

1. **Устойчивое состояние (Steady-state)** — постоянный RPS в течение 30-60 минут. Ловит: регрессии базовой производительности.
2. **Нарастание (Ramp)** — линейное увеличение RPS от 0 до целевого значения за 15 минут. Ловит: точку пробоя ёмкости, аномалии разогрева.
3. **Всплеск (Spike)** — внезапное увеличение RPS в 3-10 раз на 2 минуты, затем возврат. Ловит: задержку автомасштабирования, насыщение очереди, влияние холодного старта.
4. **Длительный прогон (Soak)** — устойчивое состояние в течение 4-8 часов. Ловит: утечки памяти, дрейф пула соединений, переполнение системы наблюдаемости.

### Карта инструментов на 2026 год

**LLMPerf** (Anyscale) — Python, но токенизация реализована на Rust. Промпты со средним/стандартным отклонением. Учитывает потоковую передачу. Лучший выбор по умолчанию для прогонов производительности.

**NVIDIA GenAI-Perf** — эталонный инструмент от NVIDIA. Использует клиент Triton; всесторонний охват метрик. Учтите: его ITL не включает TTFT; в LLMPerf — включает. Два инструмента дают разный TPOT для одного и того же сервера.

**LLM-Locust** (TrueFoundry) — расширение Locust, исправляющее ловушку GIL. Привычный DSL Locust + метрики потоковой передачи.

**guidellm** — синтетический бенчмаркинг большого масштаба.

**k6 v2026.1.0** + **k6 Operator 1.0 GA (сентябрь 2025)**:
- Сам k6 (Go, компилируемый, без GIL) получил метрики с учётом потоковой передачи.
- k6 Operator использует CRD TestRun / PrivateLoadZone для нативного распределённого тестирования в Kubernetes.
- Лучше всего подходит для шлюзов CI/CD и тестирования SLA.

**Vegeta** — Go, проще, чем k6. Насыщение HTTP с постоянной скоростью. Не учитывает специфику LLM, но хорош для тестирования шлюзов/ограничений скорости.

**Locust 2.43.3 "из коробки"** — страдает от ловушки GIL для LLM. Только с расширением LLM-Locust.

### Шлюз SLA в CI

Запускайте k6 на PR со следующими параметрами:

- 30-50 итераций на каждый базовый уровень RPS.
- Шлюз: P50/P95 TTFT, доля 5xx < 5%, TPOT ниже порога.
- Прерывать сборку при нарушении.

### Реалистичное распределение промптов

Стройте на основе реальных образцов трафика (если они у вас есть) или опубликованных распределений (например, промпты ShareGPT для чата, HumanEval для кода). Передавайте среднее + стандартное отклонение в LLMPerf. Любой ценой избегайте цикла с одним промптом.
