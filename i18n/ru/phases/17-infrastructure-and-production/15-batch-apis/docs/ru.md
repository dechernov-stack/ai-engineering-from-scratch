# Batch API — скидка 50% как отраслевой стандарт

> Каждый крупный провайдер предлагает асинхронный batch API со скидкой 50% и сроком выполнения около 24 часов. OpenAI, Anthropic, Google и большинство инференс-платформ (Fireworks batch tier, Together batch) реализуют один и тот же паттерн. Если сложить batch с кэшированием промптов, стоимость ночных пайплайнов падает примерно до 10% от синхронной цены без кэша. Правило предельно простое: если задача не интерактивна — она должна выполняться через batch. Пайплайны генерации контента, классификация документов, извлечение данных, генерация отчётов, массовая разметка, тегирование каталогов — всё, что допускает задержку в 24 часа, это деньги, оставленные на столе, пока задача не переведена на batch. Производственный паттерн 2026 года — распределять каждую новую LLM-нагрузку по трём дорожкам: интерактивная (синхронная с кэшированием), полу-интерактивная (асинхронная очередь с фолбэком), batch (ночная обработка, с накоплением кэшированного ввода). Нагрузки, которые притворяются интерактивными, но на самом деле допускают задержку в минуты, тратят впустую больше всего денег.

## Проблема

Ваша команда поддерживает ночной пайплайн генерации отчётов. 50 000 документов, каждый нужно суммировать, кластеризовать резюме, составить итоговую сводку для руководства. При синхронном выполнении это занимает 4 часа и стоит $2000 за ночь. Вы узнаёте о batch API.

Batch даёт скидку 50%. Вы также включаете кэширование промптов для системного промпта (общего для всех 50 тысяч вызовов). В сумме счёт падает до $180 за ночь — около 9% от базовой стоимости. Тот же пайплайн, три изменения в конфигурации.

Batch — самый дешёвый рычаг в наборе инструментов оптимизации стоимости LLM, который почти никто не использует. Причина в основном организационная: команды думают «реальное время», хотя по факту SLA звучит как «к утру». Этот урок о том, как не оставлять 90% счёта на столе.

## Концепция

### Три batch API

**OpenAI Batch API**: загрузка JSONL-файла со списком запросов. Обещанный срок выполнения — 24 часа (на практике обычно ~2-8 часов). Скидка 50% на входные и выходные токены. Эндпоинт `/v1/batches`. Кэш-совместимый ввод дополнительно получает ценообразование кэшированного ввода.

**Anthropic Message Batches**: загрузка JSONL. Срок выполнения 24 часа. Скидка 50%. Поддерживает `cache_control` — записи в кэш происходят явно, чтения случаются автоматически в рамках batch-обработки.

**Google Vertex AI Batch Prediction**: ввод через BigQuery или GCS. Аналогичная скидка 50% для Gemini. Интегрируется с пайплайнами Vertex.

### Семантика: асинхронно, не медленно

Batch — это «обещаю вернуть результат в течение 24 часов», а не «это займёт 24 часа». Типичный P50 — 2-6 часов. Провайдер планирует выполнение вашего batch-задания в периоды низкой нагрузки, когда GPU-ресурсы недоиспользуются.

### Сочетание с кэшированием

Суммаризация 50 тысяч документов с одним и тем же системным промптом на 4К токенов:

- Синхронно без кэша: 50000 × ($input × 4000 + $output × 200) по полным тарифам.
- Синхронно с кэшем: системный промпт кэшируется после первой записи; остальные 49999 запросов получают ввод в 10 раз дешевле.
- Batch с кэшем: всё вышеперечисленное плюс скидка 50% как на чтение, так и на запись.

Итог: batch + кэш = ~10% от счёта за синхронный вариант без кэша. Любая ночная нагрузка с общим системным промптом должна использовать эту комбинацию.

### Распределение нагрузок по категориям

**Interactive** — пользователь ждёт ответа. Важен TTFT. Синхронный вызов с кэшированием промптов. Batch нельзя применять.

**Semi-interactive** — пользователь отправляет задачу и проверяет результат через несколько минут. Асинхронная очередь с фолбэком на синхронный вызов, если batch недоступен. Пример — индексация RAG умеренного объёма.

**Batch** — пользователь ожидает результат «к утру» или «через час». Контент-пайплайны, крупномасштабная классификация, офлайн-анализ. Всегда batch, всегда со стеком кэширования.

Частая ошибка: классифицировать всё как интерактивное только потому, что пайплайн — продакшен. Продакшен — это не спецификация задержки, SLA — вот что определяет требования.

### Ловушка частичной интерактивности

Некоторые функции выглядят интерактивными, но допускают задержку в 5-10 минут. Пример: ночной отчёт о состоянии клиента с кнопкой «обновить». Пользователь нажимает «обновить»; подождать 10 минут — нормально. Команда реализует это синхронно. 50 одновременных обновлений обходятся в 10 раз дороже, чем если бы отчёт формировался через batch и доставлялся по email.

Вопрос, который стоит задать: «Что значат 24 часа для этого пользователя?» Если ответ «они бы и не заметили» — переводите на batch.

### Ловушка схемы вывода

Форматы batch-файлов различаются у разных провайдеров:

- OpenAI: JSONL, один запрос на строку.
- Anthropic: JSONL, одно сообщение на строку; формат ответа встроен.
- Vertex: таблица BigQuery или GCS-префикс с TFRecord.

Написание «единого batch-клиента» для разных провайдеров означает адаптерный код под каждого провайдера. Шлюзы, рекламирующие мультипровайдерный batch (Portkey, некоторые тарифы LiteLLM), всё равно являются лишь тонкой обёрткой над сырым форматом.

### Цифры, которые стоит запомнить

- Скидка batch у всех провайдеров: фиксированные 50% на ввод и вывод.
- SLA по срокам: гарантия 24 часа, типичный P50 — 2-6 часов.
- Batch + кэшированный ввод в сумме: ~10% от стоимости синхронного варианта без кэша.
- Правило распределения нагрузок: если задержка в 24 часа приемлема — всегда используйте batch.
