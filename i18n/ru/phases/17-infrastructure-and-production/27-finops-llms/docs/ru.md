# FinOps для LLM — юнит-экономика и атрибуция в мультиарендной среде

> Традиционный FinOps ломается на расходах LLM. Затраты — это токен-транзакции, а не время работы ресурса. Теги не маппятся — вызов API это транзакция, а не актив. Инженерные решения (дизайн промпта, окно контекста, длина вывода) — это финансовые решения. Playbook 2026 года выделяет три измерения атрибуции, которые нужно внедрить с первого дня: по пользователю (`user_id`) для seat-прайсинга и расширения, по задаче (`task_id` + `route`) для стоимости продуктовой поверхности и приоритизации, по арендатору (`tenant_id`) для юнит-экономики и продления контракта. Четыре слоя токенов — промпт, инструмент, память, ответ — единое ведро скрывает расходы. Лестница принудительных мер для мультиарендных продуктов: лимиты скорости на арендатора (2-3x ожидаемого пика, явный 429 + retry-after); дневной потолок трат (1.5-3x контрактного потолка; запускает ужесточение лимитов + оповещение); аварийные выключатели при z-score трат > 4 (автопауза + вызов дежурного). Паттерны атрибуции: tag-and-aggregate, telemetry-joiner (trace-ID → биллинг; наивысшая точность), sampling-and-extrapolation, model-based allocation, event-sourced, real-time streaming. Юнит-метрика: стоимость за решённый запрос, стоимость за сгенерированный артефакт — а не $/M токенов. Ретроактивное тегирование всегда что-то упускает; инструментируйте в момент создания запроса.

**Type:** Learn
**Languages:** Python (stdlib, toy cost-attribution simulator with kill switch)
**Prerequisites:** Phase 17 · 13 (Observability), Phase 17 · 14 (Caching)
**Time:** ~60 минут

## Учебные цели

- Объяснить, почему традиционный FinOps (теги + тарифы) ломается на расходах LLM, и назвать три новых измерения атрибуции.
- Перечислить четыре слоя токенов (промпт, инструмент, память, ответ) и объяснить, почему биллинг единым ведром скрывает затраты.
- Спроектировать лестницу принудительных мер (скорость → потолок трат → аварийный выключатель) для мультиарендного продукта.
- Выбрать юнит-метрику (стоимость за решённый запрос / артефакт) вместо $/M токенов.

## Проблема

Ваш счёт — $40 000. Вы не знаете:
- Какой арендатор его потратил.
- Какая функция продукта это вызвала.
- Злоупотреблял ли ресурсами какой-либо отдельный пользователь.
- Виноваты ли раздутые промпты, вызовы инструментов или усиление за счёт памяти.

Tag-and-aggregate на стороне провайдера работает для облачных ресурсов (EC2, S3), где теги распространяются на строки счёта. Вызовы API LLM не тегируются автоматически — нужно проставлять user/task/tenant в точке вызова и проносить через весь путь. Ретроактивная атрибуция всегда упускает крайние случаи.

## Концепция

### Три измерения атрибуции

**По пользователю** (`user_id`): кто во что обходится. Определяет seat-прайсинг, разговоры о расширении, выявляет power-пользователей.

**По задаче** (`task_id` + `route`): во что обходится та или иная продуктовая поверхность. Определяет приоритизацию фич, решения об отключении дорогих функций.

**По арендатору** (`tenant_id`): какой клиент прибылен. Определяет юнит-экономику, ценообразование при продлении, пороги тарифов.

Инструментируйте все три измерения в точке вызова с первого дня. Ретроактивно — всегда хуже.

### Четыре слоя токенов

| Слой | Пример | Типичный % от общего |
|-------|---------|---------------------|
| Промпт | системный + пользовательский ввод | 40-60% |
| Инструмент | результаты вызовов инструментов, возвращённые обратно | 20-40% (агентные нагрузки) |
| Память | предыдущий диалог / извлечённые документы | 10-30% |
| Ответ | вывод модели | 10-30% |

Объединение всех четырёх в одно ведро делает оптимизацию слепой. Разделяйте их в своей схеме атрибуции.

### Лестница принудительных мер

1. **Лимит скорости** на арендатора. 2-3x ожидаемого пика. Возврат 429 с `Retry-After`. Арендатор видит трение; никаких неожиданных счетов.

2. **Дневной потолок трат** на арендатора. 1.5-3x контрактного потолка. Триггер: ужесточение лимита скорости + оповещение customer-success.

3. **Аварийный выключатель** при z-score трат > 4 относительно базовой линии арендатора. Автопауза арендатора; вызов дежурного; эскалация в ops + CS.

### Паттерны атрибуции

- **Tag-and-aggregate**: проставление заголовков метаданных; агрегация позже. Просто; грубо.
- **Telemetry joiner**: соединение трейсов с биллингом через trace ID. Наивысшая точность. То, что делают зрелые команды.
- **Sampling + extrapolation**: выборка 5-10%, умножение. Экономически эффективно для грубой оценки трат; упускает хвосты.
- **Model-based allocation**: регрессия для вывода драйвера затрат. Для устаревших данных без тегов.
- **Event-sourced**: затраты как события в потоке (Kafka / Kinesis). В реальном времени.
- **Real-time streaming**: обновления дашборда менее чем за секунду.

### Стоимость за X — это юнит-метрика

$/M токенов — это язык вендоров. Продуктовые метрики:

- Стоимость за решённый тикет поддержки.
- Стоимость за сгенерированную статью.
- Стоимость за успешную задачу агента.
- Стоимость за минуту пользовательской сессии.

Привязывайте стоимость к продуктовому результату. Иначе оптимизация не имеет точки опоры.

### Форма трейса атрибуции затрат

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

Эмитируется на каждый вызов. Хранится в data lake. Агрегируется по измерению. Это живёт в стеке observability из Phase 17 · 13.

### Стек накопленной экономии

Стек: кэш + батч + маршрутизация + шлюз. При всех четырёх:
- Кэш L2 (Phase 17 · 14): ~в 10 раз дешевле ввод.
- Батч (Phase 17 · 15): скидка 50%.
- Маршрутизация на дешёвую модель (Phase 17 · 16): снижение затрат на 60%.
- Эффективность шлюза (Phase 17 · 19): избыточность + повторы.

Лучший случай при наложении: ~5-10% от наивной базовой линии. У большинства команд задействовано 2-3 рычага; немногие используют все четыре вместе.

### Цифры, которые стоит запомнить

- Измерения атрибуции: по пользователю, по задаче, по арендатору.
- Четыре слоя токенов: промпт, инструмент, память, ответ.
- Аварийный выключатель: z-score трат > 4.
- Юнит-метрика: стоимость за решённый запрос, а не $/M токенов.
- Наложенные оптимизации: возможны ~5-10% от базовой линии.
