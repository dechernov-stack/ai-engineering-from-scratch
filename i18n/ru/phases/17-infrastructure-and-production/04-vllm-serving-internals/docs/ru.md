# Внутреннее устройство серверного движка — PagedAttention, непрерывная пакетизация (Continuous Batching), чанковый prefill

> Пропускная способность современного серверного движка опирается на три складывающихся по умолчанию механизма, а не на один трюк. PagedAttention включён всегда. Continuous batching внедряет новые запросы в активный батч между итерациями decode. Chunked prefill нарезает длинные промпты так, чтобы токены decode никогда не голодали. Включите все три — и Llama 3.3 70B FP8 на одном H100 SXM5 выдаёт 2 200-2 400 ток/с при 128 параллельных запросах — примерно на 25% выше дефолтных настроек самого vLLM и в 3-4 раза выше наивного цикла PyTorch. Этот урок разбирает планировщик и ядро внимания vLLM — референсного движка для всех трёх техник — на уровне, который вы сможете нарисовать схематически, и завершается игрушечным continuous-батчером на `code/main.py`, который планирует prefill и decode так же, как это делает vLLM.

## The Problem

Наивный цикл обслуживания на PyTorch обрабатывает по одному запросу за раз: токенизация, prefill, decode до EOS, возврат результата. При одном пользователе это работает. При ста — это очередь терпеливых людей. Очевидное решение — статическая пакетизация — дополняет паддингом каждый запрос до самого длинного промпта в окне, дополняет паддингом каждый decode до самого длинного ожидаемого вывода и останавливает весь батч на самой медленной последовательности. Вы платите за паддинг, который никогда не используете, а быстрые запросы ждут медленных.

vLLM решает три проблемы одновременно. PagedAttention не даёт фрагментации KV-кэша съедать 60-80% памяти GPU, как это происходит при классическом непрерывном выделении памяти. Continuous batching позволяет запросам присоединяться к батчу и покидать его между каждой итерацией decode, так что батч всегда полон реальной работы. Chunked prefill разбивает промпт в 32k токенов на срезы по ~512 токенов, которые чередуются с decode, так что длинный промпт не замораживает каждый токен decode на GPU.

Продакшен-дефолт 2026 года — включить все три. Вам нужно понимать, что делает каждый из них, потому что все режимы отказа находятся в планировщике, а не в модели.

## The Concept

### PagedAttention как система виртуальной памяти

KV-кэш занимает `num_layers × 2 × num_heads × head_dim × seq_len × bytes_per_element` на последовательность. Для Llama 3.3 70B при 8192 токенах это примерно 1,25 ГБ на последовательность в BF16. Если вы заранее резервируете 8192 слота для каждого запроса, но в среднем запрос использует только 1500 токенов, вы тратите впустую примерно 82% зарезервированной HBM. Классическая пакетизация платит за эти потери.

PagedAttention заимствует идею из виртуальной памяти ОС. KV-кэш не выделяется непрерывно на последовательность. Он выделяется блоками фиксированного размера (по умолчанию 16 токенов). У каждой последовательности есть таблица блоков, которая отображает логические позиции токенов в физические идентификаторы блоков. Когда последовательность вырастает за пределы выделенных блоков, добавляется ещё один блок. Когда она завершается, её блоки возвращаются в пул.

Фрагментация падает с 60-80% (классический подход) до менее 4% (PagedAttention). Вы не включаете PagedAttention флагом — это единственный аллокатор, который поставляет vLLM. Настраиваемый параметр — `--gpu-memory-utilization` (по умолчанию 0.9), который указывает vLLM, сколько HBM резервировать под KV-блоки после загрузки весов и активаций.

### Continuous batching на уровне итераций

Старая "динамическая пакетизация" ждала окно (скажем, 10 мс), чтобы заполнить батч, а затем запускала prefill + decode + decode + decode, пока не завершится каждая последовательность. Быстрые последовательности завершались рано и простаивали, пока GPU дорабатывал медленные.

Continuous batching работает между каждым шагом decode. Назовём множество выполняющихся последовательностей списком `RUNNING`. На каждой итерации:

1. Любая последовательность в `RUNNING`, только что достигшая EOS или max_tokens, удаляется.
2. Планировщик смотрит на очередь ожидания. Если есть свободные KV-блоки, он допускает новые последовательности (prefill или возобновлённые).
3. Проход вперёд (forward pass) выполняется для всего, что сейчас находится в `RUNNING`, выдавая по одному новому токену на последовательность.

Размер батча никогда не дополняется паддингом до фиксированного числа. Последовательности на разных позициях своего вывода разделяют один объединённый forward-проход. В vLLM 2026 это называется `V1 scheduler`. Ключевой инвариант: планировщик запускается один раз за итерацию decode, а не один раз за запрос.

### Chunked prefill защищает хвост TTFT

Prefill ограничен вычислениями. Промпт в 32k токенов на Llama 3.3 70B занимает ~800 мс чистого prefill на одном H100. Пока выполняется prefill, токены decode для всех остальных последовательностей в батче ждут. В сервисном цикле задержка первого токена (TTFT) одного длинного промпта превращается в скачок межтокенной задержки (ITL) для десятков других пользователей.

Chunked prefill разбивает prefill на чанки фиксированного размера (по умолчанию 512 токенов) и планирует каждый чанк как единицу. Между чанками планировщик может продвинуть последовательности decode на один токен. Вы жертвуете небольшим абсолютным приростом задержки prefill (несколько мс на чанк) ради значительно более низкого джиттера во время decode. P99 ITL при смешанной нагрузке падает с ~50 мс до ~15 мс в опубликованных бенчмарках.

### Три дефолта взаимодействуют

Все три функции предполагают существование друг друга. PagedAttention даёт планировщику гранулированный ресурс KV, которым можно оперировать. Continuous batching нуждается в этом гранулированном ресурсе, чтобы допуск новой последовательности не требовал глобальной перестройки. Chunked prefill — это решение, которое планировщик принимает по тому же списку `RUNNING` — это ещё одна политика планировщика, а не отдельная система.

Вам не нужно знать каждый флаг. Нужно знать, что оптимизирует планировщик: goodput в рамках бюджета KV-блоков с учётом нарезки chunked prefill.

### Проверка матрицы совместимости

Проверяйте каждую комбинацию функций по матрице совместимости для вашей точной версии vLLM перед тем, как включать их все сразу, потому что совместимость меняется между релизами. В v0.18.0 матрица функций отмечает spekulative decoding как совместимый с chunked prefill и prefix caching, а страница спекулятивного декодирования перечисляет два известных несовместимых случая: конвейерный параллелизм (pipeline parallelism) до v0.15.0 включительно, и спекуляцию с draft-моделью до v0.10.0 включительно. Что касается самого метода draft, дефолт 2026 года часто — EAGLE-3 (`"method": "eagle3"`), рассматриваемый в Phase 17 · 05.

### Как выглядит планировщик

```
while True:
    finished = [s for s in RUNNING if s.is_done()]
    for s in finished: release_blocks(s); RUNNING.remove(s)

    while WAITING and have_free_blocks_for(WAITING[0]):
        s = WAITING.pop(0)
        allocate_initial_blocks(s)
        RUNNING.append(s)

    # schedule prefill chunks + decode in one batch
    batch = []
    for s in RUNNING:
        if s.in_prefill:
            batch.append(next_prefill_chunk(s))   # e.g. 512 tokens
        else:
            batch.append(decode_one_token(s))     # 1 token

    run_forward(batch)                            # one fused GPU call
```

`code/main.py` — именно этот цикл на stdlib Python с фиктивными счётчиками токенов и фиктивной задержкой forward-прохода. Запуск показывает, как chunked prefill удерживает decode-последовательности живыми во время длинного prefill.

## Use It

`code/main.py` симулирует планировщик в стиле vLLM с переключаемыми функциями. Запустите его, чтобы увидеть:

- режим `NAIVE`: по одному запросу за раз, без пакетизации.
- режим `STATIC`: паддинг и ожидание, классическая пакетизация.
- режим `CONTINUOUS`: допуск и освобождение на уровне итераций.
- режим `CONTINUOUS + CHUNKED`: срезы prefill, чередующиеся с decode.

Вывод показывает общую пропускную способность (токенов в виртуальную секунду), среднее TTFT и P99 ITL. Строка `CONTINUOUS + CHUNKED` должна доминировать при смешанном трафике.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| PagedAttention | «трюк с KV» | Аллокатор блоков фиксированного размера для KV-кэша; фрагментация <4% |
| Block table (таблица блоков) | «таблица страниц» | Отображение логической позиции токена в физический KV-блок для каждой последовательности |
| Continuous batching | «динамическая пакетизация, но правильно» | Решения о допуске/освобождении принимаются на каждой итерации decode |
| Chunked prefill | «нарезка prefill» | Разбиение длинного prefill на срезы по 512 токенов, чередующиеся с decode |
| TTFT | «время первого токена» | Prefill + очередь + сеть; при длинных промптах доминирует prefill |
| ITL | «межтокенная задержка» | Время между последовательными токенами decode; доминирует размер батча |
| Goodput | «пропускная способность, соответствующая SLO» | Токенов/сек, при котором каждый запрос всё ещё укладывается в целевые TTFT и ITL |
| V1 scheduler | «новый планировщик» | Планировщик vLLM 2026 года; запускает continuous batching с chunked prefill |
| `--gpu-memory-utilization` | «ручка памяти» | Доля HBM, зарезервированная под KV-блоки после весов и активаций |
