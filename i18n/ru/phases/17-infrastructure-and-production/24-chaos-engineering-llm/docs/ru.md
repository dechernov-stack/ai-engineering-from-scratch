# Хаос-инжиниринг для production LLM

> Хаос-инжиниринг для LLM в 2026 году стал отдельной дисциплиной. Предпосылки перед запуском экспериментов в production: определённые SLI/SLO, наблюдаемость (трассировка+метрики+логи), автоматический откат, runbook'и, дежурство (on-call). Архитектура состоит из четырёх плоскостей: управляющая (планировщик экспериментов), целевая (сервисы, инфраструктура, хранилища данных), защитная (guard'ы + прерывание + фильтры трафика), наблюдаемости (метрики + трассировки + логи), обратной связи (корректировка SLO). Защитные механизмы обязательны: оповещения по скорости расходования бюджета ошибок приостанавливают эксперименты, если суточное расходование error-budget превышает ожидаемое более чем в 2 раза; окна подавления + корреляция по trace-ID устраняют дублирование оповещений. Периодичность: еженедельно — небольшой canary-эксперимент + обзор SLO; ежемесячно — game day + постмортем; ежеквартально — межкомандный аудит устойчивости + картирование зависимостей. Специфичные для LLM эксперименты: перегрузка памяти, сетевые сбои, отказы провайдера, некорректные промпты, штормы вытеснения KV-кеша. Инструментарий: Harness Chaos Engineering (рекомендации на основе LLM, снижение радиуса поражения, интеграция инструментов MCP); LitmusChaos (CNCF); Chaos Mesh (CNCF, нативный для Kubernetes).

**Type:** Learn
**Languages:** Python (stdlib, игрушечный runner для хаос-экспериментов)
**Prerequisites:** Phase 17 · 23 (SRE для ИИ), Phase 17 · 13 (Observability)
**Time:** ~60 минут

## Цели обучения

- Назвать пять предпосылок хаос-инжиниринга (SLI/SLO, наблюдаемость, откат, runbook'и, дежурство) и объяснить, почему пропуск любой из них ломает практику.
- Изобразить на диаграмме четыре плоскости (управляющая, целевая, защитная, наблюдаемости) и контур обратной связи в SLO.
- Перечислить пять специфичных для LLM экспериментов (перегрузка памяти, сетевой сбой, отказ провайдера, некорректный промпт, шторм вытеснения KV).
- Выбрать инструмент — Harness, LitmusChaos, Chaos Mesh — исходя из используемого стека.

## Проблема

Хаос-тестирование в традиционных стеках — устоявшаяся практика. Стеки LLM добавляют новые режимы отказов. Промпт на 4К токенов с «отравленным» символом останавливает токенизатор на 12 секунд. Вышестоящий провайдер отвечает 429; ваш шлюз повторяет запрос; ваш сервис падает по OOM из-за усиленной повторами конкурентности. Шторм вытеснения KV-кеша при всплеске нагрузки вызывает каскады повторного prefill, насыщающие вычислительные ресурсы.

Ничего из этого не проявляется в юнит-тестах. Хаос-инжиниринг — это способ обнаружить такие проблемы раньше пользователей.

## Концепция

### Предпосылки

Не запускайте хаос в production без:

1. **SLI/SLO** — определённых индикаторов и целей уровня обслуживания.
2. **Наблюдаемости** — трассировок, метрик, логов, подключённых к дашбордам.
3. **Автоматического отката** — политика отката по флагам, Phase 17 · 20.
4. **Runbook'ов** — структурированных, Phase 17 · 23.
5. **Дежурства (on-call)** — кому-то нужно реагировать.

Отсутствие любого из пунктов превращает хаос в реальный инцидент.

### Четыре плоскости + обратная связь

**Управляющая плоскость** — планировщик экспериментов (workflow Litmus, расписание Chaos Mesh, UI Harness).

**Целевая плоскость** — сервисы, поды, узлы, балансировщики нагрузки, хранилища данных.

**Защитная плоскость** — аварийный выключатель, окна подавления, ограничения радиуса поражения, шлюзы по бюджету ошибок.

**Плоскость наблюдаемости** — обычные метрики + корреляция по trace-ID, чтобы отличить отказы, вызванные хаосом, от естественных.

**Контур обратной связи** — результаты возвращаются в корректировку SLO, обновление runbook'ов, исправления кода.

### Защитные механизмы обязательны

- **Оповещение по скорости расходования бюджета**: приостановить эксперимент, если суточное расходование error-budget превышает ожидаемое более чем в 2 раза.
- **Окна подавления**: отключить оповещения, не связанные с экспериментом, в зоне радиуса поражения на время эксперимента.
- **Корреляция по trace-ID**: все ошибки, вызванные экспериментом, помечаются тегом, чтобы дежурный мог устранить дубли.

### Пять специфичных для LLM экспериментов

1. **Перегрузка памяти** — вызвать шторм вытеснения KV-кеша, отправляя запросы с длинным контекстом при высокой конкурентности. Наблюдать: сервис корректно сбрасывает нагрузку или падает?

2. **Сетевой сбой** — разорвать соединение между шлюзом инференса и провайдером. Наблюдать: срабатывает ли fallback в пределах SLA? (Phase 17 · 19)

3. **Симуляция отказа провайдера** — 100% ответов 429 от OpenAI. Наблюдать: переключается ли маршрутизация на Anthropic? (Phase 17 · 16, 19)

4. **Некорректный промпт** — внедрить payload, останавливающий токенизатор (например, глубоко вложенный unicode, огромная кодовая точка UTF-8). Наблюдать: блокирует ли единичный запрос воркера?

5. **Шторм вытеснения KV** — вызвать вытеснение, насытив блочный бюджет vLLM. Наблюдать: восстанавливается ли LMCache или сервис деградирует?

### Периодичность

- **Еженедельно** — небольшие canary-эксперименты в staging, возможно 5% production.
- **Ежемесячно** — запланированный game day по конкретному сценарию; участие нескольких команд; постмортем.
- **Ежеквартально** — межкомандный аудит устойчивости; обновление карты зависимостей.

### Инструментарий

- **Harness Chaos Engineering** — коммерческий; рекомендации экспериментов на основе ИИ; снижение радиуса поражения; интеграция инструментов MCP.
- **LitmusChaos** — выпускной проект CNCF; на базе Kubernetes-workflow.
- **Chaos Mesh** — песочница CNCF; стиль CRD, нативный для Kubernetes.
- **Gremlin** — коммерческий; широкая поддержка.
- **AWS FIS** / **Azure Chaos Studio** — управляемые облачные предложения.

### Начинайте с малого

Первый эксперимент: убить под одной реплики decode при стабильном трафике. Наблюдать перенаправление и восстановление. Если это работает и выглядит безопасно — переходите к сетевому хаосу.

Первый специфичный для LLM эксперимент: внедрить одно 429 от провайдера на 5 минут. Наблюдать fallback. Большинство команд обнаруживают, что их fallback не был полностью протестирован.

### Цифры, которые стоит запомнить

- Четыре плоскости: управляющая, целевая, защитная, наблюдаемости.
- Пауза по скорости расходования бюджета: 2x от ожидаемого суточного расходования.
- Периодичность: еженедельный canary, ежемесячный game day, ежеквартальный аудит.
- Пять экспериментов для LLM: память, сеть, провайдер, некорректный промпт, шторм KV.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| SLI / SLO | «целевые показатели сервиса» | Индикатор + цель; обязательная предпосылка |
| Blast radius (радиус поражения) | «область охвата» | Набор сервисов/пользователей, затронутых экспериментом |
| Оповещение по скорости расходования бюджета | «шлюз по бюджету» | Срабатывает, когда скорость расходования error-budget превышает ожидаемую более чем в 2 раза |
| Game day | «ежемесячная тренировка» | Запланированное межкомандное хаос-упражнение |
| LitmusChaos | «CNCF workflow» | Выпускной инструмент хаоса CNCF для Kubernetes |
| Chaos Mesh | «CNCF CRD» | Песочница CNCF, нативный для Kubernetes хаос |
| Harness CE | «коммерческий с ИИ-помощью» | Хаос Harness с рекомендациями на основе ИИ |
