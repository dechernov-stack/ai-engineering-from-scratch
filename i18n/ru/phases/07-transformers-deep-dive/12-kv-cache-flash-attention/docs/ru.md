# KV-кэш, Flash Attention и оптимизация инференса

> Обучение — параллельно и упирается в FLOP. Инференс — последовательный и упирается в память. Разные узкие места — разные приёмы.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 7 · 02 (Self-Attention), Phase 7 · 05 (Full Transformer), Phase 7 · 07 (GPT)
**Time:** ~75 минут

## Проблема

Наивный авторегрессионный декодер выполняет `O(N²)` работы, чтобы сгенерировать `N` токенов: на каждом шаге он пересчитывает внимание по всему префиксу. Для ответа длиной 4K токенов это 16 миллионов операций внимания, большинство из которых избыточны. Каждое скрытое состояние токена префикса детерминировано, как только вычислено, — нужно лишь прогнать запрос нового токена против закэшированных ключей и значений всего, что было раньше.

Вдобавок само внимание перемещает много данных. Стандартное внимание материализует матрицу оценок N×N, выход softmax N×d, финальный выход N×d — слишком много чтений и записей в HBM. При N≥2K внимание становится упирающимся в память раньше, чем в FLOP. Классические ядра внимания используют современные GPU в 4–10 раз хуже возможного.

Две оптимизации, обе от Dao et al., продвинули инференс передовых моделей от «медленного» к «быстрому»:

1. **KV-кэш.** Храните векторы K и V каждого токена префикса. Внимание каждого нового токена — это один запрос против закэшированных ключей. Инференс сокращается с `O(N²)` до `O(N)` на шаг генерации.
2. **Flash Attention.** Разбейте вычисление внимания на плитки так, чтобы полная матрица N×N никогда не попадала в HBM. Весь softmax + matmul происходит в SRAM. Ускорение по времени в 2–4 раза на A100; в 5–10 раз на H100 с FP8.

К 2026 году оба подхода универсальны. Каждый продакшн-стек инференса (vLLM, TensorRT-LLM, SGLang, llama.cpp) предполагает их использование. Каждая передовая модель поставляется с включённым Flash Attention.

### Математика KV-кэша

На слой декодера, на токен, на голову:

```
bytes_per_token_per_layer = 2 * d_head * dtype_size
                          ^
                          K and V
```

Для модели 7B с 32 слоями, 32 головами, d_head=128, fp16:

```
per token per layer = 2 * 128 * 2 = 512 bytes
per token (32 layers) = 16 KB
per 32K context = 512 MB
```

Для Llama 3 70B (80 слоёв, d_head=128, GQA с 8 KV-головами):

```
per token per layer = 2 * 8 * 128 * 2 = 4096 bytes (4 KB)
per 32K context = 10.4 GB
```

Эти 10 ГБ — причина, по которой Llama 3 70B при контексте 128K требует почти всей 40-гигабайтной A100 только под KV-кэш при batch size 1.

**GQA — это выигрыш по KV-кэшу.** MHA с 64 головами заняла бы 32 ГБ. MLA сжимает ещё сильнее.

### Flash Attention — приём с тайлингом

Стандартное внимание:

```
S = Q @ K^T          (HBM read, N×N, HBM write)
P = softmax(S)       (HBM read, HBM write)
O = P @ V            (HBM read, HBM write)
```

Три обращения к HBM туда-обратно. На H100 пропускная способность HBM — 3 ТБ/с; SRAM — 30 ТБ/с. Каждое обращение к HBM — это замедление в 10 раз по сравнению с тем, чтобы держать всё на кристалле.

Flash Attention:

```
for each block of Q (tile size ~128 × 128):
    load Q_tile into SRAM
    for each block of K, V:
        load K_tile, V_tile into SRAM
        compute S_tile = Q_tile @ K_tile^T     (SRAM)
        running softmax aggregation             (SRAM)
        accumulate into O_tile                  (SRAM)
    write O_tile to HBM
```

Одно обращение к HBM на плитку. Общий объём занимаемой памяти падает с `O(N²)` до `O(N)`. Обратный проход пересчитывает некоторые значения из прямого прохода вместо их хранения — ещё один выигрыш по памяти.

**Численный приём.** Скользящий softmax поддерживает `(max, sum)` по плиткам, так что финальная нормализация точна. Это не аппроксимация — Flash Attention вычисляет бит-в-бит идентичный стандартному вниманию результат (с поправкой на неассоциативность fp16).

**Эволюция версий:**

| Версия | Год | Ключевое изменение | Ускорение на эталонном железе |
|---------|------|-----------|-------------------------------|
| Flash 1 | 2022 | Плиточное ядро SRAM | 2× на A100 |
| Flash 2 | 2023 | Улучшенный параллелизм, упорядочение causal-first | 3× на A100 |
| Flash 3 | 2024 | Асинхронность Hopper, FP8 | 1.5–2× на H100 (~740 TFLOPs FP16) |
| Flash 4 | 2026 | 5-стадийный конвейер Blackwell, программный exp2 | Ориентирован на инференс (поначалу только forward) |

Flash 4 на старте работает только с прямым проходом. Обучение по-прежнему использует Flash 3. Поддержка GQA и varlen для Flash 4 ожидается (середина 2026).

### Спекулятивное декодирование — другой выигрыш по латентности

Дешёвая модель предлагает N токенов. Большая модель проверяет все N параллельно. Если проверка принимает k токенов, вы заплатили за один прямой проход большой модели ради k генераций. Типичное k=3–5 на коде и прозе.

Настройки по умолчанию на 2026 год:
- **EAGLE 2 / Medusa.** Встроенные головы-черновики, разделяющие скрытые состояния верификатора. Ускорение в 2–3 раза без потери качества.
- **Спекулятивное декодирование с черновой моделью.** Ускорение в 2–4 раза на потребительском железе.
- **Lookahead decoding.** Итерация Якоби; черновая модель не нужна. Нишевый, но бесплатный подход.

### Непрерывное пакетирование (continuous batching)

Классический пакетный инференс: дождаться завершения самой медленной последовательности, затем начать новый batch. Расходует GPU впустую, когда короткие ответы завершаются раньше.

Непрерывное пакетирование (впервые появилось в Orca, теперь в vLLM, TensorRT-LLM, SGLang): новые запросы подставляются в batch сразу же, как только завершаются старые. Прирост пропускной способности в 5–10 раз для типичных чат-нагрузок.

### PagedAttention — KV-кэш как виртуальная память

Главная фича vLLM. KV-кэш выделяется блоками по 16 токенов; таблица страниц отображает логические позиции на физические блоки. Это позволяет делить KV между параллельными сэмплами (beam search, параллельная выборка), горячо подменять префиксы для кэширования промптов и дефрагментировать память. Прирост пропускной способности в 4 раза по сравнению с наивным смежным выделением памяти.

## Реализация

См. `code/main.py`. Мы реализуем:

1. Наивный инкрементальный декодер `O(N²)`.
2. Декодер `O(N)` с KV-кэшем.
3. Плиточный softmax, имитирующий алгоритм скользящего максимума Flash Attention.

### Шаг 1: KV-кэш

```python
class KVCache:
    def __init__(self, n_layers, n_heads, d_head):
        self.K = [[[] for _ in range(n_heads)] for _ in range(n_layers)]
        self.V = [[[] for _ in range(n_heads)] for _ in range(n_layers)]

    def append(self, layer, head, k, v):
        self.K[layer][head].append(k)
        self.V[layer][head].append(v)

    def read(self, layer, head):
        return self.K[layer][head], self.V[layer][head]
```

Просто: храним растущие списки векторов K, V на токен, по слоям и головам.

### Шаг 2: плиточный softmax

```python
def tiled_softmax_dot(q, K, V, tile=4):
    """Flash-attention-style softmax(qK^T)V with running max/sum."""
    m = float("-inf")
    s = 0.0
    out = [0.0] * len(V[0])
    for start in range(0, len(K), tile):
        k_block = K[start:start + tile]
        v_block = V[start:start + tile]
        scores = [sum(qi * ki for qi, ki in zip(q, k)) for k in k_block]
        new_m = max(m, *scores)
        exp_old = math.exp(m - new_m) if m != float("-inf") else 0.0
        exp_new = [math.exp(sc - new_m) for sc in scores]
        s = s * exp_old + sum(exp_new)
        for j in range(len(out)):
            out[j] = out[j] * exp_old + sum(e * v[j] for e, v in zip(exp_new, v_block))
        m = new_m
    return [o / s for o in out]
```

Результат, бит-в-бит идентичный `softmax(qK) V` за один проход, но в любой момент рабочий набор — это блок `tile × d_head`, а не полный `N × d_head`.

### Шаг 3: сравнение наивного и кэшированного декодирования на генерации 100 токенов

Подсчитаем операции внимания. Наивный: `O(N²)` = 5050. С кэшем: `O(N)` = 100. Код выводит оба значения.

```python
# HuggingFace transformers auto-enables KV cache on decoder-only generate().
from transformers import AutoModelForCausalLM
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.2-3B",
    attn_implementation="flash_attention_2",  # use FA3 if Hopper
    torch_dtype="bfloat16",

```

pip install vllm
vllm serve meta-llama/Llama-3.1-70B-Instruct \
    --tensor-parallel-size 4 \
    --max-model-len 32768 \
    --enable-prefix-caching \
    --kv-cache-dtype fp8

Кэширование префиксов между запросами — большой выигрыш 2026 года: один и тот же системный промпт, few-shot-примеры или длинный контекстный документ повторно используют KV между вызовами. Для агентных нагрузок с повторяющимися промптами инструментов кэширование префиксов рутинно даёт пятикратный прирост пропускной способности.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|-----------------|-----------------------|
| KV-кэш | «Приём, который делает декодирование быстрым» | Сохранённые K и V от каждого токена префикса; новые запросы обращаются к ним вместо пересчёта. |
| HBM | «Основная память GPU» | High Bandwidth Memory; 80 ГБ на H100, 192 ГБ на B200. Пропускная способность ~3 ТБ/с. |
| SRAM | «Память на кристалле» | Быстрая память на каждый SM, ~256 КБ на SM на H100. Пропускная способность ~30 ТБ/с. |
| Flash Attention | «Плиточное ядро внимания» | Вычисляет внимание без материализации N×N в HBM. |
| Непрерывное пакетирование | «Пакетирование без ожидания» | Завершённые последовательности выводятся, новые добавляются, без опустошения batch. |
| PagedAttention | «Главная фича vLLM» | KV-кэш выделяется фиксированными блоками с таблицей страниц; устраняет фрагментацию. |
| Кэширование префикса | «Повторное использование длинных промптов» | Кэширование KV для общего префикса между запросами; значительное снижение затрат для агентов. |
| Спекулятивное декодирование | «Черновик + проверка» | Дешёвая черновая модель предлагает токены; большая модель проверяет k за один проход. |
