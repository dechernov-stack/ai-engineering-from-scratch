# Обработка аудио в реальном времени

> Пакетные (batch) конвейеры обрабатывают файл. Конвейеры реального времени обрабатывают следующие 20 миллисекунд до того, как придут следующие 20. Любой разговорный ИИ, студия вещания и телефонный бот живут и умирают по этому бюджету задержки.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 6 · 02 (Spectrograms), Phase 6 · 04 (ASR), Phase 6 · 07 (TTS)
**Time:** ~75 минут

## Проблема

Вы хотите голосового ассистента, который ощущается живым. Задержка естественного переключения ролей в разговоре у человека (от тишины до ответа) составляет ~230 мс. Всё, что выше 500 мс, ощущается роботизированным; выше 1500 мс — сломанным. Бюджет для полного цикла **услышать → понять → ответить → произнести** в 2026 году выглядит так:

| Стадия | Бюджет |
|-------|--------|
| Микрофон → буфер | 20 мс |
| VAD | 10 мс |
| ASR (потоковый) | 150 мс |
| LLM (первый токен) | 100 мс |
| TTS (первый чанк) | 100 мс |
| Рендер → динамик | 20 мс |
| **Итого** | **~400 мс** |

Moshi (Kyutai, 2024) показал 200 мс в полнодуплексном режиме. GPT-4o-realtime (2024) показывает ~320 мс. Каскадные конвейеры 2022 года поставлялись с задержкой 2500 мс. 10-кратное улучшение достигнуто за счёт трёх приёмов: (1) потоковая обработка на всех уровнях, (2) асинхронный конвейер с частичными результатами, (3) прерываемая генерация.

## Концепция

![Streaming audio pipeline with ring buffer, VAD gate, interruption](../assets/real-time.svg)

**Фрейм / чанк / окно.** Аудио реального времени идёт блоками фиксированного размера. Распространённый выбор: 20 мс (320 отсчётов при 16 кГц). Всё, что ниже по конвейеру, должно поспевать за этим ритмом.

**Кольцевой буфер.** Циклический буфер фиксированного размера. Поток-производитель записывает новые фреймы, поток-потребитель читает их. Предотвращает выделения памяти в горячем пути. Размер ≈ максимальная задержка × частота дискретизации; кольцо на 2 секунды при 16 кГц = 32 000 отсчётов.

**VAD (детектор голосовой активности).** Блокирует работу нижестоящих этапов, когда никто не говорит. Silero VAD 4.0 (2024) работает <1 мс на кадр длиной 30 мс на CPU. `webrtcvad` — более старая альтернатива.

**Потоковый ASR.** Модели, выдающие частичные транскрипции по мере поступления аудио. Parakeet-CTC-0.6B в потоковом режиме (NeMo, 2024) даёт 2–5% WER при задержке 320 мс. Whisper-Streaming (Macháček et al., 2023) разбивает Whisper на чанки для почти-потоковой работы с задержкой ~2 с.

**Прерывание.** Когда пользователь говорит, пока ассистент говорит, нужно (а) обнаружить вклинивание (barge-in), (б) остановить TTS, (в) отбросить оставшийся вывод LLM. Всё это — за 100 мс, иначе пользователь воспримет ассистента как «глухого».

**Транспорт WebRTC Opus.** Фреймы по 20 мс, 48 кГц, адаптивный битрейт 8–128 кбит/с. Стандарт для браузера и мобильных устройств. LiveKit, Daily.co, Pion — стеки 2026 года для построения голосовых приложений.

**Джиттер-буфер.** Сетевые пакеты приходят не по порядку / с опозданием. Джиттер-буфер переупорядочивает и сглаживает их; слишком маленький → слышны провалы, слишком большой → задержка. Обычно 60–80 мс.

### Типичные подводные камни

- **Конкуренция потоков.** GIL Python + тяжёлые модели могут «заморить голодом» аудио-поток. Используйте аудио-библиотеку с C-коллбэками (sounddevice, PortAudio) и держите Python вне горячего пути.
- **Задержка конверсии частоты дискретизации.** Передискретизация внутри конвейера добавляет 5–20 мс. Либо передискретизируйте заранее, либо используйте ресэмплер с нулевой задержкой (PolyPhase, `soxr_hq`).
- **Прогрев TTS.** Даже быстрый TTS вроде Kokoro имеет разогрев 100–200 мс на первом запросе. Кэшируйте модель и прогревайте её фиктивным запуском до первого реального хода.
- **Эхоподавление.** Без AEC вывод TTS попадает обратно в микрофон и запускает ASR на собственном голосе бота. WebRTC AEC3 — это стандартный опенсорсный выбор.

## Постройте это

### Шаг 1: кольцевой буфер

```python
import collections

class RingBuffer:
    def __init__(self, capacity):
        self.buf = collections.deque(maxlen=capacity)
    def write(self, frame):
        self.buf.extend(frame)
    def read(self, n):
        return [self.buf.popleft() for _ in range(min(n, len(self.buf)))]
    def level(self):
        return len(self.buf)
```

Ёмкость определяет максимальную задержку буферизации. 32 000 отсчётов при 16 кГц = 2 с.

def simple_energy_vad(frame, threshold=0.01):
    return sum(x * x for x in frame) / len(frame) > threshold ** 2

## Подводные камни

- **Буферизация 500 мс «на всякий случай».** Буфер *и есть* ваш минимальный предел задержки. Уменьшайте его.
- **Непривязанные потоки.** Аудио-коллбэк на потоке с приоритетом ниже, чем у UI, = сбои под нагрузкой.
- **Слишком маленькие чанки TTS.** Чанки менее 200 мс делают артефакты вокодера слышимыми. 320 мс — оптимальная величина.
- **Отсутствие джиттер-буфера.** Реальные сети подвержены джиттеру; без сглаживания вы получаете щелчки.
- **Однократная обработка ошибок.** Аудио-конвейеры должны быть устойчивы к сбоям. Одно исключение убивает сессию.

## Упражнения

1. **Лёгкое.** Запустите `code/main.py`. Симулирует кольцевой буфер + энергетический VAD; выводит задержки по стадиям для имитированного 10-секундного потока.
2. **Среднее.** Используя `sounddevice`, постройте сквозной (passthrough) цикл, который обрабатывает ваш микрофон кадрами по 20 мс и выводит состояние VAD на каждом кадре.
3. **Сложное.** Постройте полнодуплексный эхо-тест с `aiortc`: браузер → WebRTC → Python → WebRTC → браузер. Измерьте сквозную задержку (glass-to-glass) с помощью импульса 1 кГц.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|-----------------|-----------------------|
| Кольцевой буфер | Циклическая очередь | FIFO-структура фиксированного размера, lock-free (или с SPSC-блокировкой) для аудиофреймов. |
| VAD | Шлюз тишины | Модель или эвристика, размечающая речь и отсутствие речи. |
| Потоковый ASR | STT в реальном времени | Выдаёт частичный текст по мере поступления аудио; с ограниченным забеганием вперёд. |
| Джиттер-буфер | Сетевой сглаживатель | Очередь, переупорядочивающая пакеты, пришедшие не по порядку; обычно 60–80 мс. |
| AEC | Эхоподавление | Вычитает путь обратной связи «динамик → микрофон». |
| Barge-in | Прерывание пользователем | Система обнаруживает речь пользователя во время TTS; должна отменить воспроизведение. |
| Полный дуплекс | Одновременная двусторонняя связь | Пользователь и бот могут говорить одновременно; Moshi работает в полном дуплексе. |
