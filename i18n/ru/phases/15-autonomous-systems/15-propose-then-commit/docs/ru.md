# Человек в контуре: сначала предложение, потом фиксация

> Консенсус 2026 года в отношении HITL конкретен. Это не «агент спрашивает, пользователь нажимает "Одобрить"». Это схема «сначала предложение, потом фиксация»: предложенное действие сохраняется в постоянное хранилище с ключом идемпотентности; представляется рецензенту вместе с намерением, происхождением данных, затрагиваемыми правами доступа, радиусом поражения и планом отката; фиксируется только после явного подтверждения; после выполнения проверяется, что побочный эффект действительно произошёл. `interrupt()` из LangGraph в сочетании с контрольными точками PostgreSQL, `RequestInfoEvent` из Microsoft Agent Framework и `waitForApproval()` из Cloudflare — все реализуют одну и ту же схему. Канонический режим отказа — это штампованное одобрение: кнопка «Одобрить» нажимается без рассмотрения. Задокументированное смягчение — это челлендж-ответ (challenge-and-response) с явным чек-листом.

**Type:** Learn
**Languages:** Python (stdlib, конечный автомат «сначала предложение, потом фиксация» с идемпотентностью)
**Prerequisites:** Фаза 15 · 12 (Durable execution), Фаза 15 · 14 (Tripwires)
**Time:** ~60 минут

## Проблема

Агент совершает действие. Пользователь должен решить: одобрить или нет. Если решение принимается мгновенно, это, вероятно, не рецензирование. Если решение структурировано, это медленно, но надёжно. Инженерный вопрос в том, как сделать структурированное рецензирование путём наименьшего сопротивления.

Паттерн HITL эпохи 2023 года представлял собой синхронный запрос: «Агент хочет отправить письмо X с содержимым Y — одобрить?» Пользователь нажимает «Одобрить». У всех возникает ощущение, что система безопасна. На практике это поверхностное взаимодействие в основном превращается в штамповку: пользователи одобряют быстро, одобрения мало что предсказывают, а когда агент совершает ошибку, журнал аудита показывает длинную историю одобрений, которые пользователь не может вспомнить.

Паттерн 2026 года — «сначала предложение, потом фиксация» — переносит HITL на постоянную основу, прикрепляет структурированные метаданные и требует явной фиксации. Каждый управляемый SDK для агентов поставляет свою версию: LangGraph `interrupt()`, Microsoft Agent Framework `RequestInfoEvent`, Cloudflare `waitForApproval()`. Названия API различаются; схема — нет.

## Концепция

### Конечный автомат «сначала предложение, потом фиксация»

1. **Предложение.** Агент создаёт предложенное действие. Сохраняется в постоянное хранилище (PostgreSQL, Redis, Durable Object). Включает:
   - намерение (зачем агент это делает)
   - происхождение данных (какой источник привёл к этому предложению)
   - затрагиваемые права доступа (какие области действия / файлы / конечные точки)
   - радиус поражения (каков худший сценарий)
   - план отката (если зафиксировано, как это отменить)
   - ключ идемпотентности (уникален для каждого предложения; повторная отправка возвращает ту же запись)
2. **Представление.** Рецензент видит предложение со всеми метаданными. Рецензент — это человек (а не агент, рецензирующий сам себя).
3. **Фиксация.** Явное подтверждение. Действие выполняется.
4. **Проверка.** После выполнения побочный эффект считывается заново и подтверждается. Если шаг проверки не проходит, система находится в заведомо плохом состоянии, и включается оповещение.

### Ключ идемпотентности

Без ключа идемпотентности повтор после временного сбоя может привести к двойному выполнению одобренного действия. Конкретный пример: пользователь одобряет «перевести $100 со счёта A на счёт B». Происходит сетевой сбой. Рабочий процесс повторяет попытку. Пользователь одобрил один раз, но перевод выполняется дважды. Ключ идемпотентности привязывает одобрение к единственному, уникальному побочному эффекту; второе выполнение становится «no-op».

Это тот же паттерн идемпотентности, который используют Stripe и API AWS. Его повторное применение для одобрений агентов явно описано в документации Microsoft Agent Framework.

### Постоянство хранения: почему одобрения переживают процессы

Комната ожидания одобрения — это часть состояния, которой агент не владеет. Рабочий процесс приостановлен (Урок 12). Когда одобрение приходит, рабочий процесс возобновляется точно с этого момента. Именно поэтому LangGraph сочетает `interrupt()` с контрольными точками PostgreSQL, а не только с состоянием в памяти — одобрение, пришедшее два дня спустя, всё ещё находит рабочий процесс нетронутым.

### Штампованные одобрения и смягчение через челлендж-ответ

Интерфейс HITL по умолчанию (кнопки «Одобрить» / «Отклонить») порождает быстрые одобрения без подлинного рассмотрения. Задокументированное смягчение: чек-лист челлендж-ответ, который требует положительных ответов на конкретные вопросы, прежде чем кнопка «Одобрить» становится активной. Конкретная форма:

- «Понимаете ли вы, какой ресурс это затрагивает? [ ]»
- «Убедились ли вы, что радиус поражения приемлем? [ ]»
- «Есть ли у вас план отката на случай сбоя? [ ]»

Это не бюрократия ради бюрократии — это принуждающий механизм. Рецензент, который не может отметить пункты, либо запрашивает разъяснение (эскалация), либо отклоняет (безопасное значение по умолчанию). Исследования Anthropic по безопасности агентов явно указывают HITL на основе чек-листов как смягчение для паттернов штампованного одобрения.

### Что считается значимым

Не каждое действие требует схемы «сначала предложение, потом фиксация». Руководство 2026 года:

- **Значимые действия** (всегда HITL): необратимые записи, финансовые транзакции, исходящая коммуникация, изменения продуктивной базы данных, деструктивные операции с файловой системой.
- **Обратимые действия** (иногда HITL): правки локальных файлов, изменения в staging-окружении, обратимые записи с чётким планом отката.
- **Чтения и инспекции** (никогда HITL): чтение файла, перечисление ресурсов, вызов доступного только для чтения API.

### Проверка после действия

«Фиксация прошла» — это не то же самое, что «побочный эффект произошёл». Разделение сети и состояния гонки могут привести к тому, что рабочий процесс считает, что выполнение прошло успешно, тогда как бэкенд не сохранил изменения. Шаг проверки заново считывает целевой ресурс после фиксации для подтверждения. Это тот же паттерн, что и транзакции базы данных с предложениями `RETURNING` или AWS `GetObject` после `PutObject`.

### Статья 14 Закона ЕС об ИИ

Статья 14 предписывает эффективный человеческий надзор для высокорисковых систем ИИ в ЕС. «Эффективный» — не декоративное слово. Регуляторная формулировка прямо исключает паттерны штампованного одобрения. Схема «сначала предложение, потом фиксация» с челлендж-ответом — это та форма, которая выдерживает проверку по статье 14 согласно документации по соответствию Microsoft Agent Governance Toolkit.

```figure
mx-propose-then-commit
```

## Примените это

`code/main.py` реализует конечный автомат «сначала предложение, потом фиксация» на stdlib Python. Постоянное хранилище — это JSON-файл. Ключ идемпотентности — это хеш от (thread_id, action_signature). Драйвер моделирует три случая: чистый поток одобрения, повтор после временного сбоя (который не должен привести к двойному выполнению), а также штампованное поведение по умолчанию против потока с челлендж-ответом.

## Отправьте это в работу

`outputs/skill-hitl-design.md` рецензирует предложенный HITL-рабочий процесс на соответствие схеме «сначала предложение, потом фиксация» и отмечает отсутствующие метаданные, идемпотентность, проверку или слои челлендж-ответа.

## Упражнения

1. Запустите `code/main.py`. Убедитесь, что повтор одобренного предложения использует постоянную запись и не выполняется повторно. Теперь измените ключ идемпотентности так, чтобы он включал временную метку, и покажите, что повтор приводит к двойному выполнению.

2. Расширьте запись предложения полем `rollback`. Смоделируйте выполнение, у которого шаг проверки завершается неудачей. Покажите, что откат срабатывает автоматически.

3. Прочитайте документацию Microsoft Agent Framework по `RequestInfoEvent`. Определите одно поле метаданных, которое включено в API, но отсутствует в игрушечном движке. Добавьте его и объясните, от чего оно защищает.

4. Разработайте чек-лист челлендж-ответ для конкретного действия (например, «опубликовать пост в публичном Twitter-аккаунте»). На какие три вопроса должен ответить рецензент? Почему именно эти три?

5. Выберите один случай, когда синхронного запроса «Одобрить?» было бы достаточно (без необходимости в постоянном хранилище). Объясните почему и назовите класс риска, который вы принимаете.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|---|---|---|
| Propose-then-commit | «Двухфазное одобрение» | Сохранённое предложение + явная фиксация + проверка |
| Idempotency key | «Токен, устойчивый к повторам» | Уникален для каждого предложения; второе выполнение — no-op |
| Data lineage | «Откуда это взялось» | Конкретное исходное содержимое, приведшее к предложению |
| Blast radius | «Худший сценарий» | Масштаб последствий в случае сбоя действия |
| Rubber-stamp | «Быстрое одобрение» | Нажатие «Одобрить» без подлинного рассмотрения |
| Challenge-and-response | «Принуждающий чек-лист» | Рецензент должен явно подтвердить конкретные вопросы |
| RequestInfoEvent | «Примитив MS Agent Framework» | Постоянный HITL-запрос со структурированными метаданными |
| `interrupt()` / `waitForApproval()` | «Примитивы фреймворков» | Эквиваленты LangGraph / Cloudflare той же схемы |
