# Долгоработающие фоновые агенты: устойчивое выполнение (durable execution)

> Промышленные долгосрочные агенты не работают в `while True`. Каждый вызов LLM становится активностью (activity) с контрольной точкой, повтором и воспроизведением (replay). Интеграция Temporal с OpenAI Agents SDK вышла в GA в марте 2026 года. Claude Code Routines (Anthropic) запускает плановые вызовы Claude Code без постоянного локального процесса. Сессии ставятся на паузу при вводе от человека, переживают деплои и возобновляются с последней контрольной точки, привязанной к `thread_id`. За новой эргономикой стоит старый паттерн — оркестрация workflow — с одним новым элементом: вызовы LLM как недетерминированные активности, которые при восстановлении должны воспроизводиться детерминированно.

**Type:** Learn
**Languages:** Python (stdlib, минимальная конечная машина состояний для устойчивого выполнения)
**Prerequisites:** Phase 15 · 10 (Режимы прав доступа), Phase 15 · 01 (Долгосрочные агенты)
**Time:** ~60 минут

## Проблема

Рассмотрим агента, который работает четыре часа. Он вызывает три инструмента, дважды запрашивает ввод у пользователя и делает сорок вызовов LLM. Посередине процесса хост, на котором он работает, перезагружается. Что происходит?

- В наивном цикле `while True`: всё теряется. Запуск начинается заново. Три вызова инструментов (с реальными побочными эффектами) выполняются повторно. Пользователя снова просят подтвердить то, что он уже одобрил. Сорок вызовов LLM оплачиваются повторно.
- При устойчивом выполнении: запуск возобновляется с последней контрольной точки. Уже выполненные активности не выполняются заново — их результаты воспроизводятся из устойчивого журнала. Пользователь не подтверждает повторно то, что уже одобрил. Уже выполненные вызовы LLM не оплачиваются заново.

Это тот же паттерн, который движки workflow поставляют уже десятилетие (Temporal, Cadence, Cherami от Uber). Новое здесь то, что вызовы LLM теперь представляют собой разновидность активности — недетерминированную, дорогую, с побочными эффектами — и они аккуратно вписываются в этот паттерн.

Сквозная тема урока: надёжность на длинных горизонтах деградирует (METR наблюдает «35-минутную деградацию» — вероятность успеха падает примерно квадратично с ростом горизонта). Устойчивое выполнение позволяет запускам длиться дольше, чем это поддерживает профиль надёжности, — это новый способ безопасно падать при правильном дизайне и небезопасно падать при неправильном.

## Концепция

### Активности, workflow и воспроизведение

- **Workflow**: детерминированный код оркестрации. Определяет последовательность активностей, ветвления, ожидания. Должен быть детерминированным, чтобы его можно было воспроизвести из журнала событий без неожиданных расхождений.
- **Activity**: недетерминированная, потенциально отказоустойчивая единица работы. Вызов LLM, вызов инструмента, запись файла, HTTP-запрос. Каждая активность логируется со своими входными данными и (по завершении) выходными.
- **Event log**: устойчивое хранилище данных. Каждый старт, завершение, отказ, повтор активности и каждое решение workflow фиксируются.
- **Replay**: при восстановлении код workflow заново выполняется с начала; каждая уже завершённая активность возвращает свой залогированный результат без повторного выполнения. Фактически выполняются только те активности, которые ещё не завершились.

Это та же форма, что и перерисовка React относительно виртуального DOM, или восстановление Git рабочего дерева из коммитов. Детерминизм в оркестраторе — это то, что делает устойчивость дешёвой.

### Почему вызовы LLM вписываются в паттерн

Вызовы LLM:
- Недетерминированы (temperature > 0; даже при temperature 0 возможен дрейф между версиями моделей).
- Дороги (деньги и задержка).
- Потенциально отказоустойчивы (лимиты скорости, тайм-ауты).
- Имеют побочные эффекты (если вызывают инструменты).

Это в точности профиль активности. Оборачивание каждого вызова LLM в активность даёт повтор с экспоненциальной задержкой, контрольные точки при перезапусках и воспроизводимую трассу для отладки.

### Контрольные точки, привязанные к `thread_id`

LangGraph, Microsoft Agent Framework, Cloudflare Durable Objects и Claude Code Routines сошлись на одной и той же форме API: `thread_id` (или эквивалент) идентифицирует сессию; каждый переход состояния сохраняется в бэкенд (PostgreSQL по умолчанию, SQLite для разработки, Redis для кэша); возобновление читает последнюю контрольную точку.

Выбор бэкенда имеет значение:

- **PostgreSQL**: устойчив, допускает запросы, переживает деплои. Выбор по умолчанию для LangGraph.
- **SQLite**: только для локальной разработки; теряет данные при смене хоста.
- **Redis**: быстрый, но эфемерный, если не настроены AOF/снапшоты.
- **Cloudflare Durable Objects**: прозрачно распределён; область действия задаётся уникальным ключом; сохраняется часами-неделями.

### Ввод от человека как полноценное состояние

Паттерн «предложить, затем закоммитить» (Урок 15) требует устойчивого состояния «ожидание человека». Workflow ставится на паузу, внешняя очередь хранит отложенный запрос, и подтверждение возобновляет работу ровно с этой точки. Без устойчивости это работает лишь по принципу «постараемся»; с ней же одобрение, пришедшее ночью, позволяет workflow продолжить работу утром.

### 35-минутная деградация

METR наблюдала, что у каждого измеренного класса агентов надёжность снижается после ~35 минут непрерывной работы. Удвоение длительности задачи примерно учетверяет вероятность отказа. Устойчивое выполнение этого не исправляет — оно позволяет работать дольше, чем это поддерживает профиль надёжности. Безопасный паттерн — сочетать устойчивость с контрольными точками, требующими свежего HITL (human-in-the-loop) при повторном входе, и с переключателями бюджета (Урок 13), ограничивающими общие вычисления независимо от затраченного времени.

### Когда устойчивое выполнение — неверный ответ

- Запуски короче нескольких минут без участия человека. Накладные расходы превышают выгоду.
- Строго read-only получение информации.
- Задачи, где корректность требует выполнения «от начала до конца» в пределах одного контекстного окна (некоторые задачи на рассуждение; некоторая генерация за один проход).

## Примените это

`code/main.py` реализует минимальный движок устойчивого выполнения на stdlib Python. Он поддерживает:

- Декоратор `@activity`, который логирует входные и выходные данные в JSON-журнал событий.
- Функцию workflow, которая упорядочивает активности.
- Функцию `run_or_replay(workflow, event_log)`, которая воспроизводит завершённые активности без их повторного выполнения.

Драйвер симулирует workflow из трёх активностей, аварийно завершается на середине и показывает (a) наивный повтор, выполняющий всё заново, в сравнении с (b) воспроизведением, выполняющим только недостающую активность.

## Внедрите это

`outputs/skill-durable-execution-review.md` проверяет предложенное развёртывание долгоработающего агента на корректность формы устойчивого выполнения: активности, детерминизм, бэкенд контрольных точек, состояние ввода от человека и политику HITL при возобновлении.

## Упражнения

1. Запустите `code/main.py`. Понаблюдайте за разницей в количестве выполнений активностей между наивным повтором и воспроизведением. Измените точку аварийного завершения и покажите, как соответственно меняется счётчик при воспроизведении.

2. Переделайте игрушечный движок так, чтобы он явно использовал `thread_id`. Смоделируйте две параллельные сессии, использующие общий движок, и убедитесь, что их журналы событий не конфликтуют.

3. Возьмите одну активность в игрушечном движке. Введите недетерминизм (временную метку настенных часов внутри решения workflow). Продемонстрируйте расхождение при воспроизведении. Объясните, как реальные движки с этим справляются (регистрация побочных эффектов, API вида `Workflow.now()`).

4. Прочитайте статью LangChain «Runtime behind production deep agents». Перечислите все состояния, которые сохраняет этот рантайм, и укажите, какой режим отказа покрывает каждое из них.

5. Спроектируйте политику контрольных точек для 6-часовой автономной задачи по написанию кода. Где вы ставите контрольные точки? Как выглядит возобновление после аварийного завершения? Что требует свежего HITL?

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|---|---|---|
| Workflow | «Сценарий агента» | Детерминированный код оркестрации; воспроизводим из журнала событий |
| Activity | «Шаг» | Недетерминированная единица (вызов LLM, вызов инструмента); логируется до и после |
| Event log | «Бэкенд-хранилище» | Устойчивая запись каждого перехода состояния |
| Replay | «Возобновление» | Повторный запуск workflow; завершённые активности возвращают залогированные результаты без повторного выполнения |
| Checkpoint | «Точка сохранения» | Сохранённое состояние, привязанное к thread_id; при возобновлении побеждает последняя |
| thread_id | «Ключ сессии» | Идентификатор, задающий область устойчивого состояния |
| 35-minute degradation | «Деградация надёжности» | METR: вероятность успеха падает примерно квадратично с ростом горизонта |
| Non-determinism | «Дрейф при воспроизведении» | Настенные часы, случайность, вывод LLM; должны регистрироваться как побочный эффект |
