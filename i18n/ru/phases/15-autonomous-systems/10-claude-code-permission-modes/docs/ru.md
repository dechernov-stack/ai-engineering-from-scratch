# Режимы разрешений для автономных агентов

> Лестница разрешений — градуированные уровни автономии от проверки каждого действия до одобрения всего подряд — это способ, которым харнесс регулирует, что автономный агент может делать без запроса. Claude Code, рабочий пример этого урока, предоставляет шесть таких режимов: "plan" спрашивает перед каждым действием, "default" (обозначен как "Manual" в интерфейсе) спрашивает только для рискованных действий, "acceptEdits" автоматически одобряет запись файлов, но всё ещё подтверждает выполнение shell-команд, а "bypassPermissions" одобряет всё. Auto Mode — режим разрешений `auto` — заменяет одобрение по каждому действию отдельной моделью-классификатором, которая проверяет каждое действие перед его выполнением и блокирует всё, что выходит за рамки запрошенного. Бюджеты действий обеспечиваются через `max_turns` и `max_budget_usd`. Доступность `auto` зависит от плана, включения организацией, модели и провайдера — и Anthropic прямо заявляет, что классификатора самого по себе недостаточно.

**Type:** Learn
**Languages:** Python (stdlib, симулятор двухступенчатого классификатора)
**Prerequisites:** Phase 15 · 01 (Долгосрочные агенты), Phase 15 · 09 (Ландшафт кодинг-агентов)
**Time:** ~45 минут

## Проблема

Автономный кодинг-агент на вашей машине — это отдельная категория безопасности. Поверхность атаки — это всё, что агент может достать: файловая система, сеть, учётные данные, буфер обмена, любая вкладка браузера, любой открытый терминал. Брюс Шнайер и другие публично указывали на это: агенты, использующие компьютер, не являются "обновлением функций" чат-ботов, это новый тип инструмента с новым типом профиля рисков.

Система разрешений Claude Code — это ответ Anthropic. Вместо одного переключателя "автономный / неавтономный" существует шесть режимов, охватывающих лестницу возможностей: plan → default → acceptEdits → … → bypassPermissions. Каждый режим — это особый компромисс между скоростью и проверкой каждого действия. Auto Mode (март 2026) добавляет отдельную модель-классификатор, которая убирает одобрение с критического пути пользователя: она проверяет каждое действие перед его выполнением и блокирует всё, что выходит за рамки запроса.

Инженерный вопрос: что эта система улавливает, что упускает, и какой режим действительно оправдан для данной задачи?

## Концепция

### Шесть режимов разрешений

| Режим | Поведение | Когда использовать |
|---|---|---|
| `plan` | Агент предлагает план; пользователь одобряет весь план; каждое действие проверяется перед выполнением | Незнакомая задача; код, близкий к продакшну; первое использование агента на репозитории |
| `default` | Обозначен как "Manual" в интерфейсе. Агент выполняет действия; запрашивает подтверждение пользователя для любого "рискованного" действия (выполнение shell-команд, деструктивные операции, сетевые вызовы) | Большинство интерактивных кодинг-сессий |
| `acceptEdits` | Запись файлов автоматически одобряется; выполнение shell-команд и сетевые вызовы всё ещё требуют подтверждения | Проход рефакторинга по многим файлам |
| `auto` | Отдельная модель-классификатор проверяет каждое действие перед его выполнением; блокирует всё, что выходит за рамки запроса | Долгосрочные запуски без присмотра в ограниченном рабочем пространстве |
| `dontAsk` | Никогда не запрашивает подтверждение; действия, не предодобренные правилами разрешений, отклоняются | Эфемерные песочницы, задания CI, исследовательские скрипты |
| `bypassPermissions` | Одобряет всё | Документировано как "только внутри эфемерных контейнеров, которые вы готовы выбросить" |

(Названия выше соответствуют публичной документации Claude Code; интерфейс обозначает `default` как "Manual".)

### Auto Mode на одной странице

Auto Mode (запущен 24 марта 2026) — первый режим разрешений, делегирующий одобрение по каждому действию модели. Структура:

1. **Отдельная модель-классификатор.** Проверяет каждое предлагаемое действие перед его выполнением, оценивая его относительно заявленной задачи и текущего состояния сессии, и блокирует всё, что выходит за рамки запрошенного. Заблокированные действия возвращаются пользователю.
2. **Ограниченная доступность.** То, предлагается ли `auto` вообще, зависит от плана, включения организацией, модели и провайдера.

Рядом с классификатором находятся элементы управления бюджетом:

- `max_turns` — общее число итераций в сессии.
- `max_budget_usd` — долларовый предел, прерывающий сессию.
- ограничения по числу действий для каждого инструмента (не более N вызовов `WebFetch` и т. д.).

### Что система улавливает

- Прямое внедрение инструкций (prompt injection) во входные данные инструментов, где внедрённая инструкция соответствует известной форме рискованного действия.
- Повторяющиеся циклы вызова инструментов — классификатор может заметить, что действие N+1 почти идентично действию N, пять раз подряд.
- Явно не относящиеся к задаче shell-команды в сессии, предназначенной только для редактирования файлов.

### Что система может упустить

- **Тонкое внедрение инструкций (prompt injection)**, которое модулирует поведение, не создавая ни одного помеченного действия. Непрямое внедрение инструкций — это не полностью устранимая уязвимость (руководитель отдела готовности OpenAI, 2025, о браузерных агентах — см. Урок 11).
- **Нарушения на семантическом уровне.** Каждое отдельное действие может выглядеть безопасным, в то время как составленная траектория вредоносна. Классификатор оценивает действие; он не воссоздаёт заново намерение пользователя.
- **Эксфильтрация через легитимные каналы.** Запись данных в файл, которым вы владеете, с последующей `git push` в публичный репозиторий — это последовательность разрешённых действий, проблема которой заключается в их композиции.

### Формулировка "исследовательский превью"

Anthropic выпустила Auto Mode как исследовательский превью (research preview). Документация прямо заявляет, что классификатор — это слой, а не решение: от пользователей ожидается сочетание Auto Mode с бюджетами, белыми списками, изолированными рабочими пространствами и аудитами траекторий (Уроки 12–16). Формулировка "превью" также отражает документированный разрыв между оценкой и развёртыванием (Урок 1) — классификатор, проходящий офлайн-оценки, может вести себя иначе в реальной сессии, где контекст пользователя неоднозначен.

### Где эта лестница вписывается в ваш рабочий процесс

- Незнакомая задача: начните с `plan`. Прочитать план дешевле, чем откатывать неудачный запуск.
- Известный рефакторинг: `acceptEdits` экономит много кликов подтверждения.
- Фоновый запуск без присмотра: `auto` только внутри рабочего пространства, чей радиус поражения вы измерили (без учётных данных, без продакшн-монтирований, без исходящего трафика, на который вы не давали согласия).
- Эфемерные контейнеры: `dontAsk` / `bypassPermissions` приемлемы тогда и только тогда, когда контейнер и его учётные данные являются одноразовыми.

## Применение

`code/main.py` симулирует классификатор проверки действий в виде двухступенчатого конвейера — это учебное упрощение; реальный режим `auto` опирается на отдельную модель-классификатор, а не на документированный двухступенчатый контракт. Этап 1 — это дешёвое ключевое правило для предлагаемых действий; Этап 2 — более медленный многоправильный рецензент. Драйвер подаёт короткую синтетическую траекторию (безопасные действия, попытка внедрения инструкций, повторяющийся цикл) и показывает, где классификатор улавливает проблему, а где упускает.

## Реализация

`outputs/skill-permission-mode-picker.md` сопоставляет описание задачи с правильным режимом разрешений, предельными значениями бюджета и требуемой изоляцией.

## Упражнения

1. Запустите `code/main.py`. Какой тип синтетического действия никогда не помечается Этапом 1, но всегда улавливается Этапом 2? Какой не улавливается ни одним из них?

2. Расширьте набор правил Этапа 1, чтобы поймать конкретную известную вредоносную форму (например, `curl $ATTACKER/exfil`). Измерьте частоту ложноположительных срабатываний на выборке безобидных действий.

3. Прочитайте документ Anthropic "How the agent loop works". Перечислите все внешние состояния, к которым агент обращается по умолчанию в режиме `default`. Какие из них вам потребовалось бы изолировать отдельно перед запуском `auto` без присмотра?

4. Спроектируйте бюджет 24-часового запуска без присмотра: `max_turns`, `max_budget_usd`, ограничения по каждому инструменту, белые списки. Обоснуйте каждое число.

5. Опишите одну траекторию, в которой каждое отдельное действие одобряется классификатором, но при этом составленное поведение является несогласованным (misaligned). (Урок 14 рассматривает, как аварийные выключатели и канареечные токены решают эту проблему.)
