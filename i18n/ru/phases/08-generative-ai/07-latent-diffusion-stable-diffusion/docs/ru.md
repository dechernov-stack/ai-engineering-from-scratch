# Латентная диффузия и Stable Diffusion

> Диффузия в пиксельном пространстве на изображениях 512×512 — это вычислительное преступление. Rombach et al. (2022) заметили, что вам не нужны все 786 тысяч измерений для генерации изображения — нужно ровно столько, чтобы захватить семантическую структуру, а остальное отдать отдельному декодеру. Запустите диффузию внутри латентного пространства VAE. Эта идея и есть Stable Diffusion.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 8 · 02 (VAE), Phase 8 · 06 (DDPM), Phase 7 · 09 (ViT)
**Time:** ~75 минут

## Проблема

Диффузия в пиксельном пространстве при разрешении 512² означает, что U-Net работает с тензорами формы `[B, 3, 512, 512]`. Каждый шаг семплирования — это ~100 GFLOPS для U-Net с 500M параметров. Пятьдесят шагов — это 5 TFLOPS на изображение. Обучение на миллиарде изображений делает вычислительные затраты абсурдными.

Большая часть этих FLOPS уходит на прогон через сеть перцептивно неважных деталей — высокочастотной текстуры, которую можно было бы сжать с потерями с помощью VAE. Идея Rombach: обучить VAE один раз (*первая стадия*), заморозить его и запускать диффузию целиком в 4-канальном латентном пространстве 64×64 (*вторая стадия*). Тот же U-Net. В 16 раз меньше пикселей. Примерно в 64 раза меньше FLOPS при сопоставимом качестве.

Это и есть рецепт Stable Diffusion. SD 1.x / 2.x использовали U-Net на 860M параметров над латентами `64×64×4`, SDXL использовал U-Net на 2.6B параметров над `128×128×4`, SD3 заменил U-Net на Diffusion Transformer (DiT) с flow matching. Flux.1-dev (Black Forest Labs, 2024) поставляется с DiT-MMDiT на 12B параметров. Все работают на одной и той же двухстадийной основе.

## Концепция

![Latent diffusion: VAE compression + diffusion in latent space](../assets/latent-diffusion.svg)

**Две стадии, обучаемые раздельно.**

1. **Стадия 1 — VAE.** Энкодер `E(x) → z`, декодер `D(z) → x`. Целевое сжатие: 8-кратное уменьшение по каждой пространственной оси + подбор числа каналов так, чтобы общий размер латента составлял ~1/16 от числа пикселей. Функция потерь = реконструкция (L1 + перцептивная LPIPS) + KL (малый вес, чтобы `z` не была слишком принудительно гауссовой, поскольку нам не нужно точное семплирование из `z`). Часто обучается с adversarial-потерей, чтобы декодированные изображения были резкими.

2. **Стадия 2 — диффузия на `z`.** Рассматривайте `z = E(x_real)` как данные. Обучите U-Net (или DiT) убирать шум из `z_t`. На инференсе: семплируйте `z_0` с помощью диффузии, затем `x = D(z_0)`.

**Текстовое кондиционирование.** Два дополнительных компонента. Замороженный текстовый энкодер (CLIP-L для SD 1.x, CLIP-L+OpenCLIP-G для SD 2/XL, T5-XXL для SD3 и Flux). Инъекция через cross-attention: каждый блок U-Net принимает `[Q = image features, K = V = text tokens]` и смешивает их. Токены — единственный способ, которым текст влияет на изображение.

**Функция потерь идентична Уроку 06.** Та же MSE DDPM / flow matching по шуму. Вы просто меняете домен данных.

## Построение

`code/main.py` надстраивает игрушечный 1-мерный "VAE" (энкодер и декодер-тождество, для демонстрации; настоящий VAE был бы свёрточной сетью) поверх DDPM из Урока 06 и добавляет кондиционирование по классу с classifier-free guidance. Это показывает, что одна и та же диффузионная функция потерь работает как для необработанных 1-мерных значений, так и для закодированных значений — ключевая идея.

### Шаг 1: энкодер/декодер

```python
def encode(x):    return x * 0.5          # toy "compression" to smaller scale
def decode(z):    return z * 2.0
```

У настоящего VAE есть обученные веса. Для педагогических целей этого линейного отображения достаточно, чтобы показать, что диффузия работает над `z`, не заботясь об исходном пространстве данных.

### Шаг 2: диффузия в пространстве `z`

Тот же DDPM, что и в Уроке 06. Данные, которые видит сеть, — это `z = E(x)`. После семплирования `z_0` декодируйте с помощью `D(z_0)`.

### Шаг 3: classifier-free guidance

Во время обучения отбрасывайте метку класса в 10% случаев (заменяя её нулевым токеном). На инференсе вычислите и `ε_cond`, и `ε_uncond`, затем:

```python
eps_cfg = (1 + w) * eps_cond - w * eps_uncond
```

`w = 0` = без guidance (полное разнообразие), `w = 3` = значение по умолчанию, `w = 7+` = насыщенный / переострый результат.

### Шаг 4: текстовое кондиционирование (концепция, не код)

Замените метку класса выводом замороженного текстового энкодера. Подайте текстовый эмбеддинг в U-Net через cross-attention:

```python
h = h + CrossAttention(Q=h, K=text_embed, V=text_embed)
```

Это единственное существенное отличие между диффузионной моделью, кондиционированной по классу, и Stable Diffusion.

## Подводные камни

- **Рассогласование масштаба VAE.** VAE в SD 1.x имеют масштабирующую константу (`scaling_factor ≈ 0.18215`), применяемую после кодирования. Забыв про неё, вы заставите U-Net обучаться на латентах с совершенно неверной дисперсией. Каждый чекпойнт поставляется со своей.
- **Текстовый энкодер молча ошибается.** SD3 требует T5-XXL с >=128 токенами, а откат на CLIP-only даёт потерю качества. Всегда проверяйте `use_t5=True`, иначе точность следования промпту рушится.
- **Смешение латентных пространств.** SDXL, SD3, Flux — все используют разные VAE. LoRA, обученная на латентах SDXL, не будет работать на SD3. Hugging Face diffusers 0.30+ отказывается загружать несовместимые чекпойнты.
- **Слишком высокий CFG.** `w > 10` даёт насыщенные, "масляные" изображения и переобучается под промпт за счёт разнообразия. Оптимальная точка — `w = 3-7`.
- **Утечка негативных промптов.** Пустой негативный промпт становится нулевым токеном; заполненный негативный промпт становится `ε_uncond`. Это не одно и то же; некоторые пайплайны молча по умолчанию используют нулевой токен.

## Упражнения

1. **Лёгкое.** Запустите `code/main.py` с guidance `w ∈ {0, 1, 3, 7, 15}`. Зафиксируйте среднее значение сэмпла по классам. При каком значении `w` средние по классам расходятся дальше, чем средние по реальным данным?
2. **Среднее.** Замените игрушечный линейный энкодер на пару энкодер/декодер tanh-MLP с потерей реконструкции. Переобучите диффузию на новых латентах. Изменилось ли качество сэмплов?
3. **Сложное.** Настройте реальный инференс Stable Diffusion с помощью diffusers: загрузите `sdxl-base`, запустите 30 шагов Euler с CFG=7, замерьте время. Теперь переключитесь на `sdxl-turbo` с 4 шагами и CFG=0. Тот же сюжет, другое качество — опишите, что изменилось и почему.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|-----------------|-----------------------|
| Первая стадия | "VAE" | Обученная пара энкодер/декодер; сжимает 512² до 64². |
| Вторая стадия | "U-Net" | Диффузионная модель над латентным пространством. |
| CFG | "Масштаб guidance" | `(1+w)·ε_cond - w·ε_uncond`; настраивает силу кондиционирования. |
| Нулевой токен | "Эмбеддинг пустого промпта" | Безусловный эмбеддинг, используемый для `ε_uncond`. |
| Cross-attention | "Как текст попадает внутрь" | Каждый блок U-Net обращается к текстовым токенам как к K и V. |
| DiT | "Diffusion Transformer" | Замена U-Net на трансформер над патчами латента; лучше масштабируется. |
| MMDiT | "Мультимодальный DiT" | Архитектура SD3: текстовый и изобразительный потоки с совместным attention. |
| Масштабирующий коэффициент VAE | "Магическое число" | Делит латенты на ~5.4, чтобы диффузия работала в пространстве с единичной дисперсией. |

## Заметка о продакшене: запуск Flux-12B на потребительском GPU с 8 ГБ

эталонная интеграция Flux — это канонический рецепт для вопроса "у меня потребительский GPU, можно ли это вообще запустить?". Трюк — тот же самый рецепт с тремя рычагами, который описывается в литературе по продакшен-инференсу, применённый к диффузионному DiT:

1. **Поэтапная загрузка.** У Flux есть три сети, которым никогда не нужно одновременно находиться в VRAM: текстовый энкодер T5-XXL (~10 ГБ в fp32), CLIP-L (небольшой), MMDiT на 12B и VAE. Сначала закодируйте промпт, затем *удалите* энкодеры, загрузите DiT, выполните деноising, *удалите* DiT, загрузите VAE, декодируйте. Потребительские GPU с 8 ГБ вмещают лишь одну стадию за раз.
2. **4-битная квантизация через bitsandbytes.** `BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.bfloat16)` как для энкодера T5, так и для DiT. Сокращает память в 8 раз, падение качества незаметно для text-to-image согласно бенчмаркам Aritra (ссылка в ноутбуке).
3. **Выгрузка на CPU.** `pipe.enable_model_cpu_offload()` автоматически переключает модули между CPU и GPU по мере продвижения каждого forward-прохода. Добавляет 10-20% задержки, но делает пайплайн вообще работоспособным.

Учёт памяти выглядит так: `10 GB T5 / 8 = 1.25 GB` квантизованный, `12 B params × 0.5 bytes = ~6 GB` квантизованный DiT, плюс активации. В терминах stas00 это крайний случай инференса TP=1 — без модельного параллелизма, максимальная квантизация. Для продакшена вы бы запускали TP=2 или TP=4 на H100, а для одного ноутбука разработчика это и есть рецепт.
